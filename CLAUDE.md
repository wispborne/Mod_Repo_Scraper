# CLAUDE.md

This file provides guidance to LLMs working with code in this repository.

## What this is

A Dart CLI that scrapes Starsector mod metadata from several sources and produces two outputs consumed by the TriOS launcher:

- `outputs/mod-catalog.json` — the catalog: every mod once, with its permanent id and the source posts it came from. Built by one merge over every post's listings — see **The catalog** below.
- `outputs/mod-catalog-details.json` — a richer per-topic bundle with images, download links, and optional LLM-extracted facts (the "QB" pipeline), plus the LLM's answers for Discord threads.

The old `outputs/ModRepo.json` and `outputs/forum-data-bundle.json` are still written the old way until production switches over to `mod-catalog.json` and `mod-catalog-details.json`; after the switch they are frozen, and old TriOS installs keep reading their last contents.

Both pipelines run from one entry point and are toggled independently in `config.properties`.

It also builds a third set of files, for the public website in `site/`. The website is called **Starmodder** (`https://starmodder.wispborne.com/`). When the user says "Starmodder" or "the public site", they mean this website, not the results viewer in `web/`. See **The public website** below. Those are built from the two outputs above; neither of those outputs is changed by them, and TriOS keeps reading the bundle exactly as it did.

## Commands

```bash
dart pub get                       # install deps
dart run bin/scraper_main.dart     # run the scraper (reads config.properties)
dart test                          # run all tests
dart test test/mod_merger_test.dart            # run one test file
dart test --name "substring of test name"      # run tests matching a name
dart test test/llm_live --tags llm --run-skipped   # the live-model tests (needs a local LLM)
dart analyze                       # lint (see analysis_options.yaml for extra rules)
dart run bin/viewer_server.dart    # local read-only results viewer at http://127.0.0.1:8085
dart run bin/link_mod_ids.dart     # one time: link today's permanent ids to their source posts (back up qb_data/mod-ids.json first)
dart run bin/compare_catalog.dart --data <copy of qb_data> --link   # compare a fresh catalog with the published site, by id
dart run bin/site_server.dart      # the public website at http://127.0.0.1:8099, against real data; reloads open pages when site/ changes (--no-reload to stop it)
dart compile exe bin/scraper_main.dart -o mod_repo_scraper   # what CI ships
```

### Code generation (dart_mappable)

JSON models use `dart_mappable`. Every `*.dart` model has a generated `*.mapper.dart` sibling that is committed to the repo. After changing any `@MappableClass` model, regenerate:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Do not hand-edit `*.mapper.dart` files — they are overwritten by the build.

## Configuration

Everything is driven by `config.properties` (read by `Common.readConfig()`; fields live on `BotConfig` in `lib/bot/common.dart`). It holds real auth tokens and is **gitignored** — never commit it, and do not paste its contents anywhere external. `config.example.properties` is the committed stand-in: every key with its default and a plain-English note. **Keep it in step** — a key added, renamed or given a new default here means editing that file too, and `Common._recognizedKeys` is the list to check it against. Every key is snake_case and starts with its group prefix (`modrepo_`, `qb_`, `llm_`); only `log_level` is global. Unknown keys are warned about at startup, so a typo or an old (pre-rename) key name is caught right away. Key switches:

- `modrepo_enabled`, `modrepo_forums_enabled`, `modrepo_discord_enabled`, `modrepo_nexus_enabled` — the ModRepo pipeline and its sources.
- `qb_enabled`, `qb_scope` (`new_data` / `all` / `pages` / `topics` / `libraries_only`; camelCase spellings like `newData` also work), `qb_boards` (`main`/`lesser`/`libraries`) — the QB pipeline.
- `modrepo_use_cached` / `qb_use_cached` — replay from the on-disk raw-HTTP caches instead of hitting the network (see Caching below).
- `llm_enabled` and the `llm_*` keys — optional LLM post-extraction (off in production by default).
- `modrepo_merge_debug` — write `merge-debug.json` for the viewer's Merge view, and save that merge's own snapshot. This decides it for CLI runs only; a merge started from the website always collects it.
- `modrepo_merges_to_keep` — how many merge snapshots to keep (default 20); older ones are dropped. 0 keeps everything.
- `qb_manager_url` — environment. Empty (the default) means the CLI runs the QB job itself, exactly as before. Set (e.g. `http://127.0.0.1:8085`) means it hands the job to that server. Unreachable / manager off / different data folder → warn in plain words and run standalone. Production never sets it.
- `qb_runs_to_keep` — environment. How many runs the history keeps (default 100); older ones are dropped with their log files. 0 keeps everything.
- `publish_site_path` — environment. Where the public website's own files live. Two things read it: a publish copies that folder into the clone next to the data it reads, and the site builder reads its `index.html` to build each mod's own page out of. Defaults to `site`. It has to be one value for both, or the pages would be built from a different copy of the site than the one that goes out.
- `qb_bundles_to_keep` — environment. How many published bundles to keep a snapshot of, for the what-changed page and for how far back one topic's history goes (default 500). About a megabyte each, so roughly 600 MB and about eight months of twice-daily publishing. 0 keeps everything.

## Architecture

Orchestration lives in `lib/bot/scraper/main_repo_scraper.dart` (`MainRepoScraper.main`), which asks for the two pipelines in sequence. Neither is inline any more: both are jobs, submitted to the manager core in `lib/manager/` — one queue, one history, one lock, whether the job was asked for from the command line or from a browser.

### Manager core (`lib/manager/`)

The QB pipeline is callable, not just runnable. `main()` turns the config file's job-shape keys into one `JobRequest` and hands it to a `JobManager`; everything else lives in the core. The web API and the browser UI sit over that same core.

- `job.dart` — `JobKind` (`fullRun`, `rescrapeTopics`, `resolveDownloads`, `extractLlm`, `llmCoveragePass`, `describePictures`, `llmTest`, `rebuildBundle`, `mergeModRepo`, `scrapeAndMerge`, `publishOutputs`, `fetchAndUpdate`, `rebuildFromSaved`), `JobRequest` (what to do), `RunRecord` / `RunCounters` / `RunState` (what happened). `dart_mappable`, so `job.mapper.dart` is generated. `runJob` also takes the `runId`, so anything a job saves next to the run's record and log can be filed under the same name — that is how a merge snapshot gets its name.
- `scraper_settings.dart` — the config split made real. **Environment** (`qb_data_path`, LLM endpoint/model/keys) and **guardrails** (`llm_max_topics`, `qb_delay_ms`, `llm_timeout_seconds`, `llm_idle_timeout_seconds`) go into the service's constructor; **job shape** (`qb_scope`, `qb_boards`, page limits, `qb_use_cached`, `llm_enabled`, `llm_reprocess_only`, `llm_test_mode`) is read only by the CLI, to build its request. The service must never read a job-shape key.
- `scraper_service.dart` — one method per job kind, composing the existing QB pieces. Builds the store, resolver, probe cache and LLM store once; builds the forum HTTP client per job. `fullRun` honours the request's `replayAllowed`; **per-topic kinds always fetch live**, even when `qb_use_cached=true`. Each per-topic kind drops exactly one cache layer's entries for the chosen topics (`QbDownloadResolver.dropTopics`, `DownloadableProbeCache.dropUrls`, `LlmExtractionStore.dropTopics`) and nothing else. `extractLlm` also checks the Discord threads that the last `mod-catalog.json` joined to the chosen topics (`ModCatalog.discordThreadIdsFor`). Their saved answers are kept, not dropped: each thread's pictures are described first, and the thread is read again only when its prompt has changed. Picture descriptions are not part of the fingerprint, so an unchanged thread costs no call even when its pictures were just described. A thread joined only by this run's catalog is not included. A picture skipped because its Discord address has expired is logged (`PictureCaptioner.picturesToLookAt`). `describePictures` shows the model pictures and nothing else: no post is read again and no LLM answer is dropped (`ScraperService._describePictures`, `PostExtractor.describePictures`). With topics named, every picture of those topics and of the Discord threads joined to them is described again, even one that already has a description or was recently unreadable; a saved description stays until a new one replaces it. With no topics named, it goes through every saved forum topic and Discord thread and describes only pictures with no description under the current `captionVersion`. After a caption prompt version change, this updates descriptions without reading posts again. It runs whether or not `llm_caption_pictures` is on, counts against `llm_max_topics`, and ends by rebuilding the bundle, catalog and website so the site picks up the new descriptions. It is not a per-topic kind, so an empty `topicIds` is allowed.
- `job_manager.dart` — a queue, one job at a time, wired to the service, the history store and a reporter. `cancelCurrent()` sets a flag the service checks between topics.
- `run_history_store.dart` — `<qb_data_path>/runs/runs-index.json` plus `runs/<run id>.log`. Written on start, on every state change, and every 10 progress reports; anything still saying `running` at startup becomes `interrupted`. Log capture hooks `DebugTree.extraAppenders` while a run is active — safe because only one job runs at a time. Only the newest `qb_runs_to_keep` runs (default 100, 0 keeps everything) are kept; the rest are dropped on save, log files included, since the logs are what fill the folder. **Only the paperwork goes** — the record and the run's own log. Scraped data (mods index, detail files, every cache, the bundle) all live outside `runs/` and are never touched; a test pins this. The log file named by a record is only deleted if it ends in `.log` and really sits in `runs/`, because that name is read back from a file on disk and this is the one place that deletes anything. The trim happens **after** merging in the other program's runs from disk and before writing — the other way round, a run just dropped would be read straight back as one this copy had never heard of. A run that hasn't ended is never dropped.
- `run_reporter.dart` — `RunReporter` (`phase`, `progress`, `log`). `progress` also carries the run's totals so far (`errors`, `llmCalls`) for the jobs that can count them as they go; leaving one out means "no news", not zero, so a job that can't count something never wipes what is already known (the scrape leaves `errors` alone — the engine only reports failures at the end). This is what makes spending visible while a run is live and honest on a run that dies: the counters ride the same every-10-reports save as everything else. Pinned by `test/manager/live_counters_test.dart`. `ConsoleRunReporter` drives `ConsoleProgressBar` and sends log lines to timber, which is what keeps CLI output identical. `LogRunReporter` is the server's: no bar, but its lines still go to timber, which is how `RunLogCapture` gets them. **Never give the server the silent reporter** — its `log()` drops everything, so a browsed run shows counters with no reasons ("1 error", no word of what went wrong). Pinned by a test. The service talks only to this interface, never to the console.
- `data_lock.dart` — `<qb_data_path>/scraper.lock` (pid, `server`/`cli` label, start time). `JobManager` takes it before each job and releases it in the same `finally`, so completed, failed and cancelled all release. A lock held by a live process is waited for (logged once); one whose pid is dead is cleared and logged. A delegating CLI never takes it — the server holds it for the job.
- `manager_api.dart` — the routes under `/api/manager/`: `GET /status`, `POST /jobs`, `POST /jobs/cancel`, `GET /runs`, `GET /runs/<id>`, `GET /runs/<id>/log?tail=N`, `GET /update`, `POST /update`. Bodies decode with `JobRequestMapper.fromMap`; answers are the mapper maps. `ManagerApi.offHandler(reason)` is the 503 "manager is off" stand-in. **Status is built by hand from four fields** (`managerOn`, `dataPath`, `current`, `queued`) — a test pins that list, because no config value may ever reach the browser. The data path is the one allowed exception; `cli-delegation` needs it.
- `delegation_client.dart` — `ManagerDelegate`: probe `/status`, compare data paths (`p.equals`), submit, poll once a second and drive `ConsoleRunReporter` from the snapshot, print the usual summary (plus the log tail on failure). Returns null when the job should run locally instead, having said why.

`JobManager` takes a `JobRunner` (the interface `ScraperService` implements), so tests can stand in a fake job. `RunHistoryStore.save()` merges in any run on disk it hasn't heard of before writing — two processes each hold their own copy of the index in memory, so writing it as-is would drop the other's runs. Reading works the same way round: `records` and `byId` check the index file's timestamp and size first and re-read when it has changed, so a long-lived server shows runs another program started without being restarted (it would otherwise show the history as of its own startup — worst at the moment you go looking). Runs this copy started (`_ourRunIds`) are kept from memory on that re-read, because ours are only saved every tenth report and the file would wind our own live run backwards.

`llm_test_mode` and `llm_reprocess_only` are no longer branches in `main()` — they pick the `llmTest` and `llmCoveragePass` job kinds. The config keys are unchanged.

### ModRepo pipeline (Forum / Discord / Nexus → merge → ModRepo.json)

Driven by `lib/manager/modrepo_service.dart` (`ModRepoService`), a second `JobRunner` beside `ScraperService`. `JobRouter` (same file) sends each request to whichever of the two owns that kind, and `JobManager` is given the router — so the two pipelines share a queue, a history and a lock while sharing no code, no files and no secrets. **The router also runs the two kinds that need both pipelines**, as two steps of one job: `fetchAndUpdate` is a `scrapeAndMerge` (the forum, plus the chosen Discord and Nexus) followed by a `fullRun`; with no board chosen the forum is left alone by both scrapers, and the second step is an `llmCoveragePass` (or a `rebuildBundle` with the LLM off), so the LLM still reads the Discord threads just fetched; and `rebuildFromSaved` is a `mergeModRepo` followed by a `rebuildBundle`. The merge step is sent with `oldRepoOnly`, so it writes only the old `ModRepo.json`; the QB step then builds the bundle, the catalog and the website once, and saves the Catalog diff data because the request carries `collectMergeDebug` (`MergeDebugWriter` in `merge_debug_writer.dart`, shared by both services, writes `merge-debug.json` and the snapshot to the same places either way). The order is the point: Discord threads must be fetched before the LLM reads them, and the catalog must be built after. A job stopped during the merge step never starts the QB step. Its settings split the same way as the QB half (`ModRepoEnvironment` / `ModRepoGuardrails` in `scraper_settings.dart`): tokens, folders and the snapshot limit are environment; which sources to fetch, page counts and `collectMergeDebug` ride on the request.

Two kinds: `mergeModRepo` merges what is already saved (no network at all), and `scrapeAndMerge` fetches the chosen sources first. **All three sources come back the same way: their `<name>_cache.json`**, written after every successful scrape. Discord has a second way back — replaying `discord_raw_cache.json` — but it is only tried when `discord_cache.json` has nothing to give, and it must stay that way round: that recording is only written by a job that was allowed to replay (`modrepo_use_cached=true`), which production never is, so it is usually missing and, where it exists, usually months stale. Preferring it once cost every merged mod its Discord source. Pinned by a test. `modrepo_use_cached` decides which one the CLI asks for. A source with no token is skipped with a line in the log, not failed. A source a `scrapeAndMerge` did not ask to fetch is not fetched, but its saved results are still merged: leaving them out would take its mods out of `ModRepo.json`. A merge cancelled part-way writes **nothing** — no `ModRepo.json`, no snapshot — because half a merged repo is worse than yesterday's whole one; source caches already written are kept.

- Scrapers: `forum_scraper.dart` (for the old `ModRepo.json` only, until the switch — the catalog reads the forum from QB), `discord_reader.dart`, `nexus_reader.dart`. All three save a per-source `<name>_cache.json` after a successful scrape, and that is what a merge reads back. Discord *additionally* goes through a raw-HTTP `CachingClient` (`discord_raw_cache.json`), which is a dev convenience only — see above.
- The forum's mod index page (topic 177) is today's index followed by one old index per past game version. `ForumScraper.parseModIndex` reads a mod from today's index only, when today's index lists it (matched by topic id); the old posts only add mods today's index leaves out. Reading both gave every mod an old entry carrying the game version of its day, and the merge keeps the highest game version, so TriOS's "[-]" today lost to an old "[0.97a]".
- Merge: `mod_merger.dart` — buckets by forum `topic=<id>`, then a trigram index narrows candidates, then subsequence fuzzy match (`fuzzy/fuzzy.dart`) + author aliases (`mod_repo_utils.dart`), then same-source dedup / merge / validate. Optional `MergeDebugCollector` records why each group formed, written to `merge-debug.json` **and** to that run's snapshot.
- Author names are tidied **last**, once everything else is done (`ModRepoUtils.tidyAuthorNames`, called from `ModMerger._tidyAuthorNames`). Merging pulls the same person in from every source at once, so Nexerelin came out credited to "Histidine", "Histidine, Zaphide" and "histidine_my" — two people written three ways. Credits naming several people are split apart, then spellings of one person are folded together (capitals and punctuation, digits on the end of a Discord name, and the `authorAliases` table) and the best-looking one kept. It has to run at the end: grouping and matching need every spelling a source gave us, and this throws most of them away.
- Category names are tidied straight after the authors, and last for the same reason (`tidyCategoryNames` in `category_aliases.dart`, called from `ModMerger._tidyCategoryNames`). Discord tags a mod "Faction" where the forum's mod index calls that shelf "Faction Mods", so a mod on both came out labelled twice. `discordCategoryAliases` holds **only plain synonyms** — four of Discord's twenty tags. The rest say what a mod *does* (Ship Pack, Exploration, Audio/Visual…) where the forum's ten headings say which shelf it sits on, so there is nothing to fold them into: almost all would land on "Miscellaneous Mods", which for a Discord-only mod is the one useful thing anyone knew about it. Three are left out for their own reasons: "Portrait/Flag Pack" is one tag against two forum headings with nothing to tell them apart, and "Total Conversion" and "Mod Manager" are each near a forum heading without meaning quite the same thing. Every answer in the table must be spelled exactly as the index spells it — a test pins that — or the merge invents a heading the forum does not have. Unknown names are kept as written, and the run logs every category in use so a new tag gets noticed.
- The forum's own old category names are a separate table, `legacyCategoryMap` in `qb/legacy_category_map.dart`, shared with the QB pipeline through `currentCategoryName`. It only applies to a heading the index has stopped using: "Utility mods" is in that table as an old name for "Standalone Utilities", but it is also a live heading today, so it must be left alone.
- Snapshots: `lib/manager/merge_snapshot_store.dart` — one gzipped file per merge run at `<qb_data_path>/merges/<run id>.json.gz`, plus a small `merge-counts.json` holding each one's headline numbers for the list. Gzipped because a real run's data is around 12 MB written out plainly and about a megabyte squashed. The newest N are kept (`modrepo_merges_to_keep`); the trim follows `RunHistoryStore`'s rules to the letter — only `.json.gz` files sitting directly in `merges/`, never the one just written. `merges/` is paperwork, like `runs/`: no scraped data and no output ever lives there.
- Model: `scraped_mod.dart` (`ScrapedMod`, `ModSource`, `ModUrlType`, `Image`).

### The catalog (`lib/catalog/`)

The catalog is the one list of real mods, built once and read as it is by the site and TriOS. It is written to `outputs/mod-catalog.json`, and the facts behind each mod are in `outputs/mod-catalog-details.json`. Neither reader has to work out which mods exist or which LLM answer belongs to which mod any more. The terms are in `CONTEXT.md`: a **source post** is a forum topic, a Discord thread or a Nexus page; a **listing** is one mod as one source post describes it; a **Collection** is a post holding two or more mods.

**Each post is read before anything is merged.** `CatalogInputs.read` turns every source post into its listings, from saved files only:

- A forum topic gives one **rules listing** (`forumRulesListing`): named from the first mod index line that links to it, with that line's author, game version and heading, and the other lines' names kept as other names. A topic the index does not list is named from its title the way the site names it (`displayName`), so the version, the date, a leading dash and anything a cut left dangling ("Everything Recoverable (v") come off. A topic whose post was never saved gives no listing unless the index lists it, the same rule the bundle follows: 97 Modding-board questions were once stored as a title and nothing else, and every one became a "mod". An indexed topic with no saved post still gives its index line's listing, because some sit on boards only members can read (topic 22693 answers visitors with the login page). Otherwise a topic gives a listing when `keepThreadInCatalog` keeps it. That is `keepThreadInBundle` with one more rule: a topic the LLM said is not a mod is kept only when the index lists it or the rules found something to download in it (`assumed-downloads-cache.json`). A game version in the title no longer keeps it on its own, because question threads carry one too ("[0.98a] Null error using the Star Wars mod", topic 33546). Every topic this rule dropped on real data had no download at all: questions, old "MOVED:" threads whose mod is published from its new thread, and work-in-progress showcases. The bundle still uses `keepThreadInBundle`, so the old bundle TriOS reads is unchanged. The dropped topics ride on `CatalogListings.notMods`. QB saves the index lines on each topic (`QbModSummary.indexLines`), today's index first and the old index posts only for topics today's leaves out, and fetches any topic the index lists that it has never stored (`QbScraperEngine.indexTopicsToFetch`). Only a line's own link counts as the index listing a topic, never a link in its notes: the old line for New Galactic Order links a "partial fix" post in help thread 11402, which made that thread a mod. A topic the index lists is always kept, whatever the LLM said about it.
- A Discord thread gives the mod the Discord reader made, with a ref to the thread. A Nexus page gives the Nexus mod. Nexus is not read by the LLM yet.

**The rules listing and the LLM's answer are combined by one rule, for the forum and Discord alike** (`SourcePostListings.combine`). Only the LLM's `main` mods that are grounded count: the name has to be in the post's title or the author's opening run, and a download has to be tied to it. None: the rules listing goes in alone. One: the rules listing goes in with that mod's facts, whatever either is called. Several: one listing each; the rules listing joins the one whose name or nickname matches its own name or other names (`modNamesMatch`), and if none matches the post is a Collection and the rules listing is dropped. Two main mods offering exactly the same downloads count as one, and only the first is kept, because one file cannot be two mods: Discord thread 1355071745366822950 offers one Emergent Threats zip, and the LLM named it twice, which made the thread a Collection. On a forum topic with two or more, a mod whose every download is a link to one other forum topic in this build is that topic's mod and makes no listing: topic 36175 is one author's list of fourteen mods, thirteen linking to a thread of their own, and the LLM took each link for a download, which gave every one of them a second page (two forum topics never become one mod). The rest of the post goes through the rule for several, so a list with no mod of its own is a Collection. These skipped mods ride on `CatalogListings.pointers`, and an old id once given to one leads to the mod on the topic it links to, never to what is left on the list. A Discord thread is left alone, because the merge already joins it to the forum mod by name and author. Add-ons, variants and `separate` mods never become listings. With the LLM off every post gives exactly its rules listing. Where a post has no grounded main mod but the LLM plainly read one (a name match, or its only main mod), that mod's name rides on the ref so its facts can still be found; the listing itself is unchanged.

**One merge over every listing** (`ModMerger.mergeListings`). It is the same merge as ever, carrying each listing's source post on the mod it ends up in (an `Expando` keyed by the mod object). Three rules were added for listings, and each one fixed a real case. Two forum topics never become one mod: a mod's old thread and its new one, or a fork that kept the original's name, keep a page each (the site names the others on each page), and joining them would take an address away. Two mods the LLM read off one post under different names never become one: the topic rule would otherwise join "Derelict Start" and "Remnant Start" back together. Both are checked for whole groups, not just the two entries being compared, so a Discord announcement cannot bridge two threads. A listing carries the downloads the LLM tied to it (`Listing.downloadKeys`, written by `downloadKey` in `download_key.dart` so `?dl=0` and `?dl=1` are one file), and two listings whose names match and that share one of those files match even when the authors do not: All the Domain Drones+ is "Dreadnought70" on the forum and "nathan_the_grudge_bearer" on Discord, and each Discord thread used to come out as a second copy. The LLM's name for each listing (the name on its ref) counts as a name too, both for finding pairs to compare and for the name check: the forum's "Custom LPCs - Create your own wings!" and Discord's "Custom LPCs v1.2.0 - Prometheus (LP IED) Chip Edition" are too far apart for the length check, and the LLM calls both "Custom LPCs". Matches are joined in order: first the ones between posts that already share a permanent id, then the ones through a forum link, then the ones by name and author. That keeps an announcement on the thread it was published with, and stops pages trading posts from one run to the next.

**Permanent ids are found by source post** (`ModIdStore.idForPosts`, called from `ModCatalog.build`). Each entry in `mod-ids.json` now records the posts that belong to it (`posts`, as `forum:34161#Useful.Tithes` or `discord:<thread id>`). A merged mod is looked up through its posts first, and through its name only when none of them has an id. A post asked about under an LLM name it was not linked with falls back to the whole post, but only when the post has one entry. On a post with several, a name the LLM changed between reads (topic 12535's "BSP Peenemunde" came back as "Peenemunde Mobile Battlestation") keeps its id only when it plainly means the same mod (`_renamedEntry`): the old name is gone from the post this run, and the two match by `modNamesMatch` or share a word no other name on the post uses and at most two names in the whole id file use. Exactly one old name may fit, and no other new name may fit it. Being the one name left over on each side never counts: topic 34161 lost "Corrupt.Officials" and gained "Useful.Tithes" in one run, and those are two mods. A post the old site made two pages from, both linked to the whole post, gives the one of those ids that is not also linked to another post in this build (`_wholePostEntryLeft`): topic 35988's Discord thread keeps the page it shared with the topic, and the topic keeps its own instead of getting a new id. Two or more left over is still nobody's. This needs every listing's ref, which `ModCatalog.build` hands to `beginRun`; each re-link is logged. A forum topic's own old id stays with that topic: when a mod has a forum topic, it never takes an id whose whole-topic post (`forum:<id>`, no name) is another topic still in this build, even through a Discord post linked to it. Exotica's Discord thread is Kaysaar's edition (topic 29538), and the old site had it with Lukas04's topic 32811; without this, the Discord thread took 32811's id to 29538 and both topics lost their addresses. `ModCatalog.build` hands ids out in an order: first a mod whose name (or LLM name) matches the name of an old id its posts lead to, then mods with a forum topic, then the rest. The first group is there because the old site sometimes joined a Discord announcement to whatever topic its message linked: "nitelib-update-i" was the Discord thread's NiteLib, and its linked topic 29589 is NebuLib, a different mod. A mod with no forum topic may still take an id tied to a topic, once the topic has had its claim: topic 30580 is now Xxarra's Variety Pack, and NEON's Discord threads keep `neon-s-ship-pack`. Posts pointing at two different ids mean two pages are being joined: the older id wins and the clash is logged. An id is never given to another mod — a name whose id belongs to other posts gets a new numbered one. A Collection's old id is held back first (`reserveCollection`), so its page keeps its address and no mod can land on it; a Collection with no old id gets no id and no page. **An old id no mod is given any more leads to the mod it was joined into** (`ModIdStore.movedIds`, run at the end of `ModCatalog.build`, written to `mod-catalog.json` as `movedIds`). The old site often made one page from a mod's forum topic and a second from its Discord thread; the catalog makes them one mod, and the second address would otherwise stop working. An old id goes to the one mod holding the exact post key it was linked under, else the one mod on any of its posts (or the one of those that goes by its name). An id linked to no post goes to the one mod on its own topic that goes by its name, else the one mod anywhere that goes by its name and, for an id marked with an author, is credited to that author. Never to a topic's mod by the topic alone: topic 30580 was NEON's ship pack and is now Xxarra's Variety Pack. Two mods that fit is nobody's. The move is kept on the id's entry (`movedTo`), so it outlives the posts that made it, for as long as its target is still a mod; an id that is a mod again stops being moved. `bin/link_mod_ids.dart` is the one-time step that links today's ids to their posts, read off the published `outputs/site/mods/<id>.json`; on a shared topic it records the LLM name the old site matching picked. Running it twice gives the same file. Back up `mod-ids.json` before running it on production data.

**Every job that changes listings ends with the catalog** (`CatalogStep`). The ModRepo merge jobs build it after their own merge, and every QB job that rebuilds the bundle builds it again before the site, so a topic the LLM has just found four mods on is four mods when the job ends. It reads saved files only and never calls the LLM. A merge cancelled part-way writes no catalog; a `mod-ids.json` that cannot be read fails the job before anything is written. The merge debug data (and the Merge view) now describe this merge, with each member's source post beside it.

**A mod's facts come from its posts, not from matching names** (`chooseFacts` in `fact_choice.dart`). The site looks up the LLM's answer for each of a mod's source posts by the post's id and the LLM name on the ref, then combines them: each field from the forum answer first and Discord only where the forum left it empty; the downloads as one list (the forum's, else Discord's, else the Discord reader's own link); the mod version the higher of all by TriOS's comparison; between two posts of one kind, the newer first. A mod whose post names an LLM answer the bundle does not have is built without facts and logged in one warning: it means the catalog was built from newer answers than the bundle (a run that saved LLM answers and died before publishing, then a merge), and rebuilding the bundle puts it right.

**The two new files.** `mod-catalog.json` holds one record per mod: its permanent id, the same fields a `ModRepo.json` record has, and `sourcePosts` (kind, id, LLM name, and whether the rules or the LLM found it), plus a `collections` list. It holds none of the bundle's facts. `mod-catalog-details.json` is the bundle plus `discordThreads`: each thread's id, link, name and the LLM's mods, with no message text and no download confidence. Until production switches, `ModRepo.json` and `forum-data-bundle.json` are still written the old way, the old forum scraper still runs for `ModRepo.json`, and the publish job copies only the v2 files.

**Comparing before the switch** (`bin/compare_catalog.dart`, core in `catalog_comparison.dart`). It builds the catalog on a *copy* of `qb_data` (it refuses the real one) and compares it with the published site by id: missing ids (and which of those were joined into another mod), ids that became Collection pages, ids whose posts changed, new mods, Discord threads giving several mods, and names that differ. A page whose only post is a forum topic in `notMods` is listed as **removed on purpose**, not missing: its id stays in `mod-ids.json`, so a showcase that later puts out a download gets its old address back. A page that also had a Discord thread is still missing, because the thread should have kept it. A page whose id is in the catalog's `movedIds` is listed as **leading to the mod it was joined into**, not missing. It exits with 1 while any published id would stop working. The comparison means little until a QB scrape with this code has filled in the index lines and fetched the index-only topics, and until a Discord scrape has saved threads in the new format.

**Discord in the LLM pipeline.** The Discord scrape saves each thread's opening run to `<qb_data_path>/discord-posts.json`, keyed by thread id, under the same all-or-nothing rule as `discord_cache.json` (`DiscordReader.openingRunOf`): the first message with text, then each message straight after it by the same author, stopping at anybody else's or after ten. The coverage pass reads those threads after the forum topics (`ScraperService._discordCoverage`), and "Re-run LLM" on a topic reads the threads joined to it (`ScraperService._discordThreadsJoinedTo`), through the same extractor, the same system prompt and the same limits on calls; the report counts the two apart. A thread becomes a `SourcePost` (`DiscordThreadPost.toSourcePost`), its markdown turned into HTML by the site's Discord renderer so a link stays beside its words. Its answer is stored under `discord:<thread id>` in `llm-extraction-cache.json`, and its download rules' answer under the same key in `assumed-downloads-cache.json`; forum keys stay bare topic ids. A Discord thread's fingerprint is worked out with the signature (`ex`, `is`, `hm`) taken off every Discord attachment address (`LlmExtractionStore.withoutDiscordSignatures`), while the model is still sent the real address: Discord signs a picture's address afresh on every fetch, and with the signature in the fingerprint about three threads in four were read again after each Discord scrape. An answer saved under the old, signed fingerprint is moved to the new one rather than paid for again (`moveFingerprint`), as long as the saved thread still has the signatures it was read with. Discord has its own `ExtractionPrompt.discordPromptVersion`, and only a Discord thread's prompt carries the line saying what it is, so the forum prompt is byte-for-byte what it was (`test/catalog/forum_prompt_unchanged_test.dart` pins the whole prompt and its fingerprint). The viewer shows a thread's messages and answer at `#/discord/<thread id>`, linked from the ModRepo page. A `discord-posts.json` still in the old format (each message link to one string) is read by the site for the Discord panel, and never given to the LLM.

### QB pipeline (`lib/bot/scraper/qb/`)

Adapted from a separate C# project (theRoastSuckling's QBMBAMM); its scraper was ported, but this repo is the consumer's fork. Flow driven by `QbScraperEngine.run(scope, onTopicSaved:)`:

1. `mod_index_scraper.dart` / `board_scraper.dart` walk the configured forum boards for topic summaries. Pinned threads are skipped (the mod index itself, the beginner's guide) **unless today's mod index lists them** — TriOS (topic 29674) is pinned to the top of the Mods board and was never scraped before that exception.
2. `topic_scraper.dart` + `html_processor.dart` fetch and parse each topic page. It keeps the **author's opening run**: the first post, plus each post straight after it by the same author, stopping at the first reply by anybody else (at most ten). The first post fills the fields it always did; the rest ride in `QbModDetail.extraPosts` as `QbForumPost`s with their own HTML, images, links and dates. Some authors keep every download in a second post of their own — topic 35651 lists a dozen forks in the first post and has all seven zips in the second — and reading only the first meant those threads reached the site with nothing to download. Stopping at somebody else's reply is deliberate: further down, the author's answers to bug reports carry links to unfinished builds and version numbers that are not the release. `detail.allLinks` / `allImages` / `openingPosts` are how everything downstream reads the run; **anything hunting for a download, a name or a fact uses those, and only the description keeps reading `contentHtml` alone**.
3. `download_resolver.dart` turns links into download candidates using host-specific rules (Google Drive, Dropbox, MediaFire, GitHub, forum attachments…); cached in `assumed-downloads-cache.json`.
4. Results are persisted incrementally by `json_data_store.dart` into `qb_data_path` as `mods-index.json` plus `mods/<id>/detail.json`.
5. `bundle_publisher.dart` assembles `forum-data-bundle.json` from the store + resolver + LLM store.
6. `ScraperService._rebuildBundle()` publishes it and saves a snapshot of it — see below. Every kind except `llmTest` ends here, so every run that changes what TriOS receives leaves something to compare.

**Bundle snapshots** (`lib/manager/bundle_snapshot_store.dart`): one gzipped file per publishing run at `<qb_data_path>/bundles/<run id>.json.gz`, plus `bundle-counts.json` for the list's headline numbers. **A snapshot is not a bundle** — the posts' `contentHtml` is dropped and a short `contentFingerprint` kept in its place, which takes it from 4.3 MB to 1.15 MB and is what makes keeping hundreds of them affordable. So a changed post is reported as changed and no further; the old words are gone. Each of the author's `extraPosts` loses its text the same way, so a changed second post is noticed without keeping it either. Nothing may publish or serve one as a bundle. The newest N are kept (`qb_bundles_to_keep`, default 500) under the same trim rules as `merges/`: only `.json.gz` directly in `bundles/`, never the one just written. Like `runs/` and `merges/`, this is paperwork — no scraped data and no output lives there. A snapshot that fails to save never fails the run: the bundle went out, and that was the job.

**Backfilling snapshots from git** (`bin/import_bundle_history.dart`, core in `lib/manager/bundle_history_importer.dart`): a one-time command that reads every past version of `forum-data-bundle.json` from the published repo's git history (the publisher commits the bundle on every publish) and files each as an ordinary snapshot, so the history pages reach back before we started saving snapshots ourselves. It runs `git log`/`git show` over a clone (a path you already have, or a URL it clones to a temp folder) and hands each old bundle to `BundleSnapshotStore.save`, so imported snapshots are the same shape, same fingerprints, same folder as real ones. Their names carry a `-imported` tail instead of a job kind (e.g. `20260417T032007Z-imported`) — the only difference, and how `topic_history.js` knows to show them without an "Open this run" link, since no run sits behind them. Names are built from the commit time in the same sortable stamp real run ids use, so imported and real snapshots share one timeline by name alone, and the trim drops the oldest (imported) first once the limit bites. Safe to re-run: each commit always saves under the same name. It builds the store with `--keep 0` by default so a big backfill is never trimmed part-way. Fingerprints are computed the same way as the live path, so the seam between the last imported snapshot and the first real one shows no false "post text changed".

Scraping is pipelined: `onTopicSaved` runs download resolution per topic as it is saved, and **starts** that topic's LLM read without waiting for the answer — the scrape moves on at forum speed while the model works beside it. `llm_max_concurrent_calls` (default 3) is how many topics may be talking to the model at once, wherever the call comes from; the limit lives inside `PostExtractor`, so no caller can overrun it. Every read started is waited for before the scrape step returns (`ScraperService._scrape`), so a finished scrape is still a fully-extracted one; a cancelled run finishes only the reads already talking to the model (`PostExtractor.stopNewCalls`), so Ctrl-C stops the spending too.

### QB LLM extraction (`lib/bot/scraper/qb/llm/`, optional)

When `llm_enabled=true`, `PostExtractor` sends each thread once to any OpenAI-compatible chat endpoint (`openai_client.dart` / `llm_client.dart`, prompt in `prompt.dart`) to pull out facts the rules miss: extra downloads, changelog, mod version, support links, license, a link to where the code is kept, where each mod is described, and optional summaries. `post_reducer.dart` trims post HTML first, leaving each link where it sat as `[link: <url>]`. Results are cached in `llm-extraction-cache.json` via `extraction_store.dart`, so re-runs only pay for new/changed posts. Each entry also records the model and the endpoint that wrote it (the address with any user name, password or query cut off, `OpenAiCompatibleClient.endpointLabel`), which the viewer's thread page shows under "Mods the LLM found" — with a fallback configured, that is how you tell which of the two answered. Neither ever reaches the bundle or the site.

**The answer is streamed, and there are two time limits** (`openai_client.dart`). `llm_idle_timeout_seconds` (default 180) is the longest wait with nothing new arriving. The wait for the first words counts too, and that covers llama-swap swapping models, the model loading and the prompt being read, so it cannot be small. `llm_timeout_seconds` (default 900) caps the whole call. It used to be the only limit, 120 s over a non-streamed call, and a 27B model copying a long changelog out word for word ran past it with nothing to show: the client could not tell a slow answer from a dead server. The total cap is still needed because a model stuck repeating itself never goes quiet. Either limit throws a `TimeoutException` as the `LlmException`'s cause, which is what `_callWithRetry` reads to skip the retry, and stops reading, which closes the connection so the server stops writing too. A server that ignores `stream: true` and answers in one piece is still read. `stream_options.include_usage` is sent because without it a stream carries no token counts; llama.cpp's `timings` arrive in the last chunk either way.

**A second endpoint takes over when the first one lets us down, and what decides it is cost** (`fallback_llm_client.dart`, `endpoint_cost.dart`). `llm_fallback_base_url` plus `llm_fallback_model` turn on a second provider. **Any** failure from the primary sends that post to it and latches the switch for the rest of the run — the server not being there, a timeout, a non-success status, an answer envelope that can't be read. The latch is what stops a sleeping or broken server being knocked on once per topic, paying a full timeout each time; a fresh run builds a new wrapper and tries the primary again. What the rule is *not* about is which failure happened, which is how it read until now ("only connection failures fall back") — the reason it was written that way was cost, since one 500 from a free local server would have moved a whole run onto a paid endpoint.

So the money question is asked directly instead. `endpoint_cost.dart` works out whether each endpoint charges per token, from its address and model name alone — no network call, no price table: a loopback, private-network or `.local` host is free, a model name ending `:free` is free (OpenRouter's own mark), everything else is paid, an unparseable address included, because guessing "free" is the answer that spends money. Only one pairing is blocked: a **free** primary with a **paid** fallback, and `llm_fallback_free_to_paid` (default false) reopens it. Both paid, both free, or a paid primary with a cheaper fallback always switch. **So a local primary with a cloud fallback needs `llm_fallback_free_to_paid = true`, or the fallback never fires** — the wrapper says so in the log when it is built, rather than at the first failure, so a fallback that can never fire is known about before the moment it was needed. The comparison happens in `ScraperService._buildExtractor`; the wrapper is handed one boolean and knows nothing about URLs.

Two limits worth knowing. The extraction JSON is parsed **above** the client, in `PostExtractor`, so a model that answers with unusable JSON never reaches the fallback rule at all — it keeps the retry-at-a-higher-temperature path, and `llm_structured_output = true` on the primary is what actually prevents it. And a bad `llm_base_url` is now absorbed by the fallback rather than showing up as failed calls; the switch log line quotes the error, so the typo is still visible.

**One thread is one call**, and the whole opening run goes into that one prompt (`_ReadPosts` in `post_extractor.dart`): the first post under `=== POST TEXT ===`, then each of the author's later posts under its own `=== FOLLOW-UP POST N ===` heading, with the links, rule-detected downloads and images merged across them all. Splitting it into a call per post would be worse in every way — the answer is one `mods` list about the whole thread, so a thread that names its mods in one post and downloads them in another would give one call mods with no downloads and the other downloads with nothing to attach them to; merging the two answers would mean matching the model against itself by name, and a disagreement there mints a duplicate mod with a permanent id; and the system prompt would be paid once per post instead of once per thread. Size is not the worry: topic 35651's first post is 4,234 prompt tokens and its second adds about 700, against a corpus average of 4,730 and an existing maximum of 33,195. Grounding reads the same run, so a URL in the second post counts and one in somebody's reply never does. `llm_max_input_chars` applies to the posts together, and **the later posts keep their words while the first post gives up the room** — they are short and download-dense, the first post is the long write-up, so trimming in posting order would push the Downloads post out of the prompt entirely.

Coverage is over the **store**, not over this run's scrape. `ScraperService._llmCoveragePass` walks the whole mods index after the scrape and calls `extractForTopic` on every stored topic, so a topic that was scraped before the LLM was switched on still gets picked up. The pass works a few topics at a time — the same `llm_max_concurrent_calls` — so the topics that do need a call overlap instead of queueing one behind another. Topics scraped this run were already extracted beside the scrape and come back as free store hits in the pass, so they are not paid for twice — that rests on `extractForTopic` doing its freshness check *before* `_reserveSlot()`. `llm_max_topics` caps live calls per run (not topics visited), so a big backlog can be worked through in bounded chunks; each run resumes where the last stopped, and logs how many topics still have no results.

**A link is left where it sat, written as `[link: <url>]`** (`PostReducer.reduce`). Stripping the tag used to throw the URL away: the model got a mod's name in one place and a flat list of URLs at the foot of the prompt, with nothing saying which went with which. On a thread offering several mods — a name, a paragraph and a download each, one after another — sitting next to each other is the only thing tying a download to its mod. Topic 35651 is the case that proved it: every download there is a shields.io badge inside a link with no words of its own, in the author's second post, and the model came back with one mod called "Computica's Faction Forks" carrying all seven zips. The badge itself is no help — `isBadgeOrDonationImage` drops shields.io before the model sees it, which is right, and that is where the words "KWIN RELEASE" were. The separate `=== LINKS IN THE POST ===` list stays: it is the canonical list and carries the `[flagged downloadable]` marks. The prompt tells the model the marker is ours, not the author's, so it must never be copied into a name, a changelog entry or a `descriptionAnchors` anchor — an anchor that swallowed one would fail the slice and be thrown away. `ReducedPost` never leaves the extractor, so no marker can reach the bundle or the site.

**The prompt is written against the model's pull toward one mod.** Three lines used to point that way at once — "most posts describe exactly one mod", "a mod named in the first post is very often the same mod a later post has the download for", and the hard rule "one mod named in the first post and downloaded in a second is ONE entry", which read literally is exactly the shape of a collection thread. They now say what they mean: one mod written about twice is one entry, while a thread naming several mods with a download each is several. The thread's title names the shelf, not a mod, and a name with no download (topic 35651's first post lists forks that are not out yet) is not an entry at all.

**`role` is about the other mods on the same thread, and nothing else** — which matters because only a `main` mod becomes a listing of its own (`SourcePostListings.combine`, `release_detector.dart`), an `addon` or a `variant` is listed on its parent's page, and a `separate` one goes nowhere at all. So the wording has to decide two shapes that look alike. On a thread of mods that do not need each other — Hartley's four — **every one of them is `main`**; the model used to answer `separate` for all four, which would have quietly un-published them. On a thread whose first mod is a library the rest will not run without — Yunru's six — that library is `main` and the rest are `addon` with `requires` naming it; the model used to answer six `main` mods, which would have minted five permanent ids for five pages all offering the same Patreon link. The rule that decides both, and the one the prompt now states with a worked example: a mod that needs another mod **from this thread** is an `addon`, and `needs` is only for mods you get somewhere else. `separate` is written as a last resort with "when in doubt, choose main", because a `separate` mod is silently dropped. Both shapes are pinned by `test/llm_live/`.

**A tool is kept, and marked as a tool** (`isTool` on `LlmMod`). A mod manager, a launcher or an editor is made for Starsector but run beside it rather than loaded into it. The prompt used to give such a thread `isMod: false`, which was the wrong question: `isMod` decides whether a thread is kept at all, so a tool with no game version in its title was dropped from the bundle. Now a tool thread is `isMod: true` and each entry carries `isTool: true`, listed with its downloads like any mod. The flag is on the entry rather than the thread because a thread can offer a mod and an editor together, and because the entry reaches the bundle while `isMod` does not — so it is what TriOS reads to avoid offering to install an `.exe` as a mod. It is written **only when true**; an entry that is not a tool, and every entry read before the field existed, carries no field at all, so nothing else in the bundle moves. `role` is untouched by it: a tool on its own thread is `main`. The site publishes it as `PublicMod.isTool` (again only when true), draws a "Tool" badge, and puts every tool under Utilities whatever the sources said (`_categoriesFor` in `public_data_builder.dart`). Pinned live by topic 35155.

**A mod's other names are read off the post** (`nicknames` on `LlmMod`, `_groundNicknames` in `post_extractor.dart`). Players search by shorthand — "IndEvo", "SWP", a name the mod used to have — and the site's search can only find what is written down somewhere. So the model is asked for the other names the post itself uses for each mod, and each one is **kept only when it stands as a whole word in the author's own words**: the title, the post text with our `[link: …]` notes taken out, and the words of each link — never a link address or a file name, where "Ships_v2.zip" would make "Ships" a nickname. A model asked for a short name will offer the initials whether the post writes them or not, and a made-up nickname sends a reader to the wrong mod, so that check is the whole point. The mod's own name, a name with no letters (a version), and repeats go too, and at most five are kept. It is written **only when there is one**, like `isTool`, so most entries read as they always did. The site publishes it as `PublicMod.nicknames` (left out when empty; `_nicknamesFor` also drops one that only repeats a name the mod is already published under), and the viewer's thread page shows it as "Also called". Pinned live by topic 21968, where one pack is "Formerly known as the Pirate Collection", and by 25868, where MagicLib's post gives one of its *parts* another name that must not become MagicLib's.

**A support link is only the mod's own author's, and carries a label** (`supportLinks` on `LlmExtras`, `LlmSupportLink.label`). Posts credit other people — Draconis Fleet (topic 33489) lists a composer, an artist and a playtester, each with "Support him here!" — and the model used to take every one; the site called them all "Support the author", so that mod showed five identical buttons. The prompt now asks only for links that support the mod's own author, with a worked example of a credits line. Each link also gets a 1–4 word `label` from the model, because a donation link rarely has words of its own (DarkRevenant's is a picture button on `sc2mafia.com`, and naming it by its host says nothing). `SupportLinkType.cleanLabel` throws out a label that is too long or holds an address. Two rules are in code, not the prompt, because the model kept breaking them: `SupportLinkType.isNeverSupport` drops forum threads and feedback forms, both in the extractor and again in `PublicDataBuilder` so answers read before the rule existed are cleaned too. The site names a known platform by its own name (Patreon, Ko-fi…), anything else by its label, and failing that by its host — never one shared word. Pinned live by 33489 (no credits taken) and 10982 (GraphicsLib's wordless donate button kept and labelled).

**What the author says about AI use** (`aiUse` on `LlmExtras`, `_groundAiUse` in `post_extractor.dart`). Some readers want to know which parts of a mod were made with AI tools, and authors say so in credits lists and spoilers. The model points at the author's statement the way it points at a description: a statement of 12 words or fewer is copied whole into `quote`, and a longer one is given as its first words (`startsWith`) and last words (`endsWith`). The code cuts the words between them out of one post (`cutQuote` in `qb/llm/quote_cut.dart`) and stores that as `quote`, so the stored quote is always the author's own text, line breaks and list marks included, and the stored shape did not change. The ends are matched on letters and numbers only, with our `[link: …]` notes taken out; the cut is widened to the nearest space at both ends, and a cut over 1,000 characters is dropped, because two ends make it cheap to point at half a post by mistake. The model also answers `usesAi`: true when AI was used, false when the author says none was. It then sorts the uses. Each use has an `area` (portraits, illustrations, sprites, icons, music, voice, writing, translation, code, other) and may have `how` (generated, edited, assisted), `extent` (all, most, some) and `optional`. The statement must be in the post, or the whole answer goes. A copied `quote` is compared word by word, ignoring punctuation, list marks and line breaks (`_wordsInPost`), because these statements are often a list and the model joins the items without their "- " marks (topic 19830). The post with our `[link: …]` notes taken out counts too, because a statement often names the tool's maker as a link (topic 25905). **Three different things, never to be confused:** no `aiUse` at all means the post has not been read with a prompt that asks about AI use yet; an `aiUse` with no `usesAi` (`LlmAiUse.notStated()`, written `{}`) means it was read and says nothing usable; `usesAi: false` means the author said no AI was used. So every mod read with this prompt carries an `aiUse`, and a dropped answer becomes "not stated", never nothing. A "no AI" answer that still lists uses is dropped and logged. An AI answer that names no part gets one use under `other`. A value outside the lists is dropped, and an unknown area takes its use with it. Each tool name must stand as a whole word in the author's own words (the nickname check), at most five, and tools are kept only when AI was used. "AI" in a Starsector post usually means ship AI or AI cores, so the prompt has worked examples of both: AI Tweaks (topic 28428) has no `aiUse`, and the AI-core portrait pack (25905) has portraits. A statement written for a whole thread goes on every `main` mod. Forum and Discord answers are never merged: `chooseFacts` takes the first answer that states something, forum before Discord, and only when none does the first "not stated" one, because joining a forum "no AI" with Discord "AI portraits" would misquote both. Written only when there is a statement. Live tests cover 28428, 25905, 18751 (five uses, and sprites must not be one), 19830 (a list), 22826 (an optional portrait pack named only in a section heading), 31982 ("zero AI generated content"), 33509 (translation only) and 36167 ("Claude Code built this anyway", which gives no explicit amount but refers to the whole mod, so its code is "all").

**Every version the extractor stores is written without a leading "v"** (`PostExtractor.plainVersion`): the mod's version, the changelog's version keys and each update note's version. The model wrote "v3.0.2" on one run and "3.0.2" on the next for the same post, and every flip showed up as a change in the diffs and the topic history. The prompt asks for it too, but the code is what makes it hold. Only a "v" or "v." straight before a digit is taken off; "0.12.2c" and "1.0-rc1" are kept as written. The check against the post runs on the model's own spelling first, so nothing is dropped for it.

**The model can be shown each post's pictures first** (`picture_captioner.dart`, `picture_caption_store.dart`, `llm_caption_pictures`, off by default). Before a post is read, the pictures the prompt would list (the same `isBadgeOrDonationImage` filter, the first ten) that have no saved description go to the model in **one call per post**, and it answers with each picture's kind (screenshot, logo, banner, art, button, badge, divider, missing, other), how well it would do as the small picture on the mod's card (`fit`: good, okay, poor) and one sentence. "Missing" is a host's "picture gone" placeholder: old Photobucket and imgbox links answer with one instead of an error, and nothing but the model can tell it from a real picture. Changing the caption prompt means raising `PictureCaptionStore.captionVersion`, then running the "Scan images" job (`describePictures`) to describe the old pictures again without reading any post again. **The model sees what the server hands it, which is not always what a reader sees**: Photobucket hides its own "Groupsy by photobucket" text in the see-through pixels of old pictures, and a server that throws the see-through layer away (rather than laying the picture on a background first) shows the model that text. Topic 1619's tiny fighter sprites came back as a Photobucket notice, then as the mod's logo, depending on the prompt; no prompt wording fixes it, the server's picture handling does. The prompt never quotes a host's placeholder words, because the model copies them, and it says the title names the mod, never what a picture shows. The extraction prompt then lists each described picture as `- <url>  (seen: banner: …)`. The LLM used to see addresses only, and on about a third of the forum threads with pictures it chose none for the mod. Five rules hold it together:
- **The model's server fetches the pictures**, by address. Nothing is downloaded or saved by the scraper; the user did not want pictures on the server or in the published repo. A server that cannot fetch one picture fails the whole call with a 400 and does not say which, so a failed call is asked again one picture at a time; a dead one fails in under a second and is remembered as unreadable for 30 days. A 400 that calls an address invalid counts as a bad picture too. An address that is not an http(s) address with a host is never sent (`isWebAddress`): topic 29956's picture tag holds a Markdown link, which the server rejected as "Invalid IPv6 URL", so none of that post's pictures were ever described. A 400 whose words are not about reading a picture (a model that takes no pictures at all) blames no picture, and five failed calls in a row stop captioning for the run.
- **One call per post, not per picture**: on the server this was measured against a call costs about 13 seconds whatever it holds, and four pictures cost 16.
- **Captions go to the primary endpoint only**, never through `FallbackLlmClient`, so an unreadable picture can never latch the fallback or start spending on a paid one.
- **A Discord picture whose signature has run out is not sent** (`discordLinkExpired`): it would come back "not found" and be wrongly remembered as dead. Discord pictures are filed without their query, like the fingerprint.
- **Saved captions are always used, even with captioning off**, and a picture with none is listed exactly as before, so the forum prompt of a post nobody looked at is byte-for-byte unchanged (`forum_prompt_unchanged_test.dart` still holds). **Picture descriptions are not part of the fingerprint**: it uses the prompt without `(seen: …)` descriptions (`_buildUserPrompt` in `post_extractor.dart` returns both prompts). Adding or changing descriptions, or raising `captionVersion`, does not cause another post read. The LLM sees new descriptions the next time the post is read for another reason. A saved answer with descriptions in its fingerprint moves to the new fingerprint without another LLM call if the prompt still matches. The system prompt's line about `(seen: …)` is not part of the fingerprint either. A caption call counts against `llm_max_topics` and takes one of the `llm_max_concurrent_calls` turns. The viewer's thread page shows each picture, then the saved details for it. These include the picture kind, its suitability for a mod card, and its description or the server error message. It also shows the model, endpoint, date and time, and caption prompt version. A prompt version is marked outdated when it differs from the current version. Starmodder publishes the saved description (`aiCaption`), kind (`aiKind`), and card picture rating (`aiFit`) for each gallery picture. It publishes `aiUnreadable: true` when the model's server could not read the picture. It does not publish the model, endpoint, or server error message. The gallery hover text and full-size picture viewer show the kind and rating on a separate line below the description. If the server could not read the picture, this line says so instead. The line is built by `imageAiFacts` in `site/lib.js` and follows the same AI settings as picture descriptions.

Two special modes, now job kinds rather than branches: `llm_reprocess_only` → `llmCoveragePass` (the same coverage pass, minus the scrape, then rebuild the bundle) and `llm_test_mode` → `llmTest` (small non-persisting trial → `llm-test-output.json`).

#### Live-model tests (`test/llm_live/`)

Every other test feeds the extractor a canned answer, so they check the code around the prompt and never the prompt itself. These run the **real model against real saved forum posts** (`test/llm_live/posts/<topic id>.json`, real `detail.json` files with the scrape timestamp and the local image paths taken off) and check the facts it pulls out. Ten threads so far, each there for a reason the README lists: a plain one-mod control, a mod whose post names exactly one requirement, two collection threads, a library with add-ons, a sentence that answers two save questions at once, a question thread that is not a mod at all, a mod manager that is a tool rather than a mod, a credits list whose "Support him here!" links are not the author's, and a donate button with no words that must still be kept. Eleven real Discord threads sit beside them in `test/llm_live/discord/` (one-mod announcements, update messages, add-ons, two independent mods in one thread, one mod in two builds, a requirement linked in the post, a tool, and the channel's pinned template), read through the same extractor.

- **They are skipped by `dart test`.** `dart_test.yaml` gives the `llm` tag a `skip` with the command to run them in it, so the skip line tells you what to type: `dart test test/llm_live --tags llm --run-skipped`. They take minutes and need a model.
- **Settings come from `config.properties`** (`llm_base_url`, `llm_model`, and the token), so the tests read whatever the real runs read; `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_TOKEN` override without touching the file. No model server, or a server that doesn't offer that model, and each test skips itself saying which — with `markTestSkipped`, not a `skip:` argument, so `--run-skipped` cannot force a run against a server that isn't there.
- **A failure is a prompt to tighten, not a broken build.** The model is not deterministic even at temperature 0, so a check that fails once and passes twice is noise. Every check prints everything the model said (`describe()`), because the point is to be able to act on the failure without running it again by hand.
- **Loose about wording, strict about facts.** Names are compared on letters and digits only (`sameName` / `nameHolds`), and a download is checked by the bit of its address that says which mod it belongs to. So "Kwin's" versus "Kwins" never fails, and the wrong download under the wrong mod always does. Keep new checks that way round.
- The download resolver is given a mock HTTP client, so a run never reaches GitHub. Only the model call is live.

### Caching model (important)

Two independent cache layers — do not conflate them:

- **Raw-HTTP caches** (`CachingClient`): `discord_raw_cache.json`, `<qb_data_path>/qb_raw_cache.json`. When `use_cached`/`qb_use_cached` and the file exists, the client *replays* recorded responses (`isReplaying == true`) and the throttle delay drops to 0. Caches are only re-saved when not replaying. When recording, each response is written to the file as it arrives (one JSON object per line), so an interrupted run keeps what it fetched; `CachingClient.fromFile` also reads the older "one big JSON list" format.
- **Derived caches**: per-source `<name>_cache.json` (ModRepo), `assumed-downloads-cache.json`, `link-downloadable-cache.json` (per-URL "is this a direct download?" probe results), `llm-extraction-cache.json`, `picture-captions.json` (what the model saw in each picture). These store processed results so pipeline stages can re-run without recomputation. Note the `link-downloadable-cache.json` probes are live network HEAD/GET calls that bypass the raw-HTTP replay layer, so without this cache every topic re-probes the network even when `qb_use_cached=true`.

A third thing on disk, neither cache nor output: `<qb_data_path>/runs/` — `runs-index.json` plus one log file per run (see the manager core above). It follows the same save-as-you-go rule. A fourth, which is neither: `<qb_data_path>/scraper.lock`, which exists only while a job is running (see `data_lock.dart`).

**Everything that costs money or network time is saved as the run goes, not at the end.** A run killed with Ctrl-C, or one that dies part-way, must not throw away the work it already did — the next run should pick up where it left off. So: `mods-index.json` is written every 10 topics (it names the `detail.json` files, which are written per topic — an unsaved index orphans them and the next run re-scrapes them all), `assumed-downloads-cache.json` every 10 resolved topics, `link-downloadable-cache.json` every 10 probes, `llm-extraction-cache.json` every 5 topics or 5 seconds, `picture-captions.json` every 5 pictures or 5 seconds. Each also gets a final save at the end, on the failure path too. Keep it that way when adding a cache: the only end-of-run writes should be *derived outputs* (`mod-catalog.json`, `mod-catalog-details.json`, the old two, `merge-debug.json`), which can always be rebuilt from the caches. The ModRepo per-source caches (`<name>_cache.json`) are still all-or-nothing, and so is `discord-posts.json`, written beside `discord_cache.json`.

### The public website (`lib/site/`, `site/`)

Starmodder: a static, read-only website built on what the two pipelines already collect. It is not the local results viewer under `web/` — that one is a debugging tool with a manager behind it; this one has no server at all and offers no way to change anything.

**What it publishes** (`lib/site/public_data_builder.dart` → `outputs/site/`):

- `mods.json` — one record per mod: id, name, the tidied `displayName`, authors and their other known names (`otherAuthorNames`, keyed by the credited name — one list per person, never one list for the mod, or two people on the same mod read as two spellings of one), categories, game and mod version, one picture and the other one the picture setting can show, a one-line summary, save compatibility, the day its forum thread was last posted on, the switches the filters use, and what the download button needs — `bestDownload` (one already-resolved address, its kind, and whether it opens the host's own page), `downloadCount`, and the mod's `forumUrl` and `discordUrl` for the quarter of mods with nothing to download. It is the one file the browse page fetches whole, so it holds nothing else — no post HTML, no changelogs, no galleries, and no second address for any download. A test pins it under 2 MB (it is about 1.35 MB for 1,089 mods, and the test's worst case gives 1,200 mods both pictures, a thread date and a TriOS link, which is the longest kind of address the file can carry). The margin is now the thing to watch: a field added to this record is what runs the file out of room first.
- `mods/<id>.json` — one file per mod, holding its whole page: the list record plus description, gallery, downloads, changelog by version, license, source code, support links, links out, release history, add-ons.
- `mods/<id>/index.html` — a page of its own for each mod, and the mod's address (`lib/site/mod_page_html.dart`). The site used to live entirely behind `#/mods/<id>`, and a hash is never sent to a server, so every shared link showed the same title and no picture in Discord and a search engine saw one page standing for 900 mods. **The page is the site's own `index.html` with one region of its head swapped** for that mod's `<base>`, title, description and preview tags — the region between `<!--page-head-->` and `<!--/page-head-->`. So the header, the settings box, the footer and the scripts are written once, in `site/index.html`, and a mod's page cannot drift from the rest of the site; a test pins that the marks are still there and still sit above the first relative address on the page. It costs about 6.5 MB across 1,089 mods, against 1.3 MB for the redirecting stubs it replaced. `PublicDataBuilder` reads that file once per run from `sitePath`, which comes from `publish_site_path` through both services' environments — the same folder the publish copies, so the pages can never be built from a different copy of the site than the one that goes out; **a copy it cannot read or that has lost its marks is a log line, not a failure** — each mod then gets the old small redirecting page, which still previews and still reaches the mod, only without the mod keeping its own address. **No redirect rule, no Worker, no server that reads the address** — the host only has to serve `index.html` for a folder, which every static host does and which is why `bin/site_server.dart` sets `defaultDocument` on both its handlers. It does not even have to redirect `mods/<id>` to `mods/<id>/`: `address.js` reads both, telling a folder from a file by the dot, since a mod id is only ever lowercase letters, digits and dashes.
**The page also carries the mod's words in its body**, between `<!--page-body-->` and `<!--/page-body-->` inside `<main>`: the name as a heading, who made it, the game and mod version, the author's own summary, the download, thread and source links, what it needs (linked to those mods' pages), and **the start of the post** — whole paragraphs of the plain-text `description` up to 500 characters (`postOpening`, `postOpeningLength`), a too-long first paragraph cut at a space with "…". This is for search engines that read the file without running the script; Where scripts run they are never drawn: a line in `index.html`'s head marks `<html>` with `js` before anything is drawn, `.js .page-text` hides the words and a "Loading…" written after them shows instead, until `app.js` draws the page. The whole post was tried first and cut back: it added about 9 MB across the pages for words the forum thread already carries, while the name, summary and opening are what match searches. **No AI words and no pictures go in** — a reader who chose Never for AI summaries, or turned pictures off, must not get them even for that moment; the post goes in as plain text, so it can carry no picture. All the mod pages together are about 9.7 MB.
- `sitemap.xml` and `robots.txt` (`lib/site/sitemap.dart`) — the front page and every mod's page by whole address, each with the later of its last release and its last thread post as `lastmod`. A sitemap must give whole addresses, so `siteAddress` (`https://starmodder.wispborne.com/`) is the one place the site's own address is written down; everything else stays relative.
- `mods/<old id>.json` and `mods/<old id>/index.html` for each moved id (`PublicSiteData.movedIds`): the file is just `{"movedTo": "<id>"}`, which `views/mod.js` follows with `address().redirect()` so Back skips the old address, and the page carries the target's preview tags, a `canonical` link to it and a refresh to `../<id>/`, keeping `?data=…` and a tab after the address. Neither is in `mods.json` or the sitemap.
- `updates.json` — the mods that put out a new version, newest first.
- `updates.xml` — the same releases as an Atom feed, so a reader can subscribe rather than remember to visit. Every link in it is **relative** (`index.html#/mods/<id>`), which a feed reader resolves against wherever it fetched the file from — the site has no one address to hard-code, and nothing from the config file gets in. Entry names are `tag:` URIs for the same reason. The newest 200 only, or the file would grow for ever.

**Nothing internal ever reaches these files** — no config value, no token, no local path, no run id, no confidence score. A test pins that. The fields that are not the author's own words are the summary and the description, which carry `summaryIsGenerated` / `descriptionIsGenerated` so the site can label them, plus `aiSummary` and `aiDescription` — the AI summary and paragraph, published beside the author's own words rather than only in their place, because a reader can ask to see the AI words even where the author wrote some.

**What the pages actually show** — four rules that decide the content, all of them because the raw data is not fit to read as it stands:

- **Names** (`lib/site/display_name.dart`). A thread title is not a name: it carries the bracketed game version, the mod version, dates, "[WIP]" and often a leading dash to push it up the board's list. `displayName` is the title with all of that off, published only where it differs from the title, and the list is sorted by it. The title as written is still published, so a search for an old spelling still finds the mod. It builds on `ModIdStore.stripReleaseParts`, which is `cleanName` with the author's own capitals left alone — so a name and its id are worked out the same way and can never drift apart. **Where the LLM has a name for the mod that agrees with the title** (by `modNamesMatch`), that name is shown instead (`_shownNameFor` in `public_data_builder.dart`): the rules cannot take every title apart — "Sea of Stars 0.5.1 - Go Beyond the Persean Sector" has a bare version in the middle and a subtitle behind it, and came through whole. Agreeing is required, not just being the thread's one main mod, so "Red" never replaces "Red - the Oculian Armada". The shown name is worked out once per mod, when it is joined, so the card, the release feed and "Requires" links all say the same thing. The id is not touched by any of this.
- **Descriptions** (`lib/site/post_html.dart`). The description is the author's own forum post, rebuilt from a short list of tags (paragraphs, breaks, lists, headings, quotes, code, emphasis, links, pictures) and published as `descriptionHtml`; `description` holds the same words as plain text, with no pictures. Nothing that can run or style the page survives. **Every picture stays where the author put it**, badges and donation buttons included, because without them a post reads like a different post and a link whose only content was a badge (topic 35651's downloads) was thrown away as empty. Each picture is written out fresh — `http(s)` address, alt text, a whole-number width and height, `loading="lazy"`, `referrerpolicy="no-referrer"` and nothing else — the same way a link is. **The length cap (`maxDescriptionLength`, 150,000) sits above the longest post on the forum**, so in practice a post is published whole — at 12,000 it cut one post in five, back when the description sat above everything else on the page. A post that is still cut ends with a "…" paragraph, which the mod page turns into "Continued on the forum →" (`continuedOnTheForum` in `views/mod.js`). **Picture tags do not count toward the length cap** (`_Writer` in `post_html.dart`), or a short post full of screenshots would be cut short. A post of nothing but pictures still counts as no description. **The forum's own formatting is kept, in the site's own terms** — the forum writes it as `div`s and `span`s with classes and styles, which the old "unwrap what you don't know" rule threw away, and a spoiler left its title and a stray "[close]" in the text. Spoilers become `<details class="spoiler">` (3,601 of them). The forum leaves every `[spoiler]` tag in a post as plain text when the tags do not pair up (topic 35818), so `_spoilerTagsAsHtml` pairs them itself: a tag that is never closed, or a pair that would cut through other HTML tags, stays as text. Tables keep their cells inside `div.table-scroll` (empty cells kept, or columns shift), `align` / `text-align` become `div.align-center` / `div.align-right`, sizes become one of four `size-*` steps on the site's own scale (so a 36pt banner is title-sized, not three times bigger), `bbc_u` is `<u>`, `tt` is `<code>`, a numbered `ul` is `<ol>`, and the "Quote" and "Code" header lines go — a quote header naming someone stays as a `<cite>`. **A colour is kept as `span.author-colour style="--c:#rrggbb"`** — the one `style` a description can carry, written by `hexColourOf` in `forum_formatting.dart` from a named colour, `#rgb`, `#rrggbb` or `rgb()` and nothing else — and the stylesheet clamps its lightness into a band set per theme (`--author-l-min` / `--author-l-max`), so black text reads on dark and yellow reads on Light. **A YouTube iframe becomes `a.video-link` to the video holding its `i.ytimg.com` thumbnail** — a plain link anywhere a script does not run — and `youTubePreview` in `views/mod.js` swaps in the `youtube-nocookie.com` player on a plain click; that player needs a referrer, so it is given `strict-origin-when-cross-origin`. With pictures off it reads "Video on YouTube" and fetches nothing. Vimeo is a plain link; other frames go. Every class that can come out is one of the site's own, and a test pins the list. Links get `rel="nofollow noopener"`, bare addresses become links, empty links go, and runs of line breaks are collapsed. **Only where there is no forum post** does it fall back to the merged text, then to the AI paragraph. Before this, the description was whichever text the merge liked best — for the bigger mods the Discord announcement, so Nexerelin's page read "4X in Starsector. Download: …". **A post on a thread holding several mods is nobody's description as a whole** — but where the author wrote a paragraph about one of them, that paragraph is that mod's description, cut out of the post by `lib/site/description_slice.dart`. See "A thread can be several mods" below.
- **The Discord post is shown beside the forum post** (`discordPostHtml`, `lib/site/discord_markdown.dart`, `discordPost` in `views/mod.js`). The merge keeps one description per mod, so the Discord post would otherwise be lost wherever the forum post won. The Discord scrape saves each thread's opening run to `<qb_data_path>/discord-posts.json`, keyed by thread id, and both site builds read the first message from it by the thread id in the mod's Discord link (`DiscordPostsFile.firstTextFor`). A file still in the old format, written by the site before the scrape wrote it, is read too. The markdown is turned into HTML when the site is built and then passed through `cleanPostHtml`, so it can carry nothing a forum post could not. Mentions are dropped, custom emoji keep their `:name:`, timestamps become their day, and inline spoilers become plain words. Where the merged description is only the Discord post again, it is not published as the description, so the page never shows it twice. `descriptionIsForumPost` says whether the description is the forum post; the page heads it "Forum post" when it is and "About this mod" when it is not. Each post's heading sits in a short strip (`--pad-head`) with a line under it that runs to both edges of the panel (`.post-panel`), small enough that the author's words lead. A press anywhere on that strip folds or opens the post, the same as "Collapse" — except on one of its buttons, and only where the post is long enough to fold, which is also when the strip shows a pointer and the whole strip lights up on hover (`--primary-faint`), except while the pointer is on "Hide pictures". The post's padding is on `.post-body`, not on the clip, so a folded post still shows its whole preview. The Discord post sits a little further below the forum post than the parts of one group do (`#section-discord-post`). Both posts fold to a short preview with "Collapse", which sits beside "Hide pictures" as a quiet icon-and-words button (`.post-switch`). The side column's "On this page" card (`jumpLinks`) scrolls back up to the header (the mod's picture and name) and to each post, opening the Description tab first when another tab is showing. Its entries are buttons, not `#` links, because the hash picks the page. It is drawn like a table of contents on other sites, so it does not read as a second list of links out: dim words with no icons, down a thin line, and the section being read lit in `--on` on the line and in the words (`litWhileRead` in `views/mod.js`, a scroll watch that stops itself once the list has left the page).
- **Galleries** (`lib/site/gallery_filter.dart`). Every picture in a post used to be shown as a screenshot, so a gallery was as likely to be a Ko-fi button, a build badge and the author's avatar. Every picture is still published, but one that fails these rules is marked `small: true` (written only when true), and the page hides those behind a "Show N small pictures" button. Three rules, in order of how sure they are: the host (Ko-fi, Patreon, shields.io…, and license badges from creativecommons.org, which are kept off the gallery only so the LLM's input does not change), words in the address (donate, button, badge, avatar, icon, logo, 88x31), and the width the post gave it, where under 200 pixels is not a screenshot. **A picture the post says nothing about is not marked** — a missing size is not evidence. Most posts give no size, so the page also measures each picture once it loads (`isScreenshotSized` in `views/mod.js`) and hides one narrower than 200 pixels, shorter than 100, or more than 4.5 times wider than tall (title banners, dividers); the hidden ones join the small ones behind the button, and the Gallery tab's count follows as pictures load. The forum's own furniture (smileys, theme graphics, avatars on the forum's host; `isForumFurniture`) is the one thing never published. Each picture carries `source` (`forum`, `discord` or `nexus`). The merge's pictures come only from Discord and Nexus, so a merged picture on a nexusmods.com host is `nexus` and any other is `discord` (`_announcementSource`). The picture viewer shows "Image from forum" (or Discord, or Nexus Mods) with that site's icon, linked to the mod's thread or page (`PICTURE_SOURCES` and `withSource` in `site/lib.js`). Pictures in the forum post on the Description tab get the same line. This is the gallery only: the card's one picture is picked separately, see below.
- **The card's picture, and the reader's choice of two** (`_picturesFor` in `public_data_builder.dart`). A mod can have two pictures: the one the LLM found in the author's forum post, and the first picture the merge kept, which only Discord and Nexus ever give — the forum scraper collects none. The post's picture leads, because it is the one the author put at the top of their own thread, where a Discord picture is whatever was attached to an announcement. The order is: the LLM's pick when it is one of the forum post's own pictures; then the post's first picture that passes the gallery's screenshot rules (`looksLikeAScreenshot`), but only on a thread about one mod, since on a shared thread the first picture may be another mod's; then a picture the LLM picked off the Discord thread; then the announcement picture; then the author's forum avatar (a relative avatar path is resolved against `https://fractalsoftworks.com/forum/`). The LLM leaves the picture empty on about a third of the forum threads that have pictures, and before the post's first picture was a fallback those mods showed a Discord picture, whose signed address stops working about a day after the Discord scrape — Industrial Evolution's card went blank that way. TriOS then falls back to the installed mod's icon, which a website cannot read. Anything that is not a plain http(s) address is dropped and the next one tried. The thread thumbnail is not a source. **The card picture's main goal is to be the same, best picture on every build**, so on a thread about one mod the saved picture ratings come first (`_bestRatedPicture`): the earliest of the first ten pictures rated a good card fit, else the earliest rated okay. A rating is saved per picture and never asked again, where the LLM's pick changes whenever a post is read again. A picture the model's server could not fetch, rated poor, or seen as missing, a button, a badge or a divider is never a card picture in any of the fallbacks (`_barredFromCards`). On 52 real threads this matched today's picture on 42, replaced a Photobucket placeholder and a dead gfycat link, and left threads whose every picture is dead with none rather than a broken one. **This is where the site parts company with TriOS's catalog**, which takes the merged picture first — so `imageUrl` is what the site shows and `announcementImageUrl` is the announcement picture, published beside it and left out when it is already what `imageUrl` holds (the same address twice would only make `mods.json` bigger). Publishing both is what lets the choice cost no extra fetch.
- **Which download the button offers** (`lib/site/download_order.dart`). A mod can offer a dozen links and every list used to handle that differently — Favorites drew a button per download, so one row held four buttons all saying much the same thing, and the mod page picked by its own rule. One rule now sorts them, in the builder, and every list takes the first: a TriOS link always leads (it installs what the mod needs as well, and opening it *is* the extra step, so it is never counted as needing one), then anything straight to a file, then anything that opens the host's own page; a plain download before a mirror inside each of those; and two the rule cannot tell apart keep the post's order. It is TriOS's catalog rule (`lib/catalog/catalog_download_resolver.dart` over there) with two deliberate differences: TriOS bars a needs-another-step link from leading at all, where the site pushes it down but still offers it, since a MediaFire page beats no download at all; and TriOS breaks ties on the LLM's confidence score, which the site must not publish, so the sorting happens before publishing instead. The same sorting is applied to each add-on's downloads.
- **Where a Discord-only mod's download comes from** (`lib/site/discord_download.dart`). Every download above is read off a forum thread — the LLM's per-thread list, or the resolver's candidates, both keyed by forum topic id — so a mod announced only on Discord used to reach the site with no download button and fall back to "On Discord", 224 of 1,112 published mods. The Discord reader had its link all along: `ModUrlType.DirectDownload` / `DownloadPage` on the merged mod, which TriOS already reads as `catalogDirect`. It is now the **last** fallback, used only when no thread download exists, so a mod with both is unchanged. Two rules keep it honest, and each was a real case. **Not every one of those URLs is a download**: `getUrlsFromMessage` in `discord_reader.dart` ends with `?? forumUrl`, so 138 mods store their own forum thread as the download page, and a "Download page" button that opens the forum is worse than the "On the forum" button it replaces — those go, along with Discord message links, subreddit links and any address that is already one of the mod's own buttons. **`DirectDownload` does not mean the file arrives**: it means the scraper's probe thought so, and Google Drive `/file/d/…/view` links and every mega.nz link are filed under it while opening the host's own page. So the host decides `needsAnotherStep`, not which field the URL came from, and `directUrl` is set only where a file really arrives — the browse page's "Has a download" switch tests that field and promises "goes straight to a file". On live data this gives 53 mods a "Download" button and 45 a "Download page" one, and drops 14. A link that is plainly a download but plainly dead is published as a dead link, like every other dead download on the site.
- **Summaries** (`lib/site/summary_text.dart`). A copied summary is read a line at a time first: a Discord heading line and a line that is only a short label and a link ("Forum post: https://…") are dropped, and Discord's line marks come off. Hullmods - Renewed's card used to read "## Hullmods - Renewed Forum post: https://…". Where the copied summary is then unusable, the first usable paragraph among the first four of the mod's Discord post stands in (`summaryOfDiscordPost`), because the Discord reader keeps only a post's first two lines and the author's real opening is often just below them. Without that fallback such a mod has only an AI summary, and a reader who pressed "Hide AI summaries" saw nothing under its name. A copied summary that is only a link, only the mod's name in emphasis marks, or only a list of requirements is dropped, and the AI summary takes its place labelled as AI.
- **How much AI writing a reader wants** (`aiSummaryMode` in `site/lib.js`). Three choices, the same three TriOS offers: Always, Only as a fallback (the default), Never. The banner and the Settings dialog both draw them from `AI_SUMMARY_CHOICES` in `site/lib.js`, so the two always use the same words. Always puts the AI summary ahead of the author's own on every card and row, and adds the AI paragraph above the post on a mod's page rather than instead of it — a whole forum post says more than one paragraph. Only as a fallback shows the author's own words and nothing from the AI, not even on hover. **Where an AI summary is shown, its hover text is the AI's longer paragraph** (`fullAiSummaryOnHover` in `site/lib.js`). That paragraph is `aiDescription`, which only the mod's own file carries — putting it in `mods.json` would add about 230 KB and break the file's size limit — so it is fetched the first time the pointer rests on the summary, and the one sentence stays on hover until it arrives. Never means never — `aiSummaryOf` returning nothing is what enforces that. The choice is kept in `localStorage` (`starmodderAiSummaries`). It used to be a cookie of the same name, which is copied across and deleted the first time it is read; the old on/off values still read, with `off` meaning Never. Home and Browse show a banner with the same three choices (`aiSummaryBanner`), the one in use marked. Picking one redraws the page and leaves the banner up; only its Hide button takes it away, remembered as `starmodderAiBanner`.
- **Categories** (`lib/site/public_categories.dart`). The forum's index and Discord's tags use 26 names between them, several meaning the same thing — "Utility mods" beside "Standalone Utilities", "Other/Misc." beside "Miscellaneous Mods". The site publishes **thirteen** instead, and the raw names are kept on the mod's own page as `rawCategories`. Two rules: a raw name the table has never heard of gets **no** category rather than a guessed one, so a new tag is something to notice; and "Discord Only" is deliberately absent, because it says where a mod was found, not what it is — that is published as `sources` (`forum` / `discord` / `nexus`) instead.
- **What a mod needs** (`LlmExtras.needs` → `PublicMod.needs`). Nearly every Starsector mod needs LazyLib, MagicLib, GraphicsLib or Nexerelin, and finding that out from a crash on startup is the oldest annoyance in Starsector modding. The LLM reads the requirement line off the post; each name is then **checked against the post** (`_groundNeeds`) — a model asked what a mod needs will say LazyLib whether the post did or not — and the builder points each one at its own page where the name matches a mod we publish. **The values only arrive on the next LLM extraction pass**: adding the field bumped `ExtractionPrompt.promptVersion`, which is part of the cache key, so every topic is read again. (Reading the author's later posts, adding `descriptionAnchors`, splitting the save question, writing versions without a "v", keeping tools such as mod managers with `isMod: true` and `isTool`, asking for each mod's `nicknames`, asking only for the author's own support links, each with a label, and asking what the author says about AI use, and pointing at a long AI-use statement instead of copying it, each bumped it again; it is 26 now)
- **What the author says about AI use** (`usesAi` and `aiUses` on `PublicMod`, the whole `aiUse` on `PublicModDetail`, from the LLM's `aiUse`). Four states: AI used, no AI used, read and nothing stated, and not read yet. `mods.json` carries `usesAi` only when the author said something, and `aiUses` only when it is true. Each use has `area`, `how` and `optional`. Uses are sorted by area, with duplicates removed. The amount (`extent`) is omitted to keep the file small. The mod's own file carries the quote and the tools, an empty `aiUse` for a mod read with nothing stated, and no `aiUse` for one not read yet. The mod page shows an "AI use" row under Details: "Portraits (partly AI with human edits, optional) · Code (AI-assisted)", "None", a dim "Unknown", or a dim "Not checked yet". The amount (`extent`) comes first when the author specifies it. The author's words appear on hover through `quickTip`, which also accepts a built element. The tooltip lists each use in full, then the tools as badges, then the quote with a line along its left edge (`aiUseTip` in `views/mod.js`). The row has no colour or warning mark: the site reports the author's statement without taking a side. Browse has an "AI use" filter. `site/ai_filter.js` handles matching and address keys. It has no DOM code, so `test/site/ai_filter_test.mjs` can load it. `aiFilterBody` in `views/browse.js` draws the controls. The two mode buttons are stacked: "Don't show AI-gen…" hides mods with stated AI use in the checked parts, and "Only show AI-gen…" shows only those mods. The filter starts on "Don't show AI-gen…" with nothing checked. This hides nothing. There is no off button. Switching to "Only show AI-gen…" with nothing checked checks every part. Otherwise, no mods would be shown. Parts are grouped as Art, Sound, Text, Code and Other. There is no "Parts" heading. The All and None links sit in the side panel's heading beside the fold arrow. Pressing them does not fold the panel. They are hidden while it is shut. In the top layout's box they sit in a small "AI use" heading row. Each group's checkbox selects or clears the whole group. A dash means some parts are checked. Under the heading "If AI did…", the reader picks how much AI work counts: "all of the work" (`generated`), "some, but edited by a human" (also `edited`) or "anything at all" (also `assisted`). Stated AI use with no `how` always counts. Readers can ignore optional parts (`optional`). Counts use the mods shown by the other filters. **"Don't show AI-gen…" never hides a mod whose author says nothing about AI.** Search `is:noai` for mods whose authors say they used no AI. The address carries `ai=only`, `aiparts=` (the checked parts), `ailevel=made|edited`, and `aioptional=keep`. Each is left out at its default. The starting filter adds nothing to the address. An old `hideai=portraits,music` link still opens with those parts hidden. The result line shows how many mods the filter hides, with a "Clear AI filter" link. This stays visible when the panel is closed. Each click redraws the filter and restores keyboard focus to the same control (`data-focus`). The side panel starts open. On a phone, it starts shut. The button above the results shows the current mode ("AI use: hiding"). It opens the same controls over the results. The menu shifts to fit on screen. Clicking outside closes it. The search has `has:ai` and `is:noai` (see below).
- **Saves are three questions, not one** (`saveCompatibility`, `updateNotes`, `removalCompatibility` on `LlmExtras`). Adding a mod to a running game, updating a mod a game already uses, and taking a mod out of a game are different questions, and a mod can be safe to add and still break saves on every update. They used to share one field, so "This update is not save compatible" came out as a "Needs a new game" badge. The prompt asks for each separately, copied word for word and checked against the post, and splits a sentence that answers two of them; the model once copied "safe to add, and safe to remove" into both fields, which is why topic 27785 is a live test. `saveCompatibility` keeps its old name because TriOS reads it; it now means adding only. Adding and removing each have a short answer beside them — `canAdd`, `canRemove`, each `yes`, `no` or `depends` (`SaveAnswer`). "Depends" means the words carry a condition or an exception, so a reader has to read them. A short answer is kept only when its words survived the check against the post. Only adding drives the badge and the browse filter (`_canAddToSave`): `canAdd` decides it where there is one, and "depends" gives no badge; answers read before the short answers existed fall back to `readSaveCompatibility`, which reads the words and gives "nobody said" for any words about updates or versions.
- **Updating is answered per release** (`LlmUpdateNote`: `version`, `quote`, `answer`; `lib/site/update_note.dart`). It is the one save question whose answer belongs to a release: topic 27785's second post says "Minor patch v1.0.1 is out… It is save-compatible", and as a single field that read as a note about v3.0.2. So each note carries the release it was written for, or no version when it is a rule about every update or a statement about the mod as it is now ("Not save compatible with versions prior to 2.0.0"). A version the post never writes takes its whole note with it — keeping the words without it would turn a note about an old release into one about the current release. `updateNoteFor` picks the note for a version: one written for that version wins, and a note with no version only speaks for the version the mod is on now. The mod's page shows the current version's note as "Updating"; each release in "Recent updates" carries its own as `updateCompatibilityText` / `canUpdate` and draws a badge ("Save compatible update", "Breaks existing saves", "Existing saves: it depends") with the author's words on hover; the release feed adds a "Saves:" line. A note about an older release stays in the bundle and goes on no page. The mod's page shows each answer that exists as its own row — "Adding to a save", "Updating", "Removing from a save" — and where the model copied the same words into two, they are shown once under both names.

**A thread can be several mods.** Some threads hold several mods at once — "Hartley's Miscellaneous Mods" (topic 34161) is four, "Computica's Faction Forks" (35651) is seven. The site no longer works this out: the catalog has already turned such a thread into one listing per grounded `main` mod (see **The catalog**), and each comes to the site as a mod with its own id. A mod the LLM found as one of several on a thread carries `partOfThreadTitle`, the thread it came from, because four mods with one forum link between them would otherwise read as a bug. A thread whose old address belongs to what is now a Collection keeps that address as a page listing its mods (`mods/<id>.json` holds a `collection` instead of a `listing`; `buildCollectionPageHtml` makes its page the same way a mod's is made, and `collectionPage` in `views/mod.js` draws it).

**Each mod on such a thread can still have the author's own description** (`descriptionAnchors` on `LlmMod`, `lib/site/description_slice.dart`). The shared post as a whole is nobody's description, but authors usually write a paragraph per mod under its name, and publishing an AI paraphrase instead of words sitting right there is backwards. So the model is asked to **point, not write**: it copies the first few words and the last few words of the stretch of text about one mod, the extractor checks both ends are in one of the posts (`_groundAnchors`), and the builder cuts the author's real HTML out between them and runs it through `cleanPostHtml`. Three things hold it: matching is letters and numbers only, so punctuation and HTML entities cannot break it; the cut is made at line ends, never inside a sentence, so whole paragraphs come back; and anything that cannot be found is thrown away, falling back to the merged text and then the AI paragraph, labelled as AI. A sliced description is **not** marked as generated, because the words are the author's. A thread about one mod never goes near this — it publishes its first post.

**Two mods can share a name, and each page names the other** (`_fillSameNameMods` in `lib/site/public_data_builder.dart`, `sameNameKey` in `mod_name_match.dart`, `sameNameMods` in `site/views/mod.js`). Three different things end up looking alike and all three are kept: a mod's own older thread, a fork that kept the name of the mod it forked, and two people who picked the same name. The catalog keeps every forum topic a mod of its own for exactly this reason. Deduplicating would decide for the reader which build they want, so instead each mod's page carries the others in `PublicModDetail.sameNameMods`, newest thread first by `threadLastPostOn` (published as a day, because the forum writes its times with no time zone). The grouping is one key (`sameNameKey`, which agrees with `modNamesMatch`; a test pins the two together). The panel sits above the downloads, because the reader most likely to be on the wrong page of two followed a link from outside. Nothing is added to `mods.json` for it beyond the thread date.

A **shared thread's releases go to nobody** (`_releasesByMod`): the detector believes one version for a whole thread and cannot say which of four mods moved.

**Permanent ids** (`lib/site/mod_id_store.dart`, `<qb_data_path>/mod-ids.json`). A mod's web address is built from its id, and a thread title carries the version and changes on every release — so an id is never worked out fresh. The catalog merge hands ids out, looking each mod up through its source posts first and its name only when none of its posts has one (see **The catalog**); the site reads the ids from `mod-catalog.json` and hands none out. A brand-new mod's id is its name with the bracketed game version, the mod version and any date stripped off, numbered when taken. **If that file exists but cannot be read the job fails and writes nothing**; handing out fresh ids would move every page. Each entry also records a `mark` (the forum topic id, or failing that the author), the posts it belongs to, and the day a mod was first seen, which is only a fallback for `addedOn`: that is the day the forum thread was posted or the day of the Discord message the mod was read from, whichever is earlier (`_addedOn` in `public_data_builder.dart`). The id file was written in one go, so every mod that already existed shares the day it was made, which says nothing (`ModIdStore.seedDay`). The forum writes its dates as "May 04, 2014, 01:33:25 AM", and that string is read back in one place: `parseForumDate` in `lib/bot/scraper/qb/models/forum_date.dart` (also used by the viewer). A relative date like "Today at 03:12:22 PM" names no day and reads as null.

**Working out which mods released** (`lib/site/release_detector.dart`, `release_state_store.dart`, `version_text.dart`). The LLM's version reading is noisy — over one month of real data it contradicted itself 279 times — so four rules stand between it and the feed, and they are the whole point of this step:

- A reading must hold for **two scrapes running** before it is believed.
- A believed version **never moves backwards**. This is the rule that stops the site forgetting a release and announcing it again when a reading recovers.
- A version matching the thread's game version, or the bracketed one at the front of the title, is **thrown out** — the extractor confuses the two.
- Where the title names a version, a new version that disagrees with it is **dropped**. The title can veto but never propose, because only some threads carry one.

The first version believed for a mod is never a release, or a backfill would announce every mod at once. State lives in `<qb_data_path>/mod-releases.json`: what each thread is believed to be on, how long the current reading has held, every release so far, and which saved bundles have been walked. A run advances it by one bundle; `bin/backfill_releases.dart` walks every saved bundle once to fill in the history, and is safe to re-run.

**Where it is called** (`lib/site/public_site_step.dart`): after the QB pipeline publishes a bundle (`afterBundle` — the only place a release is ever recorded), and after a merge (`afterMerge` — the release state is read, not changed). Each reads the other half back from `outputs/`.

**The site itself** (`site/`): plain ES modules, no build step, the same look as the viewer. `app.js` is a router over `views/home.js`, `browse.js`, `mod.js`, `author.js` and `about.js`; `lib.js` holds the DOM and fetch helpers, and `address.js` owns everything to do with the address bar. Things about it worth knowing:

- **The address is the route, and it is the only place the route is kept** (`site/address.js`). A mod's page is a real file at `mods/<id>/`, so that path is its route; every other page is a hash on the front document. `siteAddress().parts()` works one out of the other — path first, hash second — and **nothing is hidden in `history.state`**, so the address bar can never disagree with the page. Four rules hold it together, and each of them was a bug first:
  - **Both history events are listened for.** A hash link fires `hashchange` (and, in some browsers, `popstate` too); a jump between a mod's path and a hash address changes more than the fragment, so it fires **only** `popstate`. Listening for `hashchange` alone leaves the Back button dead on every mod page. The address last drawn is remembered so the two events never draw the same page twice.
  - **Clicks on our own links are turned into history entries** (`onClick`), because the two page shapes have different paths and an ordinary click between them would reload the whole site. A link is ours only when it names the front document or a `mods/<id>` **folder** — `mods/<id>.json` is one mod's data and sits right beside its page, so "a path with two parts starting `mods`" is not enough. The two are told apart by the dot, not by the trailing slash, so a shared address with the slash rubbed off still opens the mod and the site needs nothing of the host beyond serving `index.html` for a folder. Anything else, and any modified click, new tab or download, is left to the browser.
  - **The `<base>` is pinned to an absolute address as the site starts.** The address bar moves to `mods/<id>/` without a new document being loaded, so a base still written as `./` would follow it and every stylesheet, script and data file would be looked for inside the mod's folder. The reader's `?data=…` is pinned onto it too, which is what keeps `?data=sample` alive across every link on the site.
  - **A page's scroll position is filed under `scrollKey()`**, not under `location.hash`, because a mod's page has no hash. Its route is written as one (`#/mods/<id>`) so the key is the same string every time that page is drawn.
- **A mod's page is two columns** (`views/mod.js`, `.mod-layout` in `style.css`). The header is a small picture beside the name, the one-line summary (the same `summaryToShow` the cards use), then the byline and chips. The main column is tabs — Description, Gallery, Recent Updates (the author's changelog above the release history), Add-ons — and a tab with nothing in it is not drawn. The open tab is kept in the address as a plain hash after the mod's path (`mods/<id>/#gallery`; the first tab writes none), with `replace` so Back leaves the mod rather than stepping through tabs. That is safe only because a mod's route is read from its path alone, which `address_test.mjs` pins. The tabs are real links to those addresses, and a plain click is caught on the tab, or the site's link handling would read `#gallery` on the site's root as a page called "gallery". The Description tab opens with the AI summary, which carries a "Hide AI summaries" switch (`aiOnModPages` in `lib.js`, `starmodderAiOnModPages` in `localStorage`): it hides AI words on every mod page — that panel and an AI line under the name — and leaves a single "Show AI summary" link in its place. It is separate from the site-wide Summaries setting, and Never there still wins The page opens with a small "‹ Browse mods" link instead of the breadcrumb trail, to give the side more room. The game version is not in the header; it is a coloured badge in Compatibility. The side column starts level with the header (the layout's second row is `1fr`, so the tall column does not stretch the header's row) and is three panels: the buttons that get the mod on their own, then one panel holding the other cards about the mod, each with its own heading and a thin line running from the end of the heading to the panel's edge (`.side-merged`), then "On this page", since it is about the page rather than the mod. On a narrow screen the middle panel's cards are separate again. The cards: the buttons that get the mod (the first download as one big filled button, then one row of smaller ones — the first plain download where the big one is a TriOS link, the thread, the favorite — with "Links last checked" on the download buttons' hover), Links (source code as a badge — green and naming the host, or a grey "Not linked" that tells authors how to get one, because the site means to reward authors who share their code — with the license beside it on the same row as plain dim words giving its short name from `shortLicenseName` (the author's own wording on hover), then support links, each with its platform's logo where it has one — `site/support_icons.js`, single-colour marks copied unchanged from Simple Icons, CC0 — then the mod's forum thread, Discord post, Nexus page and the author's full changelog (also at the foot of the Recent Updates tab); there is no separate "Found on" line, because these links already say where the mod was found), Compatibility (game version, requirements, the save questions), Details (the categories as the sources named them sit behind an "Original categories" button on the Category line, since few readers want them), "Other downloads", then "On this page", and last a panel with short lists of "More by" and "Similar mods" (`relatedLists`): five rows each — a small picture, the name with its game version badge at the right, and the summary on one dim line under it; "Similar mods" also puts "by <author>" after the name (`theAuthorsOtherMods`, `modsLikeThis`). They replaced the rows of cards that used to sit at the foot of the page, and the full text of a row is on hover (`quickTip`). "Other downloads" lists only the downloads the buttons at the top do not already offer — `topDownloads` decides both, so they cannot disagree — and is not drawn when the buttons cover every download, which is most mods. Card rows are separated by spacing, not divider lines. The side is one sticky column (`.mod-aside`) that stays in view under the top bar and scrolls on its own when taller than the window. On a narrow screen that wrapper is `display: contents`, so the button card comes before the mod and the other cards after.
- **One search box, in the bar at the top, on every page** (`app.js`). It suggests up to five mods as you type — the whole list is already loaded — and "/" puts the cursor in it. There is **no index of authors**, and no nav entry for one: a list of everyone ordered by mod count is a scoreboard, and it rewards publishing more mods rather than better ones. `#/authors` with no name sends the reader to Browse. One person's page (`#/authors/<name>`) stays, reached from a mod that credits them or from the search box, and the box lists matching people **by name**, never by how many mods they have. The browse page has no author dropdown either, because a list of 562 names cannot be used.
- **How the search matches** (`site/search.js`, one module for both boxes). Browse and the box at the top both call it — `compileSearch` / `searchMods` / `suggestMods` / `peopleMatching` — so they can never disagree about what matches or what comes first. Browse reads the text once per change and keeps each mod's score (`searchScore` in `views/browse.js`), because one redraw filters, counts and sorts the same list several times. The rules, each of which was a miss first:
  - **One clean-up on both sides** (`normalize`): capitals, accents and apostrophes go, every other mark becomes a space, and a dot stays only between two digits so "0.98a" survives. Apostrophes come out *before* the Unicode decomposition, which would turn "´" into a space and a mark, and symbols go before it too, or "™" becomes "TM". "Seeker - Unidentified Contact" could not be found by typing its own name without the dash, and 274 of 1,089 names have punctuation in them.
  - **Words in any order**, every one of which must match **one** fact about the mod (the name, one person, one category…). Each fact is checked on its own, so the end of a category never runs into the start of an author's name. Double quotes keep a phrase together; commas mean "any of these"; a plus is a space, kept for old links but not offered.
  - **A minus word narrows its own group; a group made only of minus words takes mods out of the whole list**, which is what keeps `faction, -portrait` working the way it always did. Nothing loose is ever tried for a minus word — a guess must never take a mod off the list.
  - **Close spellings are kept narrow** (`closeSpelling`): words of five letters or more, no digits, the first letter right, only against the words of names and people, and only when the word did not already hit the name or a person. One mistake up to seven letters, two from eight. A close match scores below every real name match and above a word in a summary — that last part is what puts Nexerelin above the mod whose summary spells it "Nexerellin". The first-letter rule is what stops `faction` finding Fleet Action History through "action".
  - **Shorthand** is mostly in the name already: its start (`nex`), its initials (`kol`, `uaf`; an exact match on them scores like a name starting with the search), capitals inside one word (`gl` for GraphicsLib), and the starts of neighbouring words run together (`indevo`, `builtFromWordStarts`). That last one has two limits, both measured on the real list: three letters or more, and either every piece is one letter or every piece but the last is two or more — without them `faction` was "f" + "action". Beyond that, the author's own nicknames arrive on the record as `nicknames` (see the LLM section), and **`site/nicknames.js` is only for shorthand nothing else finds**, keyed by permanent id (`ssp`, `brdy`). Keep it short.
  - **`has:` and `is:` ask the switches' yes-or-no questions** (`FLAGS` in `search.js`): `source`, `download`, `addable`, `wip`, `tool`, `ai` (the author says AI was used) and `noai` (the author says none was), and a minus leaves those mods out. A mod whose author says nothing about AI answers no to both, so `-has:ai` keeps it. Both words work with every question. A question scores nothing, so it lets a mod in or keeps it out without changing the order. `from:` is where a mod was found; `source:` is its old name and still works.
  - **Ranking** adds the words' scores and a bonus for naming the mod: most when the words are a whole name or nickname, less when a name starts with them, least when they sit inside one. Ties go by name, then id. The tests check orderings, never numbers, so the numbers can be tuned.
  - **The tests are `test/site/search_test.mjs`** (about 400 cases, run from `dart test` by `search_test.dart`), against `search_fixture.json`: 128 real records copied out of a published `mods.json`, because every bug here came from a real name. `search.js` imports only `mod_names.js` and `nicknames.js`, which need no browser — that is what lets Node load it; `lib.js` exports the name helpers again for the rest of the site. When a test fails, decide whether the test or the code is wrong; never loosen a check to make it pass.
- **"Recently added" on Home shows whole rows, one by default.** How many cards make a row is read off the grid itself and re-read when the page changes width, so it is never a row and a half. A small "1 · 2 · 3 rows" picker beside the heading changes it and the choice is kept in `localStorage` (`starmodderRecentRows`). Enough mods are loaded to fill three rows at the widest the page gets; the rest are `hidden`.
- **"Recent updates" has one button that opens every changelog** (`expandAllChangelogs` in `views/home.js`), beside the heading in the same `.section-head` row the rows picker uses. The label says what a press would do — "Show all changelogs" until they are all open, then "Hide all changelogs" — and it is read off the page each time rather than remembered, because rows are also opened one at a time. A fold's `toggle` event does not travel up the page, so it is caught on the way down (capture); without that, opening the last shut row by hand would leave the button still offering to show them all. It is left out entirely when no release on the page has notes.
- **"Recent updates" says where its list comes from** (`releasesNote` in `views/home.js`, `noteWithMore` / `openInfoDialog` in `site/lib.js`). A dated list reads as a list of what came out that day, and it is not: it is what a program noticed, having read a version number out of a forum post, which it sometimes reads wrong. So an amber-edged note sits above the list saying that in two sentences, and a "More about this" press opens a box with the five things worth knowing — that a mod is here because its version moved, that a reading must hold for two runs, that the date is the day we noticed rather than the day of release, that a mod which never writes its version never appears, and that the changelog is the author's own words. The short version is on the page because a reader who presses nothing should still know the list can be wrong; the long version is behind a press because five paragraphs above every visit to the front page is somebody else's page. It is left out when there are no releases at all — the empty notice already explains itself. The box is a plain `<dialog>` built when the button is pressed and taken out of the page when it shuts; every way out (the ×, the dimmed page, Escape, the back button) goes through one `shut()`, because the dialog's own `close` event is not sent by every browser. The About page says the same thing in its own words under "How releases are worked out" — keep the two in step.
- **Every version comparison on the site is TriOS's** (`site/version.js` for the pages, `lib/site/version_compare.dart` for the builder, both copies of `Version.compareVersions` in TriOS's `lib/models/version.dart`). Keep the three in step: a fix in TriOS belongs in both copies, and each copy is held to TriOS's own cases (`version_test.mjs`, `version_compare_test.dart`, both copied from TriOS's `version_sorting_test.dart`). `VersionText.compare` uses `compareVersionParts`, which is TriOS's comparison without its final tiebreak, so "1.0" and "1" count as the same version when the release detector asks whether two match. **Game versions need one step first** (`compareGameVersions`): Starsector numbers its releases like decimals, so 0.65 came out between 0.6 and 0.7, and TriOS's rules read it as 65. The version is rewritten with the part after the first dot padded to three digits and a missing third part as 0 (0.65.2a becomes 0.650.2a, 0.95a becomes 0.950.0a), and then compared by TriOS's rules. `repairGameVersion` also puts back a lost "0." (".98a", "97a-RC11"), so those join their real release in the game version filter. It also fixes typos that match a known release (`fixMistypedRelease` and the `RELEASES` list in `site/version.js`). These can be an extra dot ("0.9.8a" is 0.98a), a missing dot ("0.81a" is 0.8.1a), or a letter between numbers ("0.95a.1a" is 0.95.1a). A fix must match exactly one known release. Other versions stay as written unless they match a typo. A game release newer than the list, such as 0.99a, is left alone; the list needs no update for new game versions. These fixes only affect grouping. Cards and mod pages still show the version as the author wrote it. Each group uses its most common spelling. Ties go to a spelling with a final letter ("0.54.1a", not "0.54.1"). The builder skips game versions with no digits ("-"). It uses the thread's game version if it has one (`_namesAVersion` in `public_data_builder.dart`).
- **Browse has two layouts** (`savedLayout` / `layoutToggle` in `views/browse.js`, `starmodderBrowseLayout` in `localStorage`): the filters along the top (the default), or in a sticky column at the left the way Modrinth lays out its search. The "Top / Side" buttons sit beside Cards / Rows, and swapping draws the whole page again from the address, which already holds every filter. At the side the switches are tick boxes, and the categories and game versions are lists with counts in folding panels (`filterPanel`); only the search box, the sort and the view buttons stay above the results. Game version starts shut. On a phone, only "Show" starts open. Each panel keeps the state the reader chose after a reload. These choices are saved in `starmodderFilterPanels` in `localStorage`, keyed by heading.
- **Browse opens on what a reader can use.** Sorted by current game version first, then most recent release, then name. **The game version filter starts on the current release** (`gameFromAddress` in `views/browse.js`) and is the only thing that decides which releases are listed; there is no separate "current version only" switch, which used to sit ticked beside a filter that had overruled it. Its other choices are every release, "Any game version" (`game=any`) and "No game version" (`game=none`, the mods that never say). The address only names a game version when it is not the current one, so a link with none opens on whatever is current that day, and an old link carrying `older=1` opens on Any. While the list is on the current release, the line above the results offers "Include N for other game versions", which switches to Any. Versions that differ only in spelling ("0.98", "0.98a", "0.98a-RC8") are one choice, and which release is "current" is worked out from the data — the highest version at least five mods are built for, so one misread "9.99" cannot push every real mod into "older".
- **Each switch on Browse has three states**: off, on, and "not", which keeps the mods that answer no. For "Safe to add mid-game" that means the author said no (`keepWhenNot`); a mod that never says is in neither list. A press moves to the next one. "Not" shows its own words (`notLabel`) and is drawn in the error colour with a cross, so it never reads as plain on. The address carries them as `only=` and `not=`.
- **Random is a seeded shuffle, not a fresh one** (`shufflePlace` in `views/browse.js`). Each mod's place comes from its id and a seed, and the seed rides in the address as `seed=` — so turning a page or changing a filter keeps the same order, and a shared link brings back the same shuffle. Drawing a new order on every redraw would put mods from page 1 on page 2 and leave others on neither. "Shuffle" picks a new seed; it is the only way to, since picking Random again from the dropdown fires nothing.
- **One download button, everywhere a mod is listed** (`downloadButton` in `lib.js`). Grid cards, browse rows, Favorites rows and Home's release rows all draw the same button, and it says what pressing it does: "Install with TriOS", "Download", "Download page", or — for a mod with nothing to download — "On the forum", falling back to "On Discord" the way the mod's own page falls back. The button stops its own click from reaching whatever it sits in, which is what keeps a press on a release row from opening that row's changelog instead. Favorites used to fetch every listed mod's own file just to find its downloads; the winner rides on the list record now, so a row costs no request at all.
- **The button is only ever the button, and it is the same width down a list.** "Download" and "Install with TriOS" are different lengths, so a button left to size itself gave a page of cards a ragged right edge; in a browse row it was worse, with right edges up to 48 pixels apart. The button spans the card at the foot, and takes a fixed 148-pixel column in a row. Nothing else shares its line, and no list says how many downloads a mod has — the mod's own page lists them all. On a phone the fixed column stands down and, in a browse row, the button drops to a line of its own — standing it beside the words left the mod's name a letter wide.
- **Favorites.** Pressing the star on a card favorites a mod. The empty star only shows while the pointer is on the card or row (or it has keyboard focus); a favorited mod always shows its star, and a screen with no hover, like a phone, always shows both; favorites are kept in `localStorage` and nowhere else. `#/favorites` shows the reader's own, and `#/favorites?ids=a,b,c` shows somebody else's — the whole list travels in the address, so sharing one needs no account and no server. `#/list` still routes to the same page, because links shared under the old name have to keep working, and the storage key is still `starmodderMyList` for the same reason: renaming it would empty everybody's favorites. The page also works out what the favorited mods require that is not itself favorited, which is the thing a shared list nearly always gets wrong; on the reader's own list a "Favorite all" button stars every one of those the site has a page for. The mods are drawn with Browse's own `modGrid` / `modRows`, so a mod looks the same here as anywhere else and its ☆ is how it comes off the list — the page watches favorites and redraws itself. It has its own Cards/Rows choice (`starmodderFavoritesView`, rows by default), kept apart from Browse's (`starmodderView`, cards by default); both draw the switch with `viewToggle` in `lib.js`. "Clear all" acts at once and offers Undo rather than asking first, and a shared list's button adds to the reader's own favorites rather than replacing them. `lib.js` owns it (`favorites`, `toggleFavorite`, `watchFavorites`, `favoriteToggle`); the count in the bar at the top watches it, and drops its watch when the nav is redrawn. The page's own words are kept to the heading and the counts — an explanation of where favorites are stored, above a list the reader built themselves, is words nobody reads.
- **Reports** (`#/reports`, `views/reports.js`, after Favorites in the nav). Five reports use `mods.json` and `updates.json` in the browser. The builder is unchanged. They show required mods (top 15), mods by game version (including "Unknown"), new mods by month from `addedOn`, mods by category, and updates per week from `updates.json`. The month chart shows the last 24 months or all months since the first. The full chart labels only the years. The updates report also lists the mods with the most updates in that time. Bars link to matching Browse filters where one exists. These links set `game=any` so Browse counts match the bars. Browse otherwise shows only the current game version. `requiredModCounts` in `lib.js` counts required mods. It uses `neededModKey` to match names by letters and digits, so "Lazy Lib" and "LazyLib" count as one. Browse uses the same rule for its "Requires" dropdown and filter. Authors are not ranked by mod count. More mods does not mean better mods.
- **The look is one block of names at the top of `style.css`.** Nothing anywhere writes a colour or a text size out longhand — every one is a name from that block, which is what lets the light version be one short `prefers-color-scheme` block rather than a second stylesheet. A few sizes are set outside the scale on purpose: the letter standing in for a missing picture, the two arrows on a screenshot, and the arrow that opens a release row on Home; those are shapes, not writing. The light cyan is **darker** than the dark theme's — light cyan on white cannot be read, and an action nobody can read is not an action.
- **Which of a mod's two pictures to show is a setting** (`imageChoice` / `imageUrlOf` in `site/lib.js`, the "Mod pictures" section of the Settings dialog). Two choices: the forum post's picture (the default) or the Discord or Nexus one, which is what TriOS shows. The choice lives in `localStorage` (`starmodderPicture`), and ticking it redraws the page. Every list draws its picture through `imageUrlOf` — cards, browse rows, Favorites rows, Home's release rows, the search suggestions and the big picture at the top of a mod's page — so nothing reads `imageUrl` directly any more. A mod with one picture carries no `announcementImageUrl` and looks the same either way, which is most of them; the site reads `announcementImageUrl || imageUrl`. The little per-mod HTML pages (`mod_page_html.dart`) always use `imageUrl`: they are read by Discord and search engines, which have no setting.
- **Pictures in a description are a setting too** (`inlinePictures` in `site/lib.js`, the second half of Settings' "Mod pictures" section; `postBody` in `views/mod.js`). On by default, kept in `localStorage` (`starmodderInlinePictures`), and ticking it redraws the page. **The same choice sits beside the "About this mod" heading** as "Hide pictures" / "Show pictures" (`picturesSwitch`), because nobody finds a setting in a dialog; it is drawn only when the post has pictures, and it redraws just the description in place. **The post is read into a `<template>` before anything else happens**, because setting `innerHTML` on an element — even one not yet on the page — starts every picture in it downloading, and "off" has to mean nothing is fetched. Off turns each picture into a small "picture" link that opens the viewer. Either way, a picture that was a link's only content leaves the link's address behind when it goes, so a badge used as a download button still works; with pictures on, that happens when the picture fails to load. A picture that is not a link opens over the page in the screenshot viewer, which steps through the description's pictures. So does a picture that is a link's only content when the link goes to a picture file or to a picture host's page for it (imgur, ibb.co, postimages and the rest in `PICTURE_HOSTS`, but not an album or gallery). Ctrl-click and the like still follow the link. Any other linked picture, such as a download badge, stays a link. The description is shown whole by default: it has the Description tab to itself, so a long post no longer pushes the screenshots or the changelog down the page. A "Collapse" / "Expand" button beside "Hide pictures" folds it to a 14-line preview; it is only drawn where the post is longer than that (measured with a `ResizeObserver`, since pictures arriving make a post longer), and the fold is not remembered between pages.
- **Spacing is one set of numbers, not a setting.** There used to be a Dense / Comfortable choice; it was folded into one, keeping each where it worked best. Lists and grids are tight (`--gap-cells`, `--pad-cell`, `--pad-bar`), so more mods fit on a screen. Reading is roomy (`--gap-wide`, `--pad-block`, `--pad-page`), so a page's sections and panels have air. A phone gets the tight numbers throughout, from one `@media (max-width: 640px)` block that overrides the names. Every gap and padding in `style.css` is one of the spacing names in the block at the top (`--gap`, `--gap-wide`, `--gap-cells`, `--pad-page`, `--pad-block`, `--pad-cell`, `--pad-front`, `--pad-bar`). Only the room between and around things is set there — never the size of the words, the pictures or the controls. An old `starmodderSpacing` value in a reader's `localStorage` is simply ignored. **The page's top-level `.stack` is the sections, spaced by `--gap-wide`; a `.stack` inside it is one group, spaced by the smaller `--gap`**, and a heading directly in a stack carries no margin of its own — so a heading always sits nearer its own words than the section above, and a page reads as groups. Keep `--gap-wide` clearly bigger than `--gap`, on a phone too, or that is lost.
- **Theme is a setting too** (`THEMES` / `applyTheme` in `site/lib.js`, the top of Settings' Appearance section). Browser Default, TriOS (id `dark`, the old cyan on navy), Light, and eight of TriOS's themes, colours copied from TriOS's `assets/themes.json`. Light is the site's own light colours, for a reader who wants light pages whatever their computer is set to. Its `[data-theme="light"]` block repeats the values in the `prefers-color-scheme: light` block, because a media query cannot share a block with a plain selector, so change the two together. It sits after the shared `[data-theme]` block so it wins over that block's dark text. The choice lives in `localStorage` (`starmodderTheme`) and is written onto `<html>` as `data-theme` — before the first paint by a tiny inline script in `index.html`, and by `applyTheme()` after. Browser Default writes nothing, so it still follows the computer's light or dark setting: on dark pages it uses Independents' colours (its selectors sit on the Independents block and the shared `[data-theme]` block), and on light pages the `prefers-color-scheme: light` block, which sits after every theme block so it wins. Each theme is a `[data-theme="…"]` block in `style.css` giving only `--primary`, `--secondary`, `--surface` and `--surface-container`; a shared `[data-theme]` block works out every see-through strength from those with `color-mix` and puts back the dark text and status colours, since every TriOS theme is dark. The blocks are written against the attribute rather than `:root` so each theme button's colour strip can carry its own `data-theme` and draw itself in that theme. Adding a theme means one CSS block and one line in `THEMES`. **A theme's second colour is the "switched on" colour** (`--on` / `--on-soft`): the page you are on in the nav, a ticked choice, a filter or category in use, a favorited star, the picked rows count. Links and hovers stay on `--primary`. In TriOS and Light `--on` is just `--primary`; without this, a theme like Independents (grey main colour, yellow second) never showed its yellow at all, because almost nothing used `--secondary`.
- **A card's categories are one line of badges at the foot of its words** (`categoryLine` in `views/browse.js`). Categories that do not fit are hidden and counted in a "+N" badge; the first always stays, so the line never reads as a bare "+3". How much fits is only known once the card is laid out, so each line measures itself with a `ResizeObserver` whenever its width changes. The badges are plain, not links, because they sit inside the card's link. The "+N" names what it hides through `quickTip` in `lib.js`, not `title`: the browser waits about a second before showing a `title`, and a reader pointing at "+3" gives up first. The note floats on `document.body`, because a card clips its own contents.
- **How long ago a card's mod changed sits at the bottom right of its picture**, at the end of the badges there (`whenLine` in `views/browse.js`). It has the badges' dark backing but no outline, and an icon in place of a verb: a clock with an arrow running back round it anticlockwise, the same for "updated" and for "added" (Home's Recently added). Hovering shows which, and the full day.
- **Cyan means "you can do something here"** — a link, a button, a chip. A mod's name is not an action, so a mod's name is white and only turns cyan under the pointer. When every title was cyan nothing stood out, because everything did.
- **Cards and rows are a box holding a link**, not a link themselves (`.mod-card` > `.card-inner`, `.mod-row` > `.row-inner`). The "+" has to sit on top of them, and a button inside a link is not allowed and behaves differently in every browser.
- **Every route change starts at the top**, except coming back to Browse, which returns to where the reader left off. Two traps in that, both pinned by how the router is written: the position has to be read by `route()` **before** it empties the page (`notePageScroll`), because an emptied page has nowhere to scroll and the browser says zero from then on; and it is filed against the address Browse last wrote for itself (`lastBrowseHash`), because `location.hash` at that moment is already the mod page the reader is on their way to. Browse scrolls itself and says so (`noteScrollPlaced`), and the router's scroll-to-top stands down for that one page. The skip link cannot be a plain `#app` link either: the hash picks the page, so following one would send the router looking for a page called "app".

- **Which build the site is** (`site/version.json`, `showBuild` in `app.js`). The footer says `v47 · 28cbe0f · 2026-08-24` beside the "data collected" line, and the commit links to it on GitHub — that is what makes a bug report answerable. The file is written by the release workflow (`.gitea/workflows/release.yaml`: `git rev-list --count HEAD`, the short commit, the commit's day), not by any Dart code, and it rides into the published repo because a publish copies everything in `site/`. It is **gitignored**, so it only exists in a build. Run from the repo, `bin/site_server.dart` answers `version.json` itself from git through `SiteVersion` (the results viewer's reader), so the footer shows the build locally too; a real `site/version.json` is served first and wins. It is fetched by hand rather than through `data()`, because it is part of the site and not part of the data — `?data=sample` must not send it looking in `sample-data/`. Every commit to `master` is built and released (there are no hand-made tags — the release is named `v48` after the same count), so the number on the site moves the next time the host downloads a release, which is twice a day. Work that should not be built goes on another branch. **Releases are built and kept on Gitea** (`git.wispborne.com/david/Mod_Repo_Scraper`), not GitHub: the code is pushed to both, but the workflow sits in `.gitea/workflows/`, which GitHub does not read. Gitea's own Actions run it, and the release is made through Gitea's API with curl, as a draft that is only published once both files are on it. Gitea answers signed-in users only, so the host reads a token from `.gitea-token` in the program's folder (gitignored, `chmod 600`, read access to repositories); the update script and the viewer's Update button both use it.

It fetches every file from **its own origin** and nothing else — never GitHub, never another host — and must never depend on anything a plain static server cannot do: no Cloudflare Workers, no Pages Functions, no redirect rules. Opening it with `?data=sample` reads the hand-written examples in `site/sample-data/` instead of the real files, which is how it is worked on before a run has built anything; those examples are pinned to the models by `test/site/sample_data_test.dart`, so a shape change has to be made in both.

**Publishing** (`lib/manager/publish_service.dart`): a publish copies `mod-catalog.json` and `mod-catalog-details.json`, the data files (`mods.json`, `updates.json`, `updates.xml`, `sitemap.xml`, `robots.txt`), every per-mod file and page (a Collection's page included), and the contents of `site/` into the clone, so the pushed repo is a complete servable website next to the data it reads. It never writes, stages or deletes `ModRepo.json` or `forum-data-bundle.json`: those are frozen for old TriOS installs. A per-mod file in the clone that this run did not produce is removed. Missing website files are a log line, not a failure — the outputs still go out.

### Results viewer (`bin/viewer_server.dart`, `lib/viewer/`, `web/`)

A local `shelf` server that serves the static `web/` frontend, a JSON API (`lib/viewer/api.dart`, `data_access.dart`) over the output files, and — when a config file can be read — the management API. Binds to `127.0.0.1` only. Viewer endpoints never write; the only writes are jobs on the management API. When output/bundle shapes change, keep this viewer in sync. Default dirs: `--data-dir qb_data`, `--outputs-dir outputs`, `--root-dir .`; also `--config config.properties` and `--no-manager`.

The old "the server never reads `config.properties`" rule is now narrower: it **may** read it, for the manager's environment and guardrails, and **must never serve** any of its values (the data path excepted). No route serializes `BotConfig`, `ScraperEnvironment` or `LlmSettings`.

`lib/viewer/server_app.dart` (`buildServerHandler`) composes the parts. It picks the `api/manager` subtree off *before* the router/cascade rather than mounting it — a mounted handler's 404 ("no run by that name") is read as "no such route" and falls through to the static files, losing the reason.

The server plants a console log tree and bridges the `logging` package (`Common.initTimberForConsole` / `Common.bridgeLoggingToTimber`); without that, `RunLogCapture` would write empty per-run logs for server-started jobs.

**Which build is running** (`lib/viewer/site_version.dart`, `GET /api/version`): the build number, the commit and the day it was made — the same three values, from the same file, that the public website shows in its footer (see **The public website** above). `SiteVersion` reads `<--root-dir>/site/version.json` first, because a released copy is unpacked from a tarball and has no git checkout to ask; that is why this line used to be blank in production. Failing that it asks git the same three questions (`rev-list --count HEAD`, `rev-parse --short HEAD`, `log -1 --format=%cs`), so a version shows while working in the repo too. `showVersion` in `web/app.js` draws it small and dim under the status chip ("v48 · 28cbe0f", the day on hover). It is for bug reports, so it never makes a fuss: neither way working gives `{}` and the site shows no line at all. Nothing is cached — it is read fresh each time.

**Updating the server from the viewer** (`lib/manager/self_update.dart`, `GET`/`POST /api/manager/update`, `web/update.js`). When Gitea has a newer release than the build running, an "Update to vN" button shows under the status chip. **The work is done by `tool/update-scraper-only.sh`**, the same script cron runs, so there is one way to update and one way back; the server only starts it and reports on it. It cannot run the script as its own child, because the script stops the service and stopping a service kills every process it started. So the script runs as its own fixed unit, `tool/starsector-scraper-update.service` (a oneshot, `User=david`), which outlives the server it replaces, and the server runs `systemctl start --no-block starsector-scraper-update.service` and nothing else. **No sudo**: `tool/starsector-scraper-update.rules` is a polkit rule that lets that one user start that one unit, so the button gives the server no way to run anything as root — which matters if the viewer is ever reachable through a proxy. It used to be `sudo systemd-run`, and allowing that without a password is root in all but name. Not `Restart=always` with the server swapping its own files either: a new build that does not start would be restarted for ever, with nothing to put the old one back, where the script's health check does that. The unit writes the script's output to `.self-update.log` in its `WorkingDirectory=`, then `Finished with exit code N` as the last line however the script ended; a test holds the unit file and `SelfUpdate.finishedPrefix` together. The new server reads that file back, which is how the page learns how it went: it watches every two seconds and reloads once the server answers with the new build, or shows the log when the update was rolled back. A log with no last line and nothing written for 15 minutes counts as died. The button is only shown on Linux, with the script beside the server and allowed to run, the unit installed, and the unit's `WorkingDirectory=` the server's own folder (otherwise the log would be written where nobody reads it); and only while the manager is on, since updating is a change and "viewing only" makes none. It refuses while a job is running or waiting (a restart would stop it), and new jobs are refused while an update is going. Gitea's API is asked for the newest release (`/api/v1/repos/<repo>/releases/latest`, its tag is `v<N>`), as the script does, with the token in `.gitea-token`, at most every ten minutes. With no token Gitea is not asked at all, and the button says the token is missing. The script holds `.update-scraper-only.lock`, so an update from the viewer and one from cron cannot swap files at the same time.

#### Frontend (`web/`, no build step, plain ES modules)

`app.js` is a hash router over view modules that each export `render(root, parts)`; shared DOM/fetch helpers are in `lib.js`. The chrome is a **sidebar** (`index.html`), not a top bar: a Home entry, then grouped sections — **Data** (Topics, Mod Catalog, Mod Details), **Jobs** (Runs and queue), **Debug** (Catalog explorer, Catalog diff, Details diff, LLM test report, Files, Log). The labels name the two files they show, `mod-catalog.json` and `mod-catalog-details.json`; the addresses (`#/modrepo`, `#/bundle`, `#/merge`) and the job names (`mergeModRepo`, `rebuildBundle`) kept their old names so saved links and saved runs still work. The two diff viewers are first-class sidebar entries, reached at `#/merge/changes` and `#/bundle/changes`; they are no longer sub-tabs inside the merge/bundle pages. The lit entry is the deepest nav route whose path segments all match the current hash, so `#/bundle/changes` lights Details diff while `#/bundle/12345` lights Mod Details. `#/home` is the default. Sidebar icons are inline SVGs built from `web/icons.js` (Tabler Icons, MIT, copied in as path data — nothing loads from the internet at run time).

The home page (`views/home.js`) is the front door: one search across Topics, the bundle, and ModRepo at once (three endpoints in parallel, results grouped, each row linking to a detail page); quick-action job buttons; the last finished run with its counts and a "what this run changed" link; and health numbers (topics with no download, no LLM answers, placeholders) that each open the topics list pre-filtered.

Confirmations and notices are **in-page dialogs**, not the browser's own popups: `lib.js`'s `askDialog()` (yes/no, the confirm button focused so Enter still works) and `noticeDialog()` (one OK). `manager.js`'s `confirmAndSubmit` shows `describeJob`'s sentence in an `askDialog`.

**List state rides in the URL.** Topics, ModRepo and the bundle list read their search / filters / sort / page from the hash query on render (`lib.js` `hashParts` strips the query; `hashQuery` reads it) and write it back with `replaceHash(buildHash(...))` as state changes — so a reload, a bookmark, or the back button brings the same list back, without every keystroke piling up in history. Rows-per-page stays a site-wide `localStorage` preference, out of the URL. The home health links use the query form, e.g. `#/topics?filters=noDownload`.

Every paged list draws `lib.js`'s `pager()`, which also carries the **Show** box for rows per page — 25 to 500, or all on one page. The choice is one setting for the whole site, kept in `localStorage` and read by `pageSizePreference()` when a view builds its state. On the wire, `pageSize=0` means "every row, one page"; a named size over 500 is still capped, and nonsense still falls back to 50. A list that adds a pager should pass the size callback too, and reset `page` to 0 inside it — page 4 of 50 is not page 4 of 250.

Every page opens with a `lib.js` `breadcrumbs()` trail (Home is prepended; the last crumb is the current page, the rest are links) — it replaces the old per-page "‹ Back to …" links on detail pages. Detail pages (thread, ModRepo mod, run, merge group) end with a closed-by-default `lib.js` `rawJson()` fold, so anything the tidy layout leaves out is one click away. Detail pages stack their blocks in a `.stack` (or the thread page's `.thread`) container that gives even spacing between blocks, so no block carries its own margins; an emptied block (a loader cleared it) takes no space, so a section that isn't there leaves no gap.

A page that shows a **list of folds** gives it a `lib.js` `expandAllButton(container, selector)` — one button whose label says what a press would do ("Expand all" until they are all open, then "Collapse all"). Pass a selector narrow enough to leave out the folds *inside* a fold: `details.change-card` on the two diff pages and the topic history, `details.panel` on the merge groups list, `:scope > details` on the LLM test report. It reads the folds from the DOM on every press, so it never holds a stale idea of what is open, and it keeps up with folds opened one at a time by catching `toggle` on the way down (that event does not bubble). A list that redraws itself must call `button.refresh()` afterwards — new folds arrive with no toggle to notice them. Where a fold's shut row says what changed, it says **which fields** moved, not how many: `changedFieldsLine()` names the first three and counts the rest, `changedFieldsTitle()` puts the full list on hover. It goes on a **second line at the left**, under the name — out on the right, past the author, nobody reads it. That is why the `.change-hint` span is built *after* the chevron: the summary is a wrapping flex row, the hint is given `flex-basis: 100%` so it takes a line of its own, and anything after it would be dragged down with it. It is left out entirely when there are no fields to name, so an added or removed row carries no empty second line.

`web/manager.js` is the only place the frontend talks to `/api/manager/`. It owns three things:

- **The status poller.** One shared `GET /status` loop — about a second while a run is live or queued, five seconds idle, stopped while the tab is hidden. Views call `subscribe(fn)` and drop the subscription on `hashchange`; nothing else polls. `refresh()` returns the in-flight ask rather than starting a second one, so a view that loads mid-beat still gets a real answer instead of `null`.
- **Sending jobs.** `submitJob` / `cancelCurrent` / `confirmAndSubmit`, plus `describeJob` — the one plain sentence every confirm box shows. A refusal is re-thrown carrying **the server's own message**: those are already written for people, so never wrap them in wording of our own. UI-started jobs always send `replayAllowed: false`.
- **The ticked topics.** The selection set lives here, not in the view, so it survives paging, searching and switching views. It also rides in `sessionStorage` (`viewerSelectedTopics`), so a half-built selection survives a reload. Cleared on submit.

`mountHeaderChip()` draws the always-on status chip at the foot of the sidebar (`#status-chip` in `index.html`). It is a status dot whose colour carries the state — grey off, green ready, amber when jobs wait, cyan and pulsing while one runs — plus a word or two and, mid-run, a progress bar.

Two views read all this: `views/runs.js` (live run, queue, history, and the start-a-job area — "Fetch and update" (forum scope and boards, which of Discord and Nexus to fetch — all three boards and Discord ticked by default, Nexus not — LLM on or off; the button is greyed out when nothing is ticked, and its confirm box names what will be fetched and what keeps its saved results), "Without fetching" (Rebuild from saved files, LLM catch-up, Scan images) and Publish. The older kinds still run and still show in the history, but the form no longer offers them, because each of them only does half of what the catalog needs) and `views/run.js` (`#/runs/<id>`: record, log tail, run again). Two gotchas worth keeping: the start-a-job cards are only redrawn when the manager goes on or off — redrawing them on the poller's beat would wipe what the user just picked — and the log route's "no log file" answer arrives as a `MissingFile` from `lib.js`'s `api()`, not as a body field. A live run's page redraws every second, so the run page's **log panel is built once and kept**: the panel and its scrolling `pre` are never taken out of the page, and each draw only removes the lines that fell off the top of the tail and appends the new ones (`linesDroppedFromTop` lines the two windows up). Rebuilding it, or even detaching it for a moment, throws away where the reader had scrolled to and anything they had selected, which makes a running log unreadable. The scroll is held at the same distance from the bottom, so a reader sitting at the foot of the log is left there and it follows itself. The **LLM test** job has no other way in — its report page (`views/llm_test.js`) carries the only button that starts it.

Comparing two saved things — two merges' mods, two bundles' topics — is one helper, `lib/viewer/compare_rows.dart`. Callers pass how a record is keyed, which fields are worth looking at, and what to call it on screen; `merge_views.dart` and `bundle_views.dart` are thin over it. A field can carry a `describe` instead of before-and-after values, which is how "the post text changed" says so without the text nobody kept.

**A diff shows what moved and nothing else.** Only changed fields get a row — that part was always true — and a field holding a list or a map now gets picked apart too, so only its changed entries are listed. A field says how with `itemsOf`: `mapItems` and `listItems` in `compare_rows.dart` cover a plain map and a plain list of names, and `bundle_views.dart` has its own for downloads, links and the LLM's mods. `urls` used to print all four of a mod's links on both sides because one of them gained an "s", which is not a diff. Two things follow. **An `itemsOf` that comes back empty means the field did not really change** — the entries were only written in a different order — and the field is dropped; on real data that moved six of 63 changed mods back to unchanged, and it is why order is deliberately not a change in `listItems`. And **every key of an entry is compared, not only the named ones** (`_partsThatMoved` in `bundle_views.dart`); the names are labels, not a filter, because a row saying "this changed" and then listing nothing sends somebody hunting for a change the page decided not to mention.

The three pages that show one of these tables — Catalog diff, Details diff and one topic's history — share `web/views/diff_table.js`. Keep it that way: three copies drifted before, and a reader comparing two pages about the same change should not see it worded two ways.

The Bundle view has a what-changed page (`views/bundle_compare.js`) built the same way as the merge one, and a run's page links straight into it — "what this run changed" compares that run's bundle with the one before it. The link only appears when there is an older snapshot to compare against.

**Watching a run mid-flight.** The newer side of that page can also be `working` — the data on disk right now rather than a saved snapshot — which is how a run is watched while it is still going. It rests on the save-as-you-go rule above: a run publishes its bundle at the end, but writes what it scrapes and what it pays the LLM for as it goes, so the gap between the newest saved snapshot and what is on disk is what the run has done up to this second. A live run's page offers "What this run has changed so far" instead of the finished-run link. The page is brought up to date by a **Refresh button** and in no other way — it is drawn only when the newer side is the data on disk, since two saved bundles never change. It deliberately does not redraw itself on a timer: that throws away where the reader had scrolled to and every card they had opened, which on a page whose whole purpose is reading what changed is worse than being a minute out of date.

`lib/viewer/working_bundle.dart` builds that side: the bundle **as it would be published right now**, in the same shape a snapshot has — post text swapped for the same fingerprint, local image paths and the forum's session token stripped the same way. Four things hold it together. It is **compared against a snapshot and nothing else**; nothing may publish or serve it as a bundle, the same rule snapshots live under. Which threads make it in is decided by `keepThreadInBundle` in `qb/mod_thread_filter.dart`, the **same function the real publisher calls** — a rule copied instead of shared would show a thread as added or removed for as long as a run lasted. It **holds its answer** against a stamp of every file the working data lives in, and re-reads only the detail files that actually moved, so a rebuild mid-run costs almost nothing (a cold build over a thousand topics is about half a second). And "last written" is **the newest file write, not the newest scrape time** — an LLM pass changes what a run has produced without re-scraping anything, and reading the scrape times would tell the reader the data was a week old while it changed under them.

The data on disk is only ever the **newer** side; asking for it as `a=` is refused in plain words. A merge has nothing to show this way and does not offer it — a merge deliberately writes nothing until it finishes.

**One thread page, reached two ways.** `#/topics/<id>` and `#/bundle/<id>` render the same page: `views/topic.js` is a thin wrapper that calls `renderThreadPage` in `views/bundle.js` (with its own "back to" link). It shows the working (on-disk) data for the thread — the latest truth — in this order, most useful first: the extracted data (the LLM's mods with their downloads and extras, then the rule-based downloads); the thread and post details; every picture, grouped by post (first post, each later post by the author, each joined Discord thread); the forum post in a sandboxed frame, with the author's later posts each in a frame of their own below it with their dates and links; and the raw JSON last. There is no TriOS card preview. When the published bundle is behind that data it shows a **staleness banner** (`bundleStaleness` compares the thread's `scrapedAt` against the bundle's `generatedAt`; states are `stale` / `absent` / `noBundle`) with a one-click Rebuild bundle button. The shared pieces — the sandboxed post frame, image and link lists, the download tables, the LLM mods with their downloads and extras, the four per-topic job buttons (`topicActionBar`, drawn only when the manager is on), and the staleness check with its Rebuild button (`bundleStaleness` / `topicStaleness` / `rebuildBundleButton`, shared with the history page) — live in `views/extraction_views.js`. Download tables come in two on-disk shapes, and telling them apart matters beyond this page: the topic endpoint serves the resolver's `DownloadCandidate` (`sourceUrl` / `resolvedUrl` / `archiveFilename`) out of `assumed-downloads-cache.json`, where one topic's list is wrapped in a `candidates` field, while the published bundle carries `AssumedDownloadCandidate` (`originalUrl` / `resolvedDirectUrl` / `fileName`) as a plain list. Reading a bundle for the cache's shape is why the diff pages showed no download changes at all on real data for as long as they existed; `downloadRowFromCandidate` / `downloadRowFromBundle` map each to one plain shape. The thread page reads working data, so it uses `downloadRowFromCandidate`; `downloadRowFromBundle` stays as the converter for the published shape. Long file names and URLs in these tables are shortened for the cell (full value on hover, `.dl-table` keeps them to one line so the table scrolls sideways rather than stacking).

**One topic's history** (`views/topic_history.js`, `#/topics/<id>/history` and `#/bundle/<id>/history`, reached by the History button on the thread page) reads like a git log: one entry per run whose saved bundle changed that topic, newest first, down a rail with a dot each. Runs that left the topic alone are not listed. `GET /api/topics/<id>/history` builds it — `topicHistory` in `bundle_views.dart` walks the kept snapshots oldest to newest and diffs neighbours over the same `bundleFields` the diff page uses, so the two can never disagree about what changed or what to call it. Three things to keep: it reads snapshots through `bundleRunUncached`, **not** the two-slot holding pen, which is sized for the compare page's pair (a test pins this); the answers are held per topic until the set of saved snapshots changes; and it is now exactly what the Bundle diff page works out for the same topic (`topicChanges` is one call to `changedFields`), rather than a second path that could disagree with it. History only reaches as far back as `qb_bundles_to_keep`, so the foot of the rail says where it starts, and "never in a bundle" is worded differently from "in every bundle and never changed". Unpublished working data leads the log as a hollow-dot entry with the Rebuild bundle button, the same way a git viewer shows uncommitted changes.

The Merge view is three files: `views/merge.js` (routing, summary, groups, removals), `views/merge_shared.js` (which merge is being looked at, the run picker, cell formatting) and `views/merge_compare.js` (before-and-after for one group, and what changed between two merges — the `#/merge/changes` diff page, its own sidebar entry). Which merge is picked lives in `merge_shared.js`, so it survives moving between the merge pages; every merge API call goes through `withRun()`. The list of saved merges is asked for again on each page load, so one that finished while the tab sat open turns up — but not on a redraw after picking, which would be a wasted request.

**Manager off is a mode, not an error.** When status says off, the chip's dot goes grey and it says "Viewing only", the Runs view explains how to turn it on in one sentence, Home shows a "viewing only" note instead of the quick-action buttons, and Topics renders no tick boxes and no buttons — the page reads exactly as the read-only viewer always has.

## Conventions

- **Plain English** in all user-facing copy (viewer text, FAQ, docs) and in explanations. Avoid jargon.
- **Whenever you add an icon beside words** (on the public site or in the viewer), check its vertical alignment in the browser before calling it done. The target: an icon is taller than the capital letters, so it looks centred when it sticks out **equally above the tops of the capitals and below the baseline** — its middle on the middle of the capitals. Two wrong targets, both tried: centring the boxes (an icon centred on its line box sits about 1px high, because a line box has more room above the capitals than below the baseline), and lining up with the small letters (the icon then hangs below the baseline and looks low). Measure the drawn shapes, not the boxes: the icon's top and bottom come from the SVG's `getBBox()` scaled by its `viewBox`; the baseline and the height of a capital "H" come from canvas `measureText` in the element's own font. The overhang above and below should differ by less than half a pixel. A screenshot from the browser pane is shrunk and compressed, so it cannot settle a single pixel; a screenshot the user pastes can, by reading which rows hold the icon's pixels and which hold the letters'. On the site, `transform: translateY(0.06em)` on the icon's span is the usual fix, and the list of icons that take it is the rule above `.jump-target` in `site/style.css` — add a new one there. An icon alone in its button is not beside words and stays centred.
- `analysis_options.yaml` enforces `avoid_print` (use the `timber`/`logging` helpers, not `print`), required return types, and prefer-final/const rules.
- Spec-driven changes live under `openspec/` (`specs/` are current capabilities, `changes/` are proposals). Use the `opsx:*` skills to propose/apply/archive changes here.
- For any Starsector game/API/modding question, use the `starsector-knowledge` skill — never answer from memory, since the API changes between game versions.
