# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## What this is

A Dart CLI that scrapes Starsector mod metadata from several sources and produces two outputs consumed by the TriOS launcher:

- `outputs/ModRepo.json` — merged, deduplicated mods from Forum + Discord + Nexus (the "ModRepo" pipeline).
- `outputs/forum-data-bundle.json` — a richer per-topic bundle with images, download links, and optional LLM-extracted facts (the "QB" pipeline).

Both pipelines run from one entry point and are toggled independently in `config.properties`.

It also builds a third set of files, for the public website in `site/` — see **The public website** below. Those are built from the two outputs above; neither of those outputs is changed by them, and TriOS keeps reading the bundle exactly as it did.

## Commands

**Codex on this Windows host:** Run Dart commands with SDK access outside the sandbox. A sandboxed `dart` resolves to Flutter's wrapper, cannot write its cache lock, and waits forever. This repository does not use FVM.

```bash
dart pub get                       # install deps
dart run bin/scraper_main.dart     # run the scraper (reads config.properties)
dart test                          # run all tests
dart test test/mod_merger_test.dart            # run one test file
dart test --name "substring of test name"      # run tests matching a name
dart test test/llm_live --tags llm --run-skipped   # the live-model tests (needs a local LLM)
dart analyze                       # lint (see analysis_options.yaml for extra rules)
dart run bin/viewer_server.dart    # local read-only results viewer at http://127.0.0.1:8085
dart run bin/site_server.dart      # the public website at http://127.0.0.1:8099, against real data
dart compile exe bin/scraper_main.dart -o mod_repo_scraper   # what CI ships
```

### Code generation (dart_mappable)

JSON models use `dart_mappable`. Every `*.dart` model has a generated `*.mapper.dart` sibling that is committed to the repo. After changing any `@MappableClass` model, regenerate:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Do not hand-edit `*.mapper.dart` files — they are overwritten by the build.

## Configuration

Everything is driven by `config.properties` (read by `Common.readConfig()`; fields live on `BotConfig` in `lib/bot/common.dart`). It holds real auth tokens and is **gitignored** — never commit it, and do not paste its contents anywhere external. `config.example.properties` is the committed stand-in: every key with its default and a plain-English note. **Keep it in step** — a key added, renamed or given a new default here means editing that file too, and `Common._recognizedKeys` is the list to check it against. Every key is snake_case and starts with its group prefix (`modrepo_`, `qb_`, `llm_`); only `log_level` is global. Unknown keys are warned about at startup, so a typo or an old (pre-rename) key name is caught right away. Key switches:

- `modrepo_enabled`, `modrepo_forums_enabled`, `modrepo_discord_enabled`, `modrepo_nexus_enabled` — the ModRepo pipeline and its sources.
- `qb_enabled`, `qb_scope` (`new_data` / `all` / `pages` / `topics` / `libraries_only`; camelCase spellings like `newData` also work), `qb_boards` (`main`/`lesser`/`libraries`) — the QB pipeline.
- `modrepo_use_cached` / `qb_use_cached` — replay from the on-disk raw-HTTP caches instead of hitting the network (see Caching below).
- `llm_enabled` and the `llm_*` keys — optional LLM post-extraction (off in production by default).
- `modrepo_merge_debug` — write `merge-debug.json` for the viewer's Merge view, and save that merge's own snapshot. This decides it for CLI runs only; a merge started from the website always collects it.
- `modrepo_merges_to_keep` — how many merge snapshots to keep (default 20); older ones are dropped. 0 keeps everything.
- `qb_manager_url` — environment. Empty (the default) means the CLI runs the QB job itself, exactly as before. Set (e.g. `http://127.0.0.1:8085`) means it hands the job to that server. Unreachable / manager off / different data folder → warn in plain words and run standalone. Production never sets it.
- `qb_runs_to_keep` — environment. How many runs the history keeps (default 100); older ones are dropped with their log files. 0 keeps everything.
- `publish_site_path` — environment. Where the public website's own files live, copied into the publish clone next to the data they read. Defaults to `site`.
- `qb_bundles_to_keep` — environment. How many published bundles to keep a snapshot of, for the what-changed page and for how far back one topic's history goes (default 500). About a megabyte each, so roughly 600 MB and about eight months of twice-daily publishing. 0 keeps everything.

## Architecture

Orchestration lives in `lib/bot/scraper/main_repo_scraper.dart` (`MainRepoScraper.main`), which asks for the two pipelines in sequence. Neither is inline any more: both are jobs, submitted to the manager core in `lib/manager/` — one queue, one history, one lock, whether the job was asked for from the command line or from a browser.

### Manager core (`lib/manager/`)

The QB pipeline is callable, not just runnable. `main()` turns the config file's job-shape keys into one `JobRequest` and hands it to a `JobManager`; everything else lives in the core. The web API and the browser UI sit over that same core.

- `job.dart` — `JobKind` (`fullRun`, `rescrapeTopics`, `resolveDownloads`, `extractLlm`, `llmCoveragePass`, `llmTest`, `rebuildBundle`, `mergeModRepo`, `scrapeAndMerge`), `JobRequest` (what to do), `RunRecord` / `RunCounters` / `RunState` (what happened). `dart_mappable`, so `job.mapper.dart` is generated. `runJob` also takes the `runId`, so anything a job saves next to the run's record and log can be filed under the same name — that is how a merge snapshot gets its name.
- `scraper_settings.dart` — the config split made real. **Environment** (`qb_data_path`, LLM endpoint/model/keys) and **guardrails** (`llm_max_topics`, `qb_delay_ms`, `llm_timeout_seconds`) go into the service's constructor; **job shape** (`qb_scope`, `qb_boards`, page limits, `qb_use_cached`, `llm_enabled`, `llm_reprocess_only`, `llm_test_mode`) is read only by the CLI, to build its request. The service must never read a job-shape key.
- `scraper_service.dart` — one method per job kind, composing the existing QB pieces. Builds the store, resolver, probe cache and LLM store once; builds the forum HTTP client per job. `fullRun` honours the request's `replayAllowed`; **per-topic kinds always fetch live**, even when `qb_use_cached=true`. Each per-topic kind drops exactly one cache layer's entries for the chosen topics (`QbDownloadResolver.dropTopics`, `DownloadableProbeCache.dropUrls`, `LlmExtractionStore.dropTopics`) and nothing else.
- `job_manager.dart` — a queue, one job at a time, wired to the service, the history store and a reporter. `cancelCurrent()` sets a flag the service checks between topics.
- `run_history_store.dart` — `<qb_data_path>/runs/runs-index.json` plus `runs/<run id>.log`. Written on start, on every state change, and every 10 progress reports; anything still saying `running` at startup becomes `interrupted`. Log capture hooks `DebugTree.extraAppenders` while a run is active — safe because only one job runs at a time. Only the newest `qb_runs_to_keep` runs (default 100, 0 keeps everything) are kept; the rest are dropped on save, log files included, since the logs are what fill the folder. **Only the paperwork goes** — the record and the run's own log. Scraped data (mods index, detail files, every cache, the bundle) all live outside `runs/` and are never touched; a test pins this. The log file named by a record is only deleted if it ends in `.log` and really sits in `runs/`, because that name is read back from a file on disk and this is the one place that deletes anything. The trim happens **after** merging in the other program's runs from disk and before writing — the other way round, a run just dropped would be read straight back as one this copy had never heard of. A run that hasn't ended is never dropped.
- `run_reporter.dart` — `RunReporter` (`phase`, `progress`, `log`). `progress` also carries the run's totals so far (`errors`, `llmCalls`) for the jobs that can count them as they go; leaving one out means "no news", not zero, so a job that can't count something never wipes what is already known (the scrape leaves `errors` alone — the engine only reports failures at the end). This is what makes spending visible while a run is live and honest on a run that dies: the counters ride the same every-10-reports save as everything else. Pinned by `test/manager/live_counters_test.dart`. `ConsoleRunReporter` drives `ConsoleProgressBar` and sends log lines to timber, which is what keeps CLI output identical. `LogRunReporter` is the server's: no bar, but its lines still go to timber, which is how `RunLogCapture` gets them. **Never give the server the silent reporter** — its `log()` drops everything, so a browsed run shows counters with no reasons ("1 error", no word of what went wrong). Pinned by a test. The service talks only to this interface, never to the console.
- `data_lock.dart` — `<qb_data_path>/scraper.lock` (pid, `server`/`cli` label, start time). `JobManager` takes it before each job and releases it in the same `finally`, so completed, failed and cancelled all release. A lock held by a live process is waited for (logged once); one whose pid is dead is cleared and logged. A delegating CLI never takes it — the server holds it for the job.
- `manager_api.dart` — the routes under `/api/manager/`: `GET /status`, `POST /jobs`, `POST /jobs/cancel`, `GET /runs`, `GET /runs/<id>`, `GET /runs/<id>/log?tail=N`. Bodies decode with `JobRequestMapper.fromMap`; answers are the mapper maps. `ManagerApi.offHandler(reason)` is the 503 "manager is off" stand-in. **Status is built by hand from four fields** (`managerOn`, `dataPath`, `current`, `queued`) — a test pins that list, because no config value may ever reach the browser. The data path is the one allowed exception; `cli-delegation` needs it.
- `delegation_client.dart` — `ManagerDelegate`: probe `/status`, compare data paths (`p.equals`), submit, poll once a second and drive `ConsoleRunReporter` from the snapshot, print the usual summary (plus the log tail on failure). Returns null when the job should run locally instead, having said why.

`JobManager` takes a `JobRunner` (the interface `ScraperService` implements), so tests can stand in a fake job. `RunHistoryStore.save()` merges in any run on disk it hasn't heard of before writing — two processes each hold their own copy of the index in memory, so writing it as-is would drop the other's runs. Reading works the same way round: `records` and `byId` check the index file's timestamp and size first and re-read when it has changed, so a long-lived server shows runs another program started without being restarted (it would otherwise show the history as of its own startup — worst at the moment you go looking). Runs this copy started (`_ourRunIds`) are kept from memory on that re-read, because ours are only saved every tenth report and the file would wind our own live run backwards.

`llm_test_mode` and `llm_reprocess_only` are no longer branches in `main()` — they pick the `llmTest` and `llmCoveragePass` job kinds. The config keys are unchanged.

### ModRepo pipeline (Forum / Discord / Nexus → merge → ModRepo.json)

Driven by `lib/manager/modrepo_service.dart` (`ModRepoService`), a second `JobRunner` beside `ScraperService`. `JobRouter` (same file) sends each request to whichever of the two owns that kind, and `JobManager` is given the router — so the two pipelines share a queue, a history and a lock while sharing no code, no files and no secrets. Its settings split the same way as the QB half (`ModRepoEnvironment` / `ModRepoGuardrails` in `scraper_settings.dart`): tokens, folders and the snapshot limit are environment; which sources to fetch, page counts and `collectMergeDebug` ride on the request.

Two kinds: `mergeModRepo` merges what is already saved (no network at all), and `scrapeAndMerge` fetches the chosen sources first. **All three sources come back the same way: their `<name>_cache.json`**, written after every successful scrape. Discord has a second way back — replaying `discord_raw_cache.json` — but it is only tried when `discord_cache.json` has nothing to give, and it must stay that way round: that recording is only written by a job that was allowed to replay (`modrepo_use_cached=true`), which production never is, so it is usually missing and, where it exists, usually months stale. Preferring it once cost every merged mod its Discord source. Pinned by a test. `modrepo_use_cached` decides which one the CLI asks for. A source with no token is skipped with a line in the log, not failed. A merge cancelled part-way writes **nothing** — no `ModRepo.json`, no snapshot — because half a merged repo is worse than yesterday's whole one; source caches already written are kept.

- Scrapers: `forum_scraper.dart`, `discord_reader.dart`, `nexus_reader.dart`. All three save a per-source `<name>_cache.json` after a successful scrape, and that is what a merge reads back. Discord *additionally* goes through a raw-HTTP `CachingClient` (`discord_raw_cache.json`), which is a dev convenience only — see above.
- Merge: `mod_merger.dart` — buckets by forum `topic=<id>`, then a trigram index narrows candidates, then subsequence fuzzy match (`fuzzy/fuzzy.dart`) + author aliases (`mod_repo_utils.dart`), then same-source dedup / merge / validate. Optional `MergeDebugCollector` records why each group formed, written to `merge-debug.json` **and** to that run's snapshot.
- Author names are tidied **last**, once everything else is done (`ModRepoUtils.tidyAuthorNames`, called from `ModMerger._tidyAuthorNames`). Merging pulls the same person in from every source at once, so Nexerelin came out credited to "Histidine", "Histidine, Zaphide" and "histidine_my" — two people written three ways. Credits naming several people are split apart, then spellings of one person are folded together (capitals and punctuation, digits on the end of a Discord name, and the `authorAliases` table) and the best-looking one kept. It has to run at the end: grouping and matching need every spelling a source gave us, and this throws most of them away.
- Category names are tidied straight after the authors, and last for the same reason (`tidyCategoryNames` in `category_aliases.dart`, called from `ModMerger._tidyCategoryNames`). Discord tags a mod "Faction" where the forum's mod index calls that shelf "Faction Mods", so a mod on both came out labelled twice. `discordCategoryAliases` holds **only plain synonyms** — four of Discord's twenty tags. The rest say what a mod *does* (Ship Pack, Exploration, Audio/Visual…) where the forum's ten headings say which shelf it sits on, so there is nothing to fold them into: almost all would land on "Miscellaneous Mods", which for a Discord-only mod is the one useful thing anyone knew about it. Three are left out for their own reasons: "Portrait/Flag Pack" is one tag against two forum headings with nothing to tell them apart, and "Total Conversion" and "Mod Manager" are each near a forum heading without meaning quite the same thing. Every answer in the table must be spelled exactly as the index spells it — a test pins that — or the merge invents a heading the forum does not have. Unknown names are kept as written, and the run logs every category in use so a new tag gets noticed.
- The forum's own old category names are a separate table, `legacyCategoryMap` in `qb/legacy_category_map.dart`, shared with the QB pipeline through `currentCategoryName`. It only applies to a heading the index has stopped using: "Utility mods" is in that table as an old name for "Standalone Utilities", but it is also a live heading today, so it must be left alone.
- Snapshots: `lib/manager/merge_snapshot_store.dart` — one gzipped file per merge run at `<qb_data_path>/merges/<run id>.json.gz`, plus a small `merge-counts.json` holding each one's headline numbers for the list. Gzipped because a real run's data is around 12 MB written out plainly and about a megabyte squashed. The newest N are kept (`modrepo_merges_to_keep`); the trim follows `RunHistoryStore`'s rules to the letter — only `.json.gz` files sitting directly in `merges/`, never the one just written. `merges/` is paperwork, like `runs/`: no scraped data and no output ever lives there.
- Model: `scraped_mod.dart` (`ScrapedMod`, `ModSource`, `ModUrlType`, `Image`).

### QB pipeline (`lib/bot/scraper/qb/`)

Adapted from a separate C# project (theRoastSuckling's QBMBAMM); its scraper was ported, but this repo is the consumer's fork. Flow driven by `QbScraperEngine.run(scope, onTopicSaved:)`:

1. `mod_index_scraper.dart` / `board_scraper.dart` walk the configured forum boards for topic summaries.
2. `topic_scraper.dart` + `html_processor.dart` fetch and parse each topic page. It keeps the **author's opening run**: the first post, plus each post straight after it by the same author, stopping at the first reply by anybody else (at most ten). The first post fills the fields it always did; the rest ride in `QbModDetail.extraPosts` as `QbForumPost`s with their own HTML, images, links and dates. Some authors keep every download in a second post of their own — topic 35651 lists a dozen forks in the first post and has all seven zips in the second — and reading only the first meant those threads reached the site with nothing to download. Stopping at somebody else's reply is deliberate: further down, the author's answers to bug reports carry links to unfinished builds and version numbers that are not the release. `detail.allLinks` / `allImages` / `openingPosts` are how everything downstream reads the run; **anything hunting for a download, a name or a fact uses those, and only the description keeps reading `contentHtml` alone**.
3. `download_resolver.dart` turns links into download candidates using host-specific rules (Google Drive, Dropbox, MediaFire, GitHub, forum attachments…); cached in `assumed-downloads-cache.json`.
4. Results are persisted incrementally by `json_data_store.dart` into `qb_data_path` as `mods-index.json` plus `mods/<id>/detail.json`.
5. `bundle_publisher.dart` assembles `forum-data-bundle.json` from the store + resolver + LLM store.
6. `ScraperService._rebuildBundle()` publishes it and saves a snapshot of it — see below. Every kind except `llmTest` ends here, so every run that changes what TriOS receives leaves something to compare.

**Bundle snapshots** (`lib/manager/bundle_snapshot_store.dart`): one gzipped file per publishing run at `<qb_data_path>/bundles/<run id>.json.gz`, plus `bundle-counts.json` for the list's headline numbers. **A snapshot is not a bundle** — the posts' `contentHtml` is dropped and a short `contentFingerprint` kept in its place, which takes it from 4.3 MB to 1.15 MB and is what makes keeping hundreds of them affordable. So a changed post is reported as changed and no further; the old words are gone. Each of the author's `extraPosts` loses its text the same way, so a changed second post is noticed without keeping it either. Nothing may publish or serve one as a bundle. The newest N are kept (`qb_bundles_to_keep`, default 500) under the same trim rules as `merges/`: only `.json.gz` directly in `bundles/`, never the one just written. Like `runs/` and `merges/`, this is paperwork — no scraped data and no output lives there. A snapshot that fails to save never fails the run: the bundle went out, and that was the job.

**Backfilling snapshots from git** (`bin/import_bundle_history.dart`, core in `lib/manager/bundle_history_importer.dart`): a one-time command that reads every past version of `forum-data-bundle.json` from the published repo's git history (the publisher commits the bundle on every publish) and files each as an ordinary snapshot, so the history pages reach back before we started saving snapshots ourselves. It runs `git log`/`git show` over a clone (a path you already have, or a URL it clones to a temp folder) and hands each old bundle to `BundleSnapshotStore.save`, so imported snapshots are the same shape, same fingerprints, same folder as real ones. Their names carry a `-imported` tail instead of a job kind (e.g. `20260417T032007Z-imported`) — the only difference, and how `topic_history.js` knows to show them without an "Open this run" link, since no run sits behind them. Names are built from the commit time in the same sortable stamp real run ids use, so imported and real snapshots share one timeline by name alone, and the trim drops the oldest (imported) first once the limit bites. Safe to re-run: each commit always saves under the same name. It builds the store with `--keep 0` by default so a big backfill is never trimmed part-way. Fingerprints are computed the same way as the live path, so the seam between the last imported snapshot and the first real one shows no false "post text changed".

Scraping is pipelined: `onTopicSaved` runs download resolution per topic as it is saved, and **starts** that topic's LLM read without waiting for the answer — the scrape moves on at forum speed while the model works beside it. `llm_max_concurrent_calls` (default 3) is how many topics may be talking to the model at once, wherever the call comes from; the limit lives inside `PostExtractor`, so no caller can overrun it. Every read started is waited for before the scrape step returns (`ScraperService._scrape`), so a finished scrape is still a fully-extracted one; a cancelled run finishes only the reads already talking to the model (`PostExtractor.stopNewCalls`), so Ctrl-C stops the spending too.

### QB LLM extraction (`lib/bot/scraper/qb/llm/`, optional)

When `llm_enabled=true`, `PostExtractor` sends each thread once to any OpenAI-compatible chat endpoint (`openai_client.dart` / `llm_client.dart`, prompt in `prompt.dart`) to pull out facts the rules miss: extra downloads, changelog, mod version, support links, license, a link to where the code is kept, where each mod is described, and optional summaries. `post_reducer.dart` trims post HTML first, leaving each link where it sat as `[link: <url>]`. Results are cached in `llm-extraction-cache.json` via `extraction_store.dart`, so re-runs only pay for new/changed posts.

**One thread is one call**, and the whole opening run goes into that one prompt (`_ReadPosts` in `post_extractor.dart`): the first post under `=== POST TEXT ===`, then each of the author's later posts under its own `=== FOLLOW-UP POST N ===` heading, with the links, rule-detected downloads and images merged across them all. Splitting it into a call per post would be worse in every way — the answer is one `mods` list about the whole thread, so a thread that names its mods in one post and downloads them in another would give one call mods with no downloads and the other downloads with nothing to attach them to; merging the two answers would mean matching the model against itself by name, and a disagreement there mints a duplicate mod with a permanent id; and the system prompt would be paid once per post instead of once per thread. Size is not the worry: topic 35651's first post is 4,234 prompt tokens and its second adds about 700, against a corpus average of 4,730 and an existing maximum of 33,195. Grounding reads the same run, so a URL in the second post counts and one in somebody's reply never does. `llm_max_input_chars` applies to the posts together, and **the later posts keep their words while the first post gives up the room** — they are short and download-dense, the first post is the long write-up, so trimming in posting order would push the Downloads post out of the prompt entirely.

Coverage is over the **store**, not over this run's scrape. `ScraperService._llmCoveragePass` walks the whole mods index after the scrape and calls `extractForTopic` on every stored topic, so a topic that was scraped before the LLM was switched on still gets picked up. The pass works a few topics at a time — the same `llm_max_concurrent_calls` — so the topics that do need a call overlap instead of queueing one behind another. Topics scraped this run were already extracted beside the scrape and come back as free store hits in the pass, so they are not paid for twice — that rests on `extractForTopic` doing its freshness check *before* `_reserveSlot()`. `llm_max_topics` caps live calls per run (not topics visited), so a big backlog can be worked through in bounded chunks; each run resumes where the last stopped, and logs how many topics still have no results.

**A link is left where it sat, written as `[link: <url>]`** (`PostReducer.reduce`). Stripping the tag used to throw the URL away: the model got a mod's name in one place and a flat list of URLs at the foot of the prompt, with nothing saying which went with which. On a thread offering several mods — a name, a paragraph and a download each, one after another — sitting next to each other is the only thing tying a download to its mod. Topic 35651 is the case that proved it: every download there is a shields.io badge inside a link with no words of its own, in the author's second post, and the model came back with one mod called "Computica's Faction Forks" carrying all seven zips. The badge itself is no help — `isBadgeOrDonationImage` drops shields.io before the model sees it, which is right, and that is where the words "KWIN RELEASE" were. The separate `=== LINKS IN THE POST ===` list stays: it is the canonical list and carries the `[flagged downloadable]` marks. The prompt tells the model the marker is ours, not the author's, so it must never be copied into a name, a changelog entry or a `descriptionAnchors` anchor — an anchor that swallowed one would fail the slice and be thrown away. `ReducedPost` never leaves the extractor, so no marker can reach the bundle or the site.

**The prompt is written against the model's pull toward one mod.** Three lines used to point that way at once — "most posts describe exactly one mod", "a mod named in the first post is very often the same mod a later post has the download for", and the hard rule "one mod named in the first post and downloaded in a second is ONE entry", which read literally is exactly the shape of a collection thread. They now say what they mean: one mod written about twice is one entry, while a thread naming several mods with a download each is several. The thread's title names the shelf, not a mod, and a name with no download (topic 35651's first post lists forks that are not out yet) is not an entry at all.

**`role` is about the other mods on the same thread, and nothing else** — which matters because only a `main` mod is published as a mod of its own (`_threadOnlyMods`, `_mainLlmMod`, `release_detector.dart`), an `addon` or a `variant` is listed on its parent's page, and a `separate` one goes nowhere at all. So the wording has to decide two shapes that look alike. On a thread of mods that do not need each other — Hartley's four — **every one of them is `main`**; the model used to answer `separate` for all four, which would have quietly un-published them. On a thread whose first mod is a library the rest will not run without — Yunru's six — that library is `main` and the rest are `addon` with `requires` naming it; the model used to answer six `main` mods, which would have minted five permanent ids for five pages all offering the same Patreon link. The rule that decides both, and the one the prompt now states with a worked example: a mod that needs another mod **from this thread** is an `addon`, and `needs` is only for mods you get somewhere else. `separate` is written as a last resort with "when in doubt, choose main", because a `separate` mod is silently dropped. Both shapes are pinned by `test/llm_live/`.

Two special modes, now job kinds rather than branches: `llm_reprocess_only` → `llmCoveragePass` (the same coverage pass, minus the scrape, then rebuild the bundle) and `llm_test_mode` → `llmTest` (small non-persisting trial → `llm-test-output.json`).

#### Live-model tests (`test/llm_live/`)

Every other test feeds the extractor a canned answer, so they check the code around the prompt and never the prompt itself. These run the **real model against real saved forum posts** (`test/llm_live/posts/<topic id>.json`, real `detail.json` files with the scrape timestamp and the local image paths taken off) and check the facts it pulls out. Six threads so far, each there for a reason the README lists: a plain one-mod control, a mod whose post names exactly one requirement, two collection threads, a library with add-ons, and a question thread that is not a mod at all.

- **They are skipped by `dart test`.** `dart_test.yaml` gives the `llm` tag a `skip` with the command to run them in it, so the skip line tells you what to type: `dart test test/llm_live --tags llm --run-skipped`. They take minutes and need a model.
- **Settings come from `config.properties`** (`llm_base_url`, `llm_model`, and the token), so the tests read whatever the real runs read; `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_TOKEN` override without touching the file. No model server, or a server that doesn't offer that model, and each test skips itself saying which — with `markTestSkipped`, not a `skip:` argument, so `--run-skipped` cannot force a run against a server that isn't there.
- **A failure is a prompt to tighten, not a broken build.** The model is not deterministic even at temperature 0, so a check that fails once and passes twice is noise. Every check prints everything the model said (`describe()`), because the point is to be able to act on the failure without running it again by hand.
- **Loose about wording, strict about facts.** Names are compared on letters and digits only (`sameName` / `nameHolds`), and a download is checked by the bit of its address that says which mod it belongs to. So "Kwin's" versus "Kwins" never fails, and the wrong download under the wrong mod always does. Keep new checks that way round.
- The download resolver is given a mock HTTP client, so a run never reaches GitHub. Only the model call is live.

### Caching model (important)

Two independent cache layers — do not conflate them:

- **Raw-HTTP caches** (`CachingClient`): `discord_raw_cache.json`, `<qb_data_path>/qb_raw_cache.json`. When `use_cached`/`qb_use_cached` and the file exists, the client *replays* recorded responses (`isReplaying == true`) and the throttle delay drops to 0. Caches are only re-saved when not replaying. When recording, each response is written to the file as it arrives (one JSON object per line), so an interrupted run keeps what it fetched; `CachingClient.fromFile` also reads the older "one big JSON list" format.
- **Derived caches**: per-source `<name>_cache.json` (ModRepo), `assumed-downloads-cache.json`, `link-downloadable-cache.json` (per-URL "is this a direct download?" probe results), `llm-extraction-cache.json`. These store processed results so pipeline stages can re-run without recomputation. Note the `link-downloadable-cache.json` probes are live network HEAD/GET calls that bypass the raw-HTTP replay layer, so without this cache every topic re-probes the network even when `qb_use_cached=true`.

A third thing on disk, neither cache nor output: `<qb_data_path>/runs/` — `runs-index.json` plus one log file per run (see the manager core above). It follows the same save-as-you-go rule. A fourth, which is neither: `<qb_data_path>/scraper.lock`, which exists only while a job is running (see `data_lock.dart`).

**Everything that costs money or network time is saved as the run goes, not at the end.** A run killed with Ctrl-C, or one that dies part-way, must not throw away the work it already did — the next run should pick up where it left off. So: `mods-index.json` is written every 10 topics (it names the `detail.json` files, which are written per topic — an unsaved index orphans them and the next run re-scrapes them all), `assumed-downloads-cache.json` every 10 resolved topics, `link-downloadable-cache.json` every 10 probes, `llm-extraction-cache.json` every 5 topics or 5 seconds. Each also gets a final save at the end, on the failure path too. Keep it that way when adding a cache: the only end-of-run writes should be *derived outputs* (`ModRepo.json`, `forum-data-bundle.json`, `merge-debug.json`), which can always be rebuilt from the caches. The ModRepo per-source caches (`<name>_cache.json`) are still all-or-nothing.

### The public website (`lib/site/`, `site/`)

Starmodder: a static, read-only website built on what the two pipelines already collect. It is not the local results viewer under `web/` — that one is a debugging tool with a manager behind it; this one has no server at all and offers no way to change anything.

**What it publishes** (`lib/site/public_data_builder.dart` → `outputs/site/`):

- `mods.json` — one record per mod: id, name, the tidied `displayName`, authors and their other known names (`otherAuthorNames`, keyed by the credited name — one list per person, never one list for the mod, or two people on the same mod read as two spellings of one), categories, game and mod version, one picture and the other one the picture setting can show, a one-line summary, save compatibility, the day its forum thread was last posted on, the switches the filters use, and what the download button needs — `bestDownload` (one already-resolved address, its kind, and whether it opens the host's own page), `downloadCount`, and the mod's `forumUrl` and `discordUrl` for the quarter of mods with nothing to download. It is the one file the browse page fetches whole, so it holds nothing else — no post HTML, no changelogs, no galleries, and no second address for any download. A test pins it under 2 MB (it is about 1.35 MB for 1,089 mods, and the test's worst case gives 1,200 mods both pictures, a thread date and a TriOS link, which is the longest kind of address the file can carry). The margin is now the thing to watch: a field added to this record is what runs the file out of room first.
- `mods/<id>.json` — one file per mod, holding its whole page: the list record plus description, gallery, downloads, changelog by version, license, source code, support links, links out, release history, add-ons.
- `mods/<id>/index.html` — a small page of its own for each mod (`lib/site/mod_page_html.dart`). Everything on the site lives behind `#/mods/<id>`, and a hash is never sent to a server, so every shared link showed the same title and no picture in Discord and a search engine saw one page standing for 900 mods. This is the smallest fix that works: that mod's title, description and picture, one line of visible words, and a script sending a person on to `../../#/mods/<id>`. **No redirect rule, no Worker, no server that reads the address** — but the host does have to serve `index.html` for a folder, which is why `bin/site_server.dart` sets `defaultDocument` on both its handlers.
- `updates.json` — the mods that put out a new version, newest first.
- `updates.xml` — the same releases as an Atom feed, so a reader can subscribe rather than remember to visit. Every link in it is **relative** (`index.html#/mods/<id>`), which a feed reader resolves against wherever it fetched the file from — the site has no one address to hard-code, and nothing from the config file gets in. Entry names are `tag:` URIs for the same reason. The newest 200 only, or the file would grow for ever.

**Nothing internal ever reaches these files** — no config value, no token, no local path, no run id, no confidence score. A test pins that. The fields that are not the author's own words are the summary and the description, which carry `summaryIsGenerated` / `descriptionIsGenerated` so the site can label them, plus `aiSummary` and `aiDescription` — the AI summary and paragraph, published beside the author's own words rather than only in their place, because a reader can ask to see the AI words even where the author wrote some.

**What the pages actually show** — four rules that decide the content, all of them because the raw data is not fit to read as it stands:

- **Names** (`lib/site/display_name.dart`). A thread title is not a name: it carries the bracketed game version, the mod version, dates, "[WIP]" and often a leading dash to push it up the board's list. `displayName` is the title with all of that off, published only where it differs from the title, and the list is sorted by it. The title as written is still published, so a search for an old spelling still finds the mod. It builds on `ModIdStore.stripReleaseParts`, which is `cleanName` with the author's own capitals left alone — so a name and its id are worked out the same way and can never drift apart.
- **Descriptions** (`lib/site/post_html.dart`). The description is the author's own forum post, rebuilt from a short list of tags (paragraphs, breaks, lists, headings, quotes, code, emphasis, links) and published as `descriptionHtml`; `description` holds the same words as plain text. Nothing that can run, style the page or load from another host survives. Links get `rel="nofollow noopener"`, bare addresses become links, empty links left behind by a dropped picture go, and runs of line breaks are collapsed. **Only where there is no forum post** does it fall back to the merged text, then to the AI paragraph. Before this, the description was whichever text the merge liked best — for the bigger mods the Discord announcement, so Nexerelin's page read "4X in Starsector. Download: …". **A post on a thread holding several mods is nobody's description as a whole** — but where the author wrote a paragraph about one of them, that paragraph is that mod's description, cut out of the post by `lib/site/description_slice.dart`. See "A thread can be several mods" below.
- **Galleries** (`lib/site/gallery_filter.dart`). Every picture in a post used to be published as a screenshot, so a gallery was as likely to be a Ko-fi button, a build badge and the author's avatar. Three rules, in order of how sure they are: the host (Ko-fi, Patreon, shields.io…), words in the address (donate, button, badge, avatar, icon, logo), and the width the post gave it, where under 200 pixels is not a screenshot. **A picture the post says nothing about is kept** — a missing size is not evidence. This is the gallery only: the card's one picture is picked separately, see below.
- **The card's picture, and the reader's choice of two** (`_picturesFor` in `public_data_builder.dart`). A mod can have two pictures: the one the LLM found in the author's forum post, and the first picture the merge kept, which only Discord and Nexus ever give — the forum scraper collects none. The post's picture leads, because it is the one the author put at the top of their own thread, where a Discord picture is whatever was attached to an announcement. Where there is neither, the author's forum avatar stands in (a relative avatar path is resolved against `https://fractalsoftworks.com/forum/`); TriOS then falls back to the installed mod's icon, which a website cannot read. Anything that is not a plain http(s) address is dropped and the next one tried. The gallery's screenshot rules are **not** applied here, and the post's own pictures and the thread thumbnail are not sources. **This is where the site parts company with TriOS's catalog**, which takes the merged picture first — so `imageUrl` is what the site shows and `announcementImageUrl` is the announcement picture, published beside it and left out when it is already what `imageUrl` holds (the same address twice would only make `mods.json` bigger). Publishing both is what lets the choice cost no extra fetch.
- **Which download the button offers** (`lib/site/download_order.dart`). A mod can offer a dozen links and every list used to handle that differently — My List drew a button per download, so one row held four buttons all saying much the same thing, and the mod page picked by its own rule. One rule now sorts them, in the builder, and every list takes the first: a TriOS link always leads (it installs what the mod needs as well, and opening it *is* the extra step, so it is never counted as needing one), then anything straight to a file, then anything that opens the host's own page; a plain download before a mirror inside each of those; and two the rule cannot tell apart keep the post's order. It is TriOS's catalog rule (`lib/catalog/catalog_download_resolver.dart` over there) with two deliberate differences: TriOS bars a needs-another-step link from leading at all, where the site pushes it down but still offers it, since a MediaFire page beats no download at all; and TriOS breaks ties on the LLM's confidence score, which the site must not publish, so the sorting happens before publishing instead. The same sorting is applied to each add-on's downloads.
- **Summaries** (`lib/site/summary_text.dart`). A copied summary that is only a link, only the mod's name in emphasis marks, or only a list of requirements is dropped, and the AI summary takes its place labelled as AI.
- **How much AI writing a reader wants** (`aiSummaryMode` in `site/lib.js`). Three choices, the same three TriOS offers and worded the same way: Always, Only if missing (the default), Never. Always puts the AI summary ahead of the author's own on every card and row, and adds the AI paragraph above the post on a mod's page rather than instead of it — a whole forum post says more than one paragraph. Only if missing shows the author's own words and puts the AI summary on hover instead (`summaryTitle` in `site/lib.js`), since a lot of those pasted author summaries say nothing about the mod. Never means never, hover included — `aiSummaryOf` returning nothing is what enforces that. The choice is a cookie; the old on/off cookie still reads, with `off` meaning Never.
- **Categories** (`lib/site/public_categories.dart`). The forum's index and Discord's tags use 26 names between them, several meaning the same thing — "Utility mods" beside "Standalone Utilities", "Other/Misc." beside "Miscellaneous Mods". The site publishes **thirteen** instead, and the raw names are kept on the mod's own page as `rawCategories`. Two rules: a raw name the table has never heard of gets **no** category rather than a guessed one, so a new tag is something to notice; and "Discord Only" is deliberately absent, because it says where a mod was found, not what it is — that is published as `sources` (`forum` / `discord` / `nexus`) instead.
- **What a mod needs** (`LlmExtras.needs` → `PublicMod.needs`). Nearly every Starsector mod needs LazyLib, MagicLib, GraphicsLib or Nexerelin, and finding that out from a crash on startup is the oldest annoyance in Starsector modding. The LLM reads the requirement line off the post; each name is then **checked against the post** (`_groundNeeds`) — a model asked what a mod needs will say LazyLib whether the post did or not — and the builder points each one at its own page where the name matches a mod we publish. **The values only arrive on the next LLM extraction pass**: adding the field bumped `ExtractionPrompt.promptVersion`, which is part of the cache key, so every topic is read again. (It is 14 now — reading the author's later posts and adding `descriptionAnchors` bumped it again.)

**A thread can be several mods** (`_threadOnlyMods` in `lib/site/public_data_builder.dart`). Some threads hold several mods at once — "Hartley's Miscellaneous Mods" (topic 34161) is four. The merge only learns about a mod from the board listings or from Discord, so the ones the author never posted on Discord reached the site nowhere at all, though the LLM had read them off the post with their own downloads. So a `main` mod the LLM names on a thread, that no mod already being published accounts for, is published as a mod of its own: a stand-in `ScrapedMod` is built for it and goes round the same loop as everything else, which is how it gets an id, a record and a page without a second publishing path. TriOS has done this all along (`withSynthesizedAddonEntries`), and the two should agree about which mods exist. Nine rules hold it together:

- **Every thread in the bundle is read, whether or not a published mod points at it.** This used to be the other way round, because the bundle keeps every thread ever scraped while the merge only walks the mod index and the newest board pages — so publishing out of a thread nothing points at would hand permanent addresses to mods nobody had vetted. What made it safe was the grounding below, which was added later for shared threads: the translation pack that motivated the caution, whose "names" the LLM had read off zip filenames, is exactly what the name check throws out. The rule cost real mods. Topic 35651, "Computica's Faction Forks", is seven mods that were scraped and read and reached the site nowhere, because its title carries no bracketed game version (so the ModRepo forum scraper drops it from the board listing) and Computica never posted the forks on Discord. Reading every thread adds about 163 mods, on top of the 18 the shared-thread rule already found — most of them ordinary mod threads that have simply fallen behind the newest board pages.
- **The gate is the LLM's mod list, never its `isMod` answer.** The instinct is to use the model's own yes-or-no on whether a thread is a mod release. Measured, it decides nothing: of the 63 threads it calls non-mods, not one lists a `main` mod with a download, so every thread it would exclude is already excluded. It is also not clean enough to lean on — "Iron Legion Faction Mod" and "Serenity - Firefly Mod" are among its noes, and a thread whose whole title is "Delete." is among its yeses. And it is not on the bundle at all (`BundlePublisher` reads it off the LLM store for `keepThreadInBundle` and drops it), so gating on it would mean changing the thread-data model, its mapper, the bundle, the viewer's working bundle, the sample data and the test that pins the sample data — for a filter that removes no thread. If a later `promptVersion` ever starts listing downloads on threads it calls non-mods, that is the point to reach for it.
- **The single-`main`-mod rule only holds where a merged mod is there to hold it.** One `main` mod on a thread a published mod points at *is* that published mod, whatever either is called — TriOS's `_isTheCatalogEntry` rule, and what keeps "Red - the Oculian Armada" tied to the mod called "Red". On a thread nothing points at there is nothing for that single entry to be, so it is published. Most of what this brings in is single-mod threads: ExtendedControls, Custom Start, Ship Editor, ThirstSector, Nijigen Extend.
- **No age rule and no liveness rule.** A thread last posted on in 2012 publishes on the same terms as one last posted last week, and a dead link is published as a dead link. Two 2012 threads give 46 mods between them. The one place they are met is Browse's default view, because a mod with no game version passes the current-release filter (`isForCurrentGame` in [browse.js](site/views/browse.js)) and 99 of these have none — a pre-existing rule about missing data, deliberately not changed here.
- **The name has to be in the post, and a download tied to it.** A model asked what a thread holds will pad the list, and an id, once given, is kept for ever. Same grounding as `_groundNeeds`. "The post" here is the author's whole opening run, so a fork named only in the Downloads post still counts.
- **Matching is `lib/site/mod_name_match.dart`, not `cleanName`.** This is the trap. `ModIdStore.cleanName` is the id's name and can never be made keener — the id file is keyed on it — and it leaves "Useful.Tithes 1.0.a" with its version on. So it never matches the LLM's "Useful.Tithes", and matching on it would publish a second page for a mod that already has one. `modNamesMatch` is a separate, keener cleaner: it cuts a name at the first version wherever it sits (the forum writes "Disco.Balls 1.1.c - More Lamp Colour Options", version in the middle, subtitle behind it), then compares letters and numbers only. TriOS draws the same line between `cleanModDisplayName` and its record slug.
- **A `main` mod only.** An add-on or a variant stays an add-on on the page of the mod it belongs to; a page for something that cannot be installed alone helps nobody. TriOS synthesizes those too, and the site deliberately does not. On a shared thread an add-on is listed only on the page of the mod its `requires` names.
- **`partOfThreadTitle` marks the made-up ones and nothing else.** A merged mod never carries it, which is TriOS's meaning for the same field. Without it four mods with one forum link between them read as a bug.
- **A name that already belongs to a published mod is no reason to skip.** 18 of the mods this brings in carry one: four are forks that kept the original's name (Computica's Junk Pirates, Valkyrians, Blackrock Drive Yards and Stellar Networks) and the rest are a mod's own older thread (Scy from topic 8010 beside the Scy from 29535, Unknown Skies, Diable Avionics twice over). Both are worth publishing — an old thread often holds the last build that ran on an old game version, a fork is often the only one that runs on the current one — so the clash falls through to `ModIdStore`, which gives the second mod of a name the same id with a number on the end. See "Two mods can share a name" below.

**Each mod on such a thread can still have the author's own description** (`descriptionAnchors` on `LlmMod`, `lib/site/description_slice.dart`). The shared post as a whole is nobody's description, but authors usually write a paragraph per mod under its name, and publishing an AI paraphrase instead of words sitting right there is backwards. So the model is asked to **point, not write**: it copies the first few words and the last few words of the stretch of text about one mod, the extractor checks both ends are in one of the posts (`_groundAnchors`), and the builder cuts the author's real HTML out between them and runs it through `cleanPostHtml`. Three things hold it: matching is letters and numbers only, so punctuation and HTML entities cannot break it; the cut is made at line ends, never inside a sentence, so whole paragraphs come back; and anything that cannot be found is thrown away, falling back to the merged text and then the AI paragraph, labelled as AI. A sliced description is **not** marked as generated, because the words are the author's. A thread about one mod never goes near this — it publishes its first post.

**Two mods can share a name, and each page names the other** (`_fillSameNameMods` in `lib/site/public_data_builder.dart`, `sameNameKey` in `mod_name_match.dart`, `sameNameMods` in `site/views/mod.js`). 38 names on the site belong to more than one mod, covering 77 pages. Three different things end up looking alike and all three are kept: a mod's own older thread, a fork that kept the name of the mod it forked, and two people who picked the same name (the two "Kadur Remnant" threads are different mods by different people). Deduplicating would decide for the reader which build they want, so instead each mod's page carries the others, and `PublicModDetail.sameNameMods` is what holds them — the field that was called `olderVersions` while it stood for a mod's own older thread alone and sat empty, which is wrong for a fork. Four things to keep:

- **The deciding fact is when the thread was last posted on**, published as `threadLastPostOn` on the list record and on the mod's own page, read from the bundle's `lastPostDate` through `parseForumDate`. It is what separates a live thread from an archive, and between two pages called "Scy" everything else is the same on both or missing — the names match, the author is often the same person, and `addedOn` says when the thread started rather than whether anybody still posts on it. It is published as a **day**, not a moment, because the forum writes its times with no time zone on them and a browser would read them as its own.
- **The grouping is one key, not a pairwise search.** `sameNameKey` gives two names the same value exactly when `modNamesMatch` says they are one mod, so a group can be built by filing every mod under it. A test pins the two together on a list of real names; a name of nothing but punctuation keeps its cleaned form, or every such name would come down to one empty key.
- **The panel sits above the downloads.** The reader most likely to be on the wrong page of two is the one who followed a link from outside, and they never scroll to a panel at the foot. Its heading does not say "Older versions", which is true of only one of the three cases.
- **Nothing is added to `mods.json`.** The grouping is worked out in the builder and written into each mod's own file, so the one file the browse page fetches whole gains nothing but the thread date.

Two things follow for every mod on such a thread, merged ones included. Its **facts** come from the LLM entry whose name matches its own, or — on a thread naming a single mod — from that one whatever either is called (`_mainLlmMod`, both halves of TriOS's `_isTheCatalogEntry`); where several are named and none matches, the mod publishes with no LLM facts, because it used to take the first `main` entry's and every mod on topic 34161 showed Useful.Tithes' download. And a **shared thread's releases go to nobody** (`_releasesByMod`): the detector believes one version for a whole thread and cannot say which of four mods moved, and the map used to keep one mod per topic so they went to whichever came last.

**Permanent ids** (`lib/site/mod_id_store.dart`, `<qb_data_path>/mod-ids.json`). A mod's web address is built from its id, and a thread title carries the version and changes on every release — so the id is worked out once, from the name with the bracketed game version, the mod version and any date stripped off, and read back on every later run. **If that file exists but cannot be read the run fails and publishes nothing**; handing out fresh ids would move every page. A dozen real mods share a name with something unrelated (two "Kadur Remnant" threads, "CarrierUI" by two people), so each entry also records a `mark` — the forum topic id, or failing that the author — and the second mod of a name gets the same id with a number on the end. The entry also records the day a mod was first seen, which is only a fallback for `addedOn`: that is the day the forum thread was posted or the day of the Discord message the mod was read from, whichever is earlier (`_addedOn` in `public_data_builder.dart`). The id file was written in one go, so every mod that already existed shares the day it was made — sorting by that gave "recently added" in alphabetical order. The forum writes its dates as "May 04, 2014, 01:33:25 AM", and that string is read back in one place: `parseForumDate` in `lib/bot/scraper/qb/models/forum_date.dart` (also used by the viewer). A relative date like "Today at 03:12:22 PM" names no day and reads as null.

**Working out which mods released** (`lib/site/release_detector.dart`, `release_state_store.dart`, `version_text.dart`). The LLM's version reading is noisy — over one month of real data it contradicted itself 279 times — so four rules stand between it and the feed, and they are the whole point of this step:

- A reading must hold for **two scrapes running** before it is believed.
- A believed version **never moves backwards**. This is the rule that stops the site forgetting a release and announcing it again when a reading recovers.
- A version matching the thread's game version, or the bracketed one at the front of the title, is **thrown out** — the extractor confuses the two.
- Where the title names a version, a new version that disagrees with it is **dropped**. The title can veto but never propose, because only some threads carry one.

The first version believed for a mod is never a release, or a backfill would announce every mod at once. State lives in `<qb_data_path>/mod-releases.json`: what each thread is believed to be on, how long the current reading has held, every release so far, and which saved bundles have been walked. A run advances it by one bundle; `bin/backfill_releases.dart` walks every saved bundle once to fill in the history, and is safe to re-run.

**Where it is called** (`lib/site/public_site_step.dart`): after the QB pipeline publishes a bundle (`afterBundle` — the only place a release is ever recorded), and after a merge (`afterMerge` — the release state is read, not changed). Each reads the other half back from `outputs/`.

**The site itself** (`site/`): plain ES modules, no build step, the same look as the viewer. `app.js` is a hash router over `views/home.js`, `browse.js`, `mod.js`, `author.js` and `about.js`; `lib.js` holds the DOM, address and fetch helpers. Three things about it worth knowing:

- **One search box, in the bar at the top, on every page** (`app.js`). It suggests up to five mods as you type — the whole list is already loaded — and "/" puts the cursor in it. `#/authors` with no name is the people index; the browse page has no author dropdown, because a list of 562 names cannot be used.
- **"Recently added" on Home shows whole rows, one by default.** How many cards make a row is read off the grid itself and re-read when the page changes width, so it is never a row and a half. A small "1 · 2 · 3 rows" picker beside the heading changes it and the choice is kept in `localStorage` (`starmodderRecentRows`). Enough mods are loaded to fill three rows at the widest the page gets; the rest are `hidden`.
- **"Recent updates" has one button that opens every changelog** (`expandAllChangelogs` in `views/home.js`), beside the heading in the same `.section-head` row the rows picker uses. The label says what a press would do — "Show all changelogs" until they are all open, then "Hide all changelogs" — and it is read off the page each time rather than remembered, because rows are also opened one at a time. A fold's `toggle` event does not travel up the page, so it is caught on the way down (capture); without that, opening the last shut row by hand would leave the button still offering to show them all. It is left out entirely when no release on the page has notes.
- **"Recent updates" says where its list comes from** (`releasesNote` in `views/home.js`, `noteWithMore` / `openInfoDialog` in `site/lib.js`). A dated list reads as a list of what came out that day, and it is not: it is what a program noticed, having read a version number out of a forum post, which it sometimes reads wrong. So an amber-edged note sits above the list saying that in two sentences, and a "More about this" press opens a box with the five things worth knowing — that a mod is here because its version moved, that a reading must hold for two runs, that the date is the day we noticed rather than the day of release, that a mod which never writes its version never appears, and that the changelog is the author's own words. The short version is on the page because a reader who presses nothing should still know the list can be wrong; the long version is behind a press because five paragraphs above every visit to the front page is somebody else's page. It is left out when there are no releases at all — the empty notice already explains itself. The box is a plain `<dialog>` built when the button is pressed and taken out of the page when it shuts; every way out (the ×, the dimmed page, Escape, the back button) goes through one `shut()`, because the dialog's own `close` event is not sent by every browser. The About page says the same thing in its own words under "How releases are worked out" — keep the two in step.
- **Browse opens on what a reader can use.** Sorted by current game version first, then most recent release, then name; mods for older releases are left out behind a switch that is on, with a count and one click to include them. Versions that differ only in spelling ("0.98", "0.98a", "0.98a-RC8") are one choice, and which release is "current" is worked out from the data — the highest version at least five mods are built for, so one misread "9.99" cannot push every real mod into "older".
- **One download button, everywhere a mod is listed** (`downloadButton` in `lib.js`). Grid cards, browse rows, My List rows and Home's release rows all draw the same button, and it says what pressing it does: "Install with TriOS", "Download", "Download page", or — for a mod with nothing to download — "On the forum", falling back to "On Discord" the way the mod's own page falls back. The button stops its own click from reaching whatever it sits in, which is what keeps a press on a release row from opening that row's changelog instead. My List used to fetch every listed mod's own file just to find its downloads; the winner rides on the list record now, so a row costs no request at all.
- **The button is only ever the button, and it is the same width down a list.** "Download" and "Install with TriOS" are different lengths, so a button left to size itself gave a page of cards a ragged right edge; in a browse row it was worse, with right edges up to 48 pixels apart. The button spans the card at the foot, and takes a fixed 148-pixel column in a row. Nothing else shares its line — how many downloads a mod has is said by `downloadCountBadge` among the mod's other small facts ("2 downloads", not a link, since the card and the row already lead to the page that lists them), and on My List it joins the row's line of author, version and game version. On a phone the fixed column stands down and, in a browse row, the button drops to a line of its own — standing it beside the words left the mod's name a letter wide.
- **The reader's own mod list.** Ticking the "+" on a card puts a mod in a list kept in `localStorage` and nowhere else; `#/list` shows it, and `#/list?ids=a,b,c` shows somebody else's — the whole list travels in the address, so sharing one needs no account and no server. The page also works out what the listed mods need that is not itself in the list, which is the thing a shared list nearly always gets wrong. `lib.js` owns the list (`myList`, `toggleInMyList`, `watchMyList`); the count in the bar at the top watches it, and drops its watch when the nav is redrawn.
- **The look is one block of names at the top of `style.css`.** Nothing anywhere writes a colour or a text size out longhand — every one is a name from that block, which is what lets the light version be one short `prefers-color-scheme` block rather than a second stylesheet. A few sizes are set outside the scale on purpose: the letter standing in for a missing picture, the two arrows on a screenshot, and the arrow that opens a release row on Home; those are shapes, not writing. The light cyan is **darker** than the dark theme's — light cyan on white cannot be read, and an action nobody can read is not an action.
- **Which of a mod's two pictures to show is a setting** (`imageChoice` / `imageUrlOf` in `site/lib.js`, the "Mod pictures" section of the Settings dialog). Two choices: the forum post's picture (the default) or the Discord or Nexus one, which is what TriOS shows. The choice lives in `localStorage` (`starmodderPicture`), and ticking it redraws the page. Every list draws its picture through `imageUrlOf` — cards, browse rows, My List rows, Home's release rows, the search suggestions and the big picture at the top of a mod's page — so nothing reads `imageUrl` directly any more. A mod with one picture carries no `announcementImageUrl` and looks the same either way, which is most of them; the site reads `announcementImageUrl || imageUrl`. The little per-mod HTML pages (`mod_page_html.dart`) always use `imageUrl`: they are read by Discord and search engines, which have no setting.
- **Spacing is a setting, and Dense is the default.** The Settings button in the bar at the top opens a native `<dialog>` with an Appearance section: Dense or Comfortable. The choice lives in `localStorage` (`starmodderSpacing`) and is written onto `<html>` as `data-spacing` — by a tiny inline script in `index.html` before the first paint, and by `applySpacing()` in `lib.js` after. Every gap and padding in `style.css` is one of the spacing names in the block at the top (`--gap`, `--gap-wide`, `--gap-cells`, `--pad-page`, `--pad-block`, `--pad-cell`, `--pad-front`, `--pad-bar`); the `:root[data-spacing="comfortable"]` block swaps in the roomier numbers. Only the room between and around things changes — never the size of the words, the pictures or the controls. **The page's top-level `.stack` is the sections, spaced by `--gap-wide`; a `.stack` inside it is one group, spaced by the smaller `--gap`**, and a heading directly in a stack carries no margin of its own — so a heading always sits nearer its own words than the section above, and a page reads as groups. Keep `--gap-wide` clearly bigger than `--gap` in both blocks, or that is lost.
- **Cyan means "you can do something here"** — a link, a button, a chip. A mod's name is not an action, so a mod's name is white and only turns cyan under the pointer. When every title was cyan nothing stood out, because everything did.
- **Cards and rows are a box holding a link**, not a link themselves (`.mod-card` > `.card-inner`, `.mod-row` > `.row-inner`). The "+" has to sit on top of them, and a button inside a link is not allowed and behaves differently in every browser.
- **Every route change starts at the top**, except coming back to Browse, which returns to where the reader left off. Two traps in that, both pinned by how the router is written: the position has to be read by `route()` **before** it empties the page (`notePageScroll`), because an emptied page has nowhere to scroll and the browser says zero from then on; and it is filed against the address Browse last wrote for itself (`lastBrowseHash`), because `location.hash` at that moment is already the mod page the reader is on their way to. Browse scrolls itself and says so (`noteScrollPlaced`), and the router's scroll-to-top stands down for that one page. The skip link cannot be a plain `#app` link either: the hash picks the page, so following one would send the router looking for a page called "app".

- **Which build the site is** (`site/version.json`, `showBuild` in `app.js`). The footer says `v47 · 28cbe0f · 2026-08-24` beside the "data collected" line, and the commit links to it on GitHub — that is what makes a bug report answerable. The file is written by the release workflow (`git rev-list --count HEAD`, the short commit, the commit's day), not by any Dart code, and it rides into the published repo because a publish copies everything in `site/`. It is **gitignored**, so it only exists in a build; run from the repo the fetch fails and the footer carries no version line. It is fetched by hand rather than through `data()`, because it is part of the site and not part of the data — `?data=sample` must not send it looking in `sample-data/`. Every commit to `master` is built and released (there are no hand-made tags — the release is named `v48` after the same count), so the number on the site moves the next time the host downloads a release, which is twice a day. Work that should not be built goes on another branch.

It fetches every file from **its own origin** and nothing else — never GitHub, never another host — and must never depend on anything a plain static server cannot do: no Cloudflare Workers, no Pages Functions, no redirect rules. Opening it with `?data=sample` reads the hand-written examples in `site/sample-data/` instead of the real files, which is how it is worked on before a run has built anything; those examples are pinned to the models by `test/site/sample_data_test.dart`, so a shape change has to be made in both.

**Publishing** (`lib/manager/publish_service.dart`): a publish copies the three data files, every per-mod file, and the contents of `site/` into the clone, so the pushed repo is a complete servable website next to the data it reads. A per-mod file in the clone that this run did not produce is removed. Missing website files are a log line, not a failure — the existing outputs still go out.

### Results viewer (`bin/viewer_server.dart`, `lib/viewer/`, `web/`)

A local `shelf` server that serves the static `web/` frontend, a JSON API (`lib/viewer/api.dart`, `data_access.dart`) over the output files, and — when a config file can be read — the management API. Binds to `127.0.0.1` only. Viewer endpoints never write; the only writes are jobs on the management API. When output/bundle shapes change, keep this viewer in sync. Default dirs: `--data-dir qb_data`, `--outputs-dir outputs`, `--root-dir .`; also `--config config.properties` and `--no-manager`.

The old "the server never reads `config.properties`" rule is now narrower: it **may** read it, for the manager's environment and guardrails, and **must never serve** any of its values (the data path excepted). No route serializes `BotConfig`, `ScraperEnvironment` or `LlmSettings`.

`lib/viewer/server_app.dart` (`buildServerHandler`) composes the parts. It picks the `api/manager` subtree off *before* the router/cascade rather than mounting it — a mounted handler's 404 ("no run by that name") is read as "no such route" and falls through to the static files, losing the reason.

The server plants a console log tree and bridges the `logging` package (`Common.initTimberForConsole` / `Common.bridgeLoggingToTimber`); without that, `RunLogCapture` would write empty per-run logs for server-started jobs.

**Which build is running** (`lib/viewer/site_version.dart`, `GET /api/version`): the build number, the commit and the day it was made — the same three values, from the same file, that the public website shows in its footer (see **The public website** above). `SiteVersion` reads `<--root-dir>/site/version.json` first, because a released copy is unpacked from a tarball and has no git checkout to ask; that is why this line used to be blank in production. Failing that it asks git the same three questions (`rev-list --count HEAD`, `rev-parse --short HEAD`, `log -1 --format=%cs`), so a version shows while working in the repo too. `showVersion` in `web/app.js` draws it small and dim under the status chip ("v48 · 28cbe0f", the day on hover). It is for bug reports, so it never makes a fuss: neither way working gives `{}` and the site shows no line at all. Nothing is cached — it is read fresh each time.

#### Frontend (`web/`, no build step, plain ES modules)

`app.js` is a hash router over view modules that each export `render(root, parts)`; shared DOM/fetch helpers are in `lib.js`. The chrome is a **sidebar** (`index.html`), not a top bar: a Home entry, then grouped sections — **Data** (Topics, ModRepo, Forum Data Bundle), **Jobs** (Runs and queue), **Debug** (ModRepo explorer, ModRepo diff, Bundle diff, LLM test report, Files, Log). The two diff viewers are first-class sidebar entries, reached at `#/merge/changes` and `#/bundle/changes`; they are no longer sub-tabs inside the merge/bundle pages. The lit entry is the deepest nav route whose path segments all match the current hash, so `#/bundle/changes` lights Bundle diff while `#/bundle/12345` lights Forum Data Bundle. `#/home` is the default. Sidebar icons are inline SVGs built from `web/icons.js` (Tabler Icons, MIT, copied in as path data — nothing loads from the internet at run time).

The home page (`views/home.js`) is the front door: one search across Topics, the bundle, and ModRepo at once (three endpoints in parallel, results grouped, each row linking to a detail page); quick-action job buttons; the last finished run with its counts and a "what this run changed" link; and health numbers (topics with no download, no LLM answers, placeholders) that each open the topics list pre-filtered.

Confirmations and notices are **in-page dialogs**, not the browser's own popups: `lib.js`'s `askDialog()` (yes/no, the confirm button focused so Enter still works) and `noticeDialog()` (one OK). `manager.js`'s `confirmAndSubmit` shows `describeJob`'s sentence in an `askDialog`.

**List state rides in the URL.** Topics, ModRepo and the bundle list read their search / filters / sort / page from the hash query on render (`lib.js` `hashParts` strips the query; `hashQuery` reads it) and write it back with `replaceHash(buildHash(...))` as state changes — so a reload, a bookmark, or the back button brings the same list back, without every keystroke piling up in history. Rows-per-page stays a site-wide `localStorage` preference, out of the URL. The home health links use the query form, e.g. `#/topics?filters=noDownload`.

Every paged list draws `lib.js`'s `pager()`, which also carries the **Show** box for rows per page — 25 to 500, or all on one page. The choice is one setting for the whole site, kept in `localStorage` and read by `pageSizePreference()` when a view builds its state. On the wire, `pageSize=0` means "every row, one page"; a named size over 500 is still capped, and nonsense still falls back to 50. A list that adds a pager should pass the size callback too, and reset `page` to 0 inside it — page 4 of 50 is not page 4 of 250.

Every page opens with a `lib.js` `breadcrumbs()` trail (Home is prepended; the last crumb is the current page, the rest are links) — it replaces the old per-page "‹ Back to …" links on detail pages. Detail pages (thread, ModRepo mod, run, merge group) end with a closed-by-default `lib.js` `rawJson()` fold, so anything the tidy layout leaves out is one click away. Detail pages stack their blocks in a `.stack` (or the thread page's `.thread`) container that gives even spacing between blocks, so no block carries its own margins; an emptied block (a loader cleared it) takes no space, so a section that isn't there leaves no gap.

A page that shows a **list of folds** gives it a `lib.js` `expandAllButton(container, selector)` — one button whose label says what a press would do ("Expand all" until they are all open, then "Collapse all"). Pass a selector narrow enough to leave out the folds *inside* a fold: `details.change-card` on the two diff pages and the topic history, `details.panel` on the merge groups list, `:scope > details` on the LLM test report. It reads the folds from the DOM on every press, so it never holds a stale idea of what is open, and it keeps up with folds opened one at a time by catching `toggle` on the way down (that event does not bubble). A list that redraws itself must call `button.refresh()` afterwards — new folds arrive with no toggle to notice them. Where a fold's shut row says what changed, it says **which fields** moved, not how many: `changedFieldsLine()` names the first three and counts the rest, `changedFieldsTitle()` puts the full list on hover. It goes on a **second line at the left**, under the name — out on the right, past the author, nobody reads it. That is why the `.change-hint` span is built *after* the chevron: the summary is a wrapping flex row, the hint is given `flex-basis: 100%` so it takes a line of its own, and anything after it would be dragged down with it. It is left out entirely when there are no fields to name, so an added or removed row carries no empty second line.

`web/manager.js` is the only place the frontend talks to `/api/manager/`. It owns three things:

- **The status poller.** One shared `GET /status` loop — about a second while a run is live or queued, five seconds idle, stopped while the tab is hidden. Views call `subscribe(fn)` and drop the subscription on `hashchange`; nothing else polls. `refresh()` returns the in-flight ask rather than starting a second one, so a view that loads mid-beat still gets a real answer instead of `null`.
- **Sending jobs.** `submitJob` / `cancelCurrent` / `confirmAndSubmit`, plus `describeJob` — the one plain sentence every confirm box shows. A refusal is re-thrown carrying **the server's own message**: those are already written for people, so never wrap them in wording of our own. UI-started jobs always send `replayAllowed: false`.
- **The ticked topics.** The selection set lives here, not in the view, so it survives paging, searching and switching views. It also rides in `sessionStorage` (`viewerSelectedTopics`), so a half-built selection survives a reload. Cleared on submit.

`mountHeaderChip()` draws the always-on status chip at the foot of the sidebar (`#status-chip` in `index.html`). It is a status dot whose colour carries the state — grey off, green ready, amber when jobs wait, cyan and pulsing while one runs — plus a word or two and, mid-run, a progress bar.

Two views read all this: `views/runs.js` (live run, queue, history, and the start-a-job area — two cards, one to scrape/extract and one to merge into ModRepo.json) and `views/run.js` (`#/runs/<id>`: record, log tail, run again). Two gotchas worth keeping: the start-a-job cards are only redrawn when the manager goes on or off — redrawing them on the poller's beat would wipe what the user just picked — and the log route's "no log file" answer arrives as a `MissingFile` from `lib.js`'s `api()`, not as a body field. A live run's page redraws every second, so the run page's **log panel is built once and kept**: the panel and its scrolling `pre` are never taken out of the page, and each draw only removes the lines that fell off the top of the tail and appends the new ones (`linesDroppedFromTop` lines the two windows up). Rebuilding it, or even detaching it for a moment, throws away where the reader had scrolled to and anything they had selected, which makes a running log unreadable. The scroll is held at the same distance from the bottom, so a reader sitting at the foot of the log is left there and it follows itself. The **LLM test** job has no other way in — its report page (`views/llm_test.js`) carries the only button that starts it.

Comparing two saved things — two merges' mods, two bundles' topics — is one helper, `lib/viewer/compare_rows.dart`. Callers pass how a record is keyed, which fields are worth looking at, and what to call it on screen; `merge_views.dart` and `bundle_views.dart` are thin over it. A field can carry a `describe` instead of before-and-after values, which is how "the post text changed" says so without the text nobody kept.

**A diff shows what moved and nothing else.** Only changed fields get a row — that part was always true — and a field holding a list or a map now gets picked apart too, so only its changed entries are listed. A field says how with `itemsOf`: `mapItems` and `listItems` in `compare_rows.dart` cover a plain map and a plain list of names, and `bundle_views.dart` has its own for downloads, links and the LLM's mods. `urls` used to print all four of a mod's links on both sides because one of them gained an "s", which is not a diff. Two things follow. **An `itemsOf` that comes back empty means the field did not really change** — the entries were only written in a different order — and the field is dropped; on real data that moved six of 63 changed mods back to unchanged, and it is why order is deliberately not a change in `listItems`. And **every key of an entry is compared, not only the named ones** (`_partsThatMoved` in `bundle_views.dart`); the names are labels, not a filter, because a row saying "this changed" and then listing nothing sends somebody hunting for a change the page decided not to mention.

The three pages that show one of these tables — the ModRepo diff, the Bundle diff and one topic's history — share `web/views/diff_table.js`. Keep it that way: three copies drifted before, and a reader comparing two pages about the same change should not see it worded two ways.

The Bundle view has a what-changed page (`views/bundle_compare.js`) built the same way as the merge one, and a run's page links straight into it — "what this run changed" compares that run's bundle with the one before it. The link only appears when there is an older snapshot to compare against.

**Watching a run mid-flight.** The newer side of that page can also be `working` — the data on disk right now rather than a saved snapshot — which is how a run is watched while it is still going. It rests on the save-as-you-go rule above: a run publishes its bundle at the end, but writes what it scrapes and what it pays the LLM for as it goes, so the gap between the newest saved snapshot and what is on disk is what the run has done up to this second. A live run's page offers "What this run has changed so far" instead of the finished-run link. The page is brought up to date by a **Refresh button** and in no other way — it is drawn only when the newer side is the data on disk, since two saved bundles never change. It deliberately does not redraw itself on a timer: that throws away where the reader had scrolled to and every card they had opened, which on a page whose whole purpose is reading what changed is worse than being a minute out of date.

`lib/viewer/working_bundle.dart` builds that side: the bundle **as it would be published right now**, in the same shape a snapshot has — post text swapped for the same fingerprint, local image paths and the forum's session token stripped the same way. Four things hold it together. It is **compared against a snapshot and nothing else**; nothing may publish or serve it as a bundle, the same rule snapshots live under. Which threads make it in is decided by `keepThreadInBundle` in `qb/mod_thread_filter.dart`, the **same function the real publisher calls** — a rule copied instead of shared would show a thread as added or removed for as long as a run lasted. It **holds its answer** against a stamp of every file the working data lives in, and re-reads only the detail files that actually moved, so a rebuild mid-run costs almost nothing (a cold build over a thousand topics is about half a second). And "last written" is **the newest file write, not the newest scrape time** — an LLM pass changes what a run has produced without re-scraping anything, and reading the scrape times would tell the reader the data was a week old while it changed under them.

The data on disk is only ever the **newer** side; asking for it as `a=` is refused in plain words. A merge has nothing to show this way and does not offer it — a merge deliberately writes nothing until it finishes.

**One thread page, reached two ways.** `#/topics/<id>` and `#/bundle/<id>` render the same page: `views/topic.js` is a thin wrapper that calls `renderThreadPage` in `views/bundle.js` (with its own "back to" link). It shows the working (on-disk) data for the thread — the latest truth — as thread and post fields, the post in a sandboxed frame, the author's own later posts each in a frame of their own below it with their dates and their images and links, the rule-based and LLM downloads, the LLM extras, and a TriOS card preview at the foot. When the published bundle is behind that data it shows a **staleness banner** (`bundleStaleness` compares the thread's `scrapedAt` against the bundle's `generatedAt`; states are `stale` / `absent` / `noBundle`) with a one-click Rebuild bundle button. The shared pieces — the sandboxed post frame, image and link lists, the download tables, the LLM mods with their downloads and extras, the three per-topic job buttons (`topicActionBar`, drawn only when the manager is on), and the staleness check with its Rebuild button (`bundleStaleness` / `topicStaleness` / `rebuildBundleButton`, shared with the history page) — live in `views/extraction_views.js`. Download tables come in two on-disk shapes, and telling them apart matters beyond this page: the topic endpoint serves the resolver's `DownloadCandidate` (`sourceUrl` / `resolvedUrl` / `archiveFilename`) out of `assumed-downloads-cache.json`, where one topic's list is wrapped in a `candidates` field, while the published bundle carries `AssumedDownloadCandidate` (`originalUrl` / `resolvedDirectUrl` / `fileName`) as a plain list. Reading a bundle for the cache's shape is why the diff pages showed no download changes at all on real data for as long as they existed; `downloadRowFromCandidate` / `downloadRowFromBundle` map each to one plain shape. The thread page reads working data, so it uses `downloadRowFromCandidate`; `downloadRowFromBundle` stays as the converter for the published shape. Long file names and URLs in these tables are shortened for the cell (full value on hover, `.dl-table` keeps them to one line so the table scrolls sideways rather than stacking).

**One topic's history** (`views/topic_history.js`, `#/topics/<id>/history` and `#/bundle/<id>/history`, reached by the History button on the thread page) reads like a git log: one entry per run whose saved bundle changed that topic, newest first, down a rail with a dot each. Runs that left the topic alone are not listed. `GET /api/topics/<id>/history` builds it — `topicHistory` in `bundle_views.dart` walks the kept snapshots oldest to newest and diffs neighbours over the same `bundleFields` the diff page uses, so the two can never disagree about what changed or what to call it. Three things to keep: it reads snapshots through `bundleRunUncached`, **not** the two-slot holding pen, which is sized for the compare page's pair (a test pins this); the answers are held per topic until the set of saved snapshots changes; and it is now exactly what the Bundle diff page works out for the same topic (`topicChanges` is one call to `changedFields`), rather than a second path that could disagree with it. History only reaches as far back as `qb_bundles_to_keep`, so the foot of the rail says where it starts, and "never in a bundle" is worded differently from "in every bundle and never changed". Unpublished working data leads the log as a hollow-dot entry with the Rebuild bundle button, the same way a git viewer shows uncommitted changes.

The Merge view is three files: `views/merge.js` (routing, summary, groups, removals), `views/merge_shared.js` (which merge is being looked at, the run picker, cell formatting) and `views/merge_compare.js` (before-and-after for one group, and what changed between two merges — the `#/merge/changes` diff page, its own sidebar entry). Which merge is picked lives in `merge_shared.js`, so it survives moving between the merge pages; every merge API call goes through `withRun()`. The list of saved merges is asked for again on each page load, so one that finished while the tab sat open turns up — but not on a redraw after picking, which would be a wasted request.

**Manager off is a mode, not an error.** When status says off, the chip's dot goes grey and it says "Viewing only", the Runs view explains how to turn it on in one sentence, Home shows a "viewing only" note instead of the quick-action buttons, and Topics renders no tick boxes and no buttons — the page reads exactly as the read-only viewer always has.

## Conventions

- **Plain English** in all user-facing copy (viewer text, FAQ, docs) and in explanations. Avoid jargon.
- `analysis_options.yaml` enforces `avoid_print` (use the `timber`/`logging` helpers, not `print`), required return types, and prefer-final/const rules.
- Spec-driven changes live under `openspec/` (`specs/` are current capabilities, `changes/` are proposals). Use the `opsx:*` skills to propose/apply/archive changes here.
- For any Starsector game/API/modding question, use the `starsector-knowledge` skill — never answer from memory, since the API changes between game versions.
